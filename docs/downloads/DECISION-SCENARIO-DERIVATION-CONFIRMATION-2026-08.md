# 待决策项 · 分支推演与确认

## 0. 这份文档做什么

上一份《全面架构与战略分析》给了一张决策清单和路线图,但只列了"是什么、建议是什么",没有把**每条路走下去会发生什么、能不能回头、和其他决策有什么牵连**说透。这份文档补这一课:对 §3 里每个待决策项,推演"选A"和"选B"两条分支各自的连锁后果,再给出一个不藏着掖着的建议——推演不是替你做决定,是让你做决定时看清楚全部代价,而不是只看到我上一份文档里精简过的那一行建议。

顺带做了一次新的核实(§5),因为推演过程中发现有一个点上次没有查到底。

## 1. D3:gbrain+kairon 归并(ADR-0413)分支推演

**当前状态**:已经是既成事实(#1600 已合并),ADR 是补签字,不是预决策。

### 分支A:签字 ACCEPTED

- 立即后果:无——工程状态不变,只是治理记录补齐,PROPOSED→ACCEPTED 是纯文档动作。
- 连锁后果:`BET-Y1Q3-T6-01` 从 `in_progress/awaiting human_gate` 转 `done`,T6-SUBTRACT 轨道的下一条候选(T6-04)可以正常排队(目前它已经在候选池里,理论上不依赖 T6-01 是否 done,但台账卫生角度看,悬着一个"实施完成但决策未闭环"的条目会一直是台账里的噪音)。
- 不可逆性:签字本身可逆(可以之后再发起 supersede 这个 ADR),但它签的是"接受已发生的事实",不影响回滚 tag 的存在——`pre-knowledge-merge-20260816` 依然在,签字不会让这个安全网消失。

### 分支B:否决,触发回滚

- 立即后果:执行 ADR-0413 里写好的回滚流程——checkout `pre-knowledge-merge-20260816`、恢复 `.gitmodules` 双条目、revert 归并 commit。
- 连锁后果:归并后(8-16 到现在)如果有任何新 commit 落在 `projects/knowledge/` 目录下,需要手工 replay 到回滚后的双 submodule 结构里——**这是唯一的真实代价**,而且代价大小取决于这几天有没有人在这个目录下继续写代码(如果没有,回滚几乎零成本;如果有,工作量随天数累积)。
- 不可逆性:技术上可逆,但"高成本可逆"——时间拖得越久,回滚成本越高,这是这个分支**唯一会随时间变差**的决策点。

### 推荐与置信度

**推荐分支A(签字确认)**,置信度高。理由很直接:证据链完整(去重清单闭环、测试保护线守住、失败数无新增),核心风险(不可逆)已经被证伪(现在是"可逆但有成本"),而且成本本身是"越晚处理越贵"——**这是本轮所有待决策项里,拖延本身就是一种隐性成本的一项**,不建议压着不表态。

## 2. D5:物理多机张力(ADR-0414)分支推演

**当前状态**:不涉及任何已执行的工程动作,纯粹是"要不要把 G-DEL.1 的状态语义从 BLOCKED 改成 PARKED-DEFERRED"。

### 分支A:接受方案a(改语义,不降标准)

- 立即后果:`phase-scope.yaml` 里 G-DEL.1 状态字段改写,不再产生"BLOCKED 但没人修"的持续认知噪音。
- 连锁后果:验收标准(物理多机是金标准)保持不变——**这不是放弃多机目标,是给"暂时做不到"一个诚实的状态名**。任何 CI/巡检看到 PARKED-DEFERRED 不会再触发误导性的"待修复"信号。
- 与其他决策的牵连:这一项直接决定了上一份路线图 §6 阶段4"单机灾备速赢"要不要现在就做——如果确认 PARKED-DEFERRED,意味着"物理多机短期内不会解决单点风险"这件事被正式承认,那么单机灾备(launchd 26 个 plist 未入库那一项)的优先级应该**上调**,不该继续放在阶段4;如果不接受这个方案、坚持认为多机会较快到位,灾备投入的紧迫性可以适当往后放。**这是两份文档之间最大的一处联动,值得你决策时一并考虑。**

### 分支B:否决,维持 BLOCKED + 加注记

- 立即后果:G-DEL.1 继续显示 BLOCKED,但补一条注记说明"deferred 期间无需修复"。
- 连锁后果:ADR-0414 自己已经写明这个方案的代价——"deferred 期间持续产生'为何 BLOCKED 无人修'的认知成本",本质是把分支A解决的问题原样保留,只是加了个免责声明。
- 不可逆性:两个分支都是纯状态语义,互相可逆,随时可以改回来。

### 推荐与置信度

**推荐分支A**,置信度中高。理由:方案本身诚实(不偷偷降标准),且解决了一个实际存在的噪音源。唯一让我保留"中高"而不是"高"的原因是——**这个决策会联动灾备投入的优先级**(见上),你在签字前值得先想清楚"物理多机 deferred 到底会 defer 多久",如果心里有一个大致时间线,这个决策会更踏实,而不是纯粹的状态清理。

## 3. OPS-INFRA 三项处置分支推演

### 3.1 `cron-daily-dashboard.sh`(静默失败≥11天)

- **分支A(删cron行)**:立即止损,governance-scanner 每小时已覆盖同等信息面,推演不出实质性信息损失。**这条基本没有反对理由**,唯一要做的确认是:governance-scanner 的产出格式和用途是否真的能替代 dashboard 原本给人看的那个视图——如果你或团队还在看 dashboard 生成的那份文件,替代前最好瞄一眼两者产出是否等价。
- **分支B(补脚本)**:需要先弄清楚这个脚本本来该做什么(它从未入过git,连原始需求都没有记录),等于是重新设计一个已经不知道原意的东西——成本和收益都不确定。
- **推荐**:分支A,置信度高,但**建议先花5分钟对比一下 governance-scanner 和 dashboard 历史产物的内容差异**,别单凭"名字听起来像"就下结论。

### 3.2 `bin/mof-drift` 路径断

- **分支A(改crontab路径指向真实位置)**:恢复这条巡检,但要先确认它和 Hermes 05:00 的 `omo-drift-detection` 检测范围是否重叠——T6-08 报告里说"两者检测面待比对,倾向后者(即倾向删,不是倾向修)"。
- **分支B(删这条crontab,全交给Hermes)**:如果两者确实重叠,这是更干净的选择,少一处需要维护的路径。
- **推荐**:**在分支A和B之间,推荐先做一次轻量核实**(比对 `bin/mof/mof-drift` 和 Hermes `omo-drift-detection` 各自的检测逻辑差异,可能只需要读两个脚本,不需要新起一个bet),再决定删还是修——这条和 dashboard 那条不一样,dashboard 有明确的替代者,这条的"替代关系"还只是推测,不建议直接拍板删。

### 3.3 E-DOC(ln-001~005)是否接线

- **分支A(补实现)**:五条规则里,ln-001/002/003 是静态检查(相对好实现),ln-004 和已有的 freshness 泛规则语义相邻(可能是扩展现有机制,不是从零写),ln-005 已经有生成脚本只差门禁。**这五条的实现成本其实不算高**,T6-08 报告已经给出了具体落点(governance-checks.yaml + 一个检查脚本)。
- **分支B(标注DESIGN-ONLY,不接线)**:零工程成本,但保留"文档说得像已经在管,实际没管"的认知落差,直到下次有人真的因为以为 Documents 边界被拦截而吃亏。
- **推荐**:**倾向分支A,但不是最高优先级**——这五条规则本身要解决的问题(防止 Documents 目录被脚本污染、防止跨域修改绕过治理)是真实存在的风险,只是目前没有证据说这个风险已经被利用过。可以作为阶段2(2-4周)工作的一部分,和"扫描所有调度任务"那项工作一起派工,不需要单独立项。
