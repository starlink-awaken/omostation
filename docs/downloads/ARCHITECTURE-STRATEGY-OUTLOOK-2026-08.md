# 织星/eCOS 全面架构与战略分析 · 下一阶段规划

## 0. 这份文档的定位

前面几轮已经做完了"诊断"和"局部核实"：8月15日的《总纲》诊断了"声明≠事实"这个系统性病灶并给出治理机制；8月17日的 OPS-INFRA 核实报告把宿主机三套调度系统的真实状态摸清楚了；今天早些时候的复盘确认了这两轮派工的产出质量都不错，而且自己纠正了我之前判断错的地方。

这份文档要做的是往前一步：**不是再诊断一遍，是把当前所有"已经摸清但还没决策"的东西汇总成一张可执行的下阶段地图**，并且在诊断的基础上做一次架构/战略层面的再评估——因为过去 48 小时台账又往前跑了一大截（Y1Q1 21/23、Y1Q2 37/38，且冒出了两条之前没有的 ADR：0413 D3 决策补档、0414 D5 张力澄清），如果不重新盘一次现状，规划会建立在过时的信息上。

**方法论延续总纲的纪律**：每个论断标来源；不确定的标"未核实"；不把"已执行"和"已批准"混为一谈。

## 2. 关键结构性发现：治理机制本身正在经受住反复检验

这一点值得先说清楚，因为它改变了下一步规划的基调。总纲诊断"声明≠事实"是系统性病灶后，过去几轮的实际运行给出了三次独立的"免疫系统起作用"的证据：

1. **T6-02 复盘自己抓到自己**：台账曾把 T6-01 标 done，但实际还没合并到 main——这个错误不是被外部发现的，是 T6-02 自己的验证轮抓出来的（见 T6-02 retro"打假"第1条）。
2. **T6-03 复盘诚实记录"假 done"**：一次 run 被 block 了却被误标完成，T6-03 自己的复盘如实写了"honest gap"，没有掩盖。
3. **T6-08 反过来纠正了我自己**：我的 OPS-INFRA 蓝图里"E-DOC-001~005""ADR-0190"两处编号是转写错的，"三重审计重复"这个判断被证明不成立——T6-08 没有将错就错，而是回仓核实、明确打假、纠正了派工指令本身的错误。

**这三次加在一起说明**：8月15日总纲提出的"打假"纪律不是写在纸上的口号，是真的在被每一轮 bet 执行时使用，而且这次连**派工指令的作者（我）**的错误也被同一套纪律捉住了。这是这套治理体系目前为止最强的一个正向信号——**下一阶段的规划可以往"扩大这套机制的覆盖面"倾斜，而不必再重新设计一套新机制。**

同时也要如实说清楚代价：这套纪律目前主要靠"每个 bet 强制写复盘+打假段"撑着，是人力/agent 精力密集的，还没有自动化到"CI 强制检测声明与事实不符"的程度（那是 D0-D5 里 D5 想做但目前只做到"closeout 前必须有 retro"这一步，没做到"retro 内容真实性自动校验"）。

## 3. 待你拍板的决策清单（按紧迫度排序）

### 3.1 D3：gbrain+kairon 归并（ADR-0413）—— 最高优先级，因为已经是既成事实

**现状**：#1600 已在 2026-08-16 合并到 main，`projects/knowledge/{gbrain,kairon}` 已经是单一目录，`.gitmodules` 双条目已移除。ADR-0413 是"补档"，不是"预决策"——工程实施已经跑完了，等的只是你对这个既成事实的正式确认。

**"不可逆"判断已被修正**：原先总纲 §11 说这一步"不可逆"，需要谨慎；T6-01 实施后重新核实，实际是**"可逆但有成本"**——回滚 tag `pre-knowledge-merge-20260816`（指向归并前 main `b7530c27`）已经打好，checkout 即可恢复双 submodule 结构，代价是归并后的增量 commit 需要手工 replay。

**证据闭环**（不是自称，是有具体数字）：去重后 src 行数减少与去重清单（9,433 行）实测差 42 行（9,475 vs 9,433，属于合理误差范围）；test_loc 454,784 高于基线 350,854（保护线守住，没有靠删测试冲指标）；kairon 测试 0 失败；gbrain 测试失败数与基线持平（388 vs 389，零新增）。

**你需要做的**：确认 ADR-0413 状态从 PROPOSED → ACCEPTED，或者否决并触发回滚流程（tag checkout + `.gitmodules` 恢复 + revert 归并 commit）。**这不是一个需要新调研的决策，是一个需要你看一眼证据、点头或摇头的决策**——证据已经很完整了。

### 3.2 D5：物理多机张力（ADR-0414）—— 次优先级，纯粹是状态语义澄清

**现状**：ADR-0225/0226（物理多机是官方验收标准，G-DEL.1 现在 BLOCKED，因为可达物理主机 2<4）与 ADR-0247（战略转向多 Agent 协作优先，物理多机 deferred）三者之间从未互相引用（实测 grep 0225/0226 全文 "0247" = 0 次），导致 G-DEL.1 长期挂着 BLOCKED 状态但没人知道该不该修。

**起草的方案（方案 a，等你确认）**：不降低验收标准本身，但把 G-DEL.1 的状态语义从 `BLOCKED`（暗示"待修复"）改成 `PARKED-DEFERRED`（明确"无动作项，不产生告警噪音"），触发恢复条件是"ADR-0247 的 deferred 解除 或 四机硬件到位，二者取先"。

**为什么这值得你花两分钟看一下**：这类"没人敢删的过时告警"正是 §4 里提到的静默失败模式的近亲——G-DEL.1 长期 BLOCKED 但没人处理，和 dashboard cron 静默失败 11 天没人发现，本质上是同一种"信号存在但没人看/看了也不知道该不该管"的组织问题，只是这次是有记录的、这次是主动澄清的。

## 4. 四层模型（model / governance / constraint / control）现状更新

在 OPS-INFRA 蓝图 §1.3 的基础上，用 T6-08 的实测结果更新一版：

| 层 | 8月17日蓝图时的判断 | T6-08 实测后的修正 |
|---|---|---|
| **Model**（愿景/规划层） | 5 代愿景并存，D3/D5 待决 | D3/D5 已有 PROPOSED 方案，从"缺方案"变成"缺签字"——**层本身的工作已经做完，卡在决策环节** |
| **Governance**（治理层，BET/ADR/retro） | 机制设计完备，执行中偶有"假 done" | 新增证据：机制不仅设计完备，还表现出**自我纠错能力**（见 §2），但纠错目前依赖人力写复盘，未自动化 |
| **Constraint**（约束层，chain-bind/hard gate） | `--bet` 硬门禁已上线，但可被 `cockpit agent start` 绕过（T6-02 打假第3条） | 本轮未新增证据，**这个绕过口子大概率还在**，值得下一轮验证是否已堵上 |
| **Control**（管控层，宿主机调度/告警） | 三套调度系统重叠情况不明，怀疑三重冗余 | **实测推翻**：三层职责正交，无需合并；但发现真问题——**11天静默失败没有任何告警机制**，这是控制层目前唯一的结构性缺口 |

**读出来的规律**：model/governance 两层这一轮进展很扎实，短板已经清楚地收敛到 **constraint 层的绕过口子** 和 **control 层的告警缺失** 这两个具体点上——不再是"哪里有问题不知道"，是"知道具体在哪，等排期"。

## 5. 风险地图（按"造成损失的可能性 × 造成损失后的可恢复性"排序）

1. **launchd 26 个 plist 未入库**（灾备清单 T6-08 实测）——可能性低（硬盘损坏不常见）但恢复代价最高（逐个凭记忆重建，含绝对路径与环境变量）。**这是当前单点风险里恢复难度最大的一项。**
2. **静默失败无告警是一个模式，不是一次事故**——dashboard 断流 11 天、mof-drift 路径断，都是"脚本/路径已经错了但没人知道"。这次抓到的是两个具体实例，**没有理由相信这是全部**——任何一个 crontab/launchd/Hermes 任务只要输出没人看，都可能正在犯同样的错误。这比两个具体脚本本身更值得重视。
3. **constraint 层的绕过口子**（`--bet` 硬门禁可被 `cockpit agent start` 绕过）——目前没有证据说明被利用过，但只要口子还在，"每个 bet 必须绑定"这条纪律的实际强制力就是打折的。
4. **E-DOC 边界规则的认知落差**——不是"规则被绕过"，是"规则从来没被接线"，但文档层面读起来像是已经在生效。中风险：不太可能造成即时事故，但会让人对整个 MOF 体系的"已强制"清单产生不必要的信任。
5. **Y2/Y3 规划纵深几乎为零**——不是紧急风险，是长期风险：如果 Y1 收口后没有及时把 Y2 拆解到 bet 粒度，执行节奏会断档。

## 6. 未来 6-12 个月分阶段路线图

### 阶段 1（本周内，纯决策，不需要新派工）

- 签字 ADR-0413（D3）、ADR-0414（D5）——或否决并触发已经写好的回滚流程
- 对 §3.3 三项 OPS-INFRA 处置项二选一
- 批量清理 §3.4 的 4 条遗留 PROPOSED ADR（可以派一个轻量 bet 做初筛，但最终定性还是要你签）

**这一阶段的特点是：所有前置调研都已经做完，纯粹是拍板，预计花费你本人的时间不超过一小时。**

### 阶段 2（2-4 周，需要新派工）

针对 §5 第2条"静默失败无告警是一个模式"，建议不要只修那两个具体脚本，而是做一次**系统性排查**：

- 派工目标：把所有 crontab/launchd/Hermes 任务（三套系统合计约 35-40 个任务）逐一核对"脚本是否真实存在于其声称的路径"+"最近一次产出是否新鲜"，仿照这次 dashboard/mof-drift 的方法论，一次性扫完，而不是等下次又是别的任务默默坏了才发现。
- 同时把 constraint 层的绕过口子（`cockpit agent start` 直接绕过 `--bet` 门禁）验证是否仍然存在，如果存在，评估堵上的成本。
- 这一阶段直接复用 T6-SUBTRACT track 的既有流程（claim → start --bet → verify → closeout → retro），不需要新设计流程。

### 阶段 3（1-2 个月，规划性工作，非修复性）

- 把 Y2（Y2Q1-Y2Q4）从"3/3/3/3 个占位符"细化到可认领的具体 bet——目前 Y2 全是 0/3，这不是执行滞后，是规划本身还没往下拆解。建议先拿 Y2Q1 做一次拆解练习，摸清楚拆解的工作量，再决定是一次性拆完 Y2 全年还是按季度滚动拆。
- 结合 T6-04/05/06（当前仅有的 3 条可认领 bet）执行完之后，T6-SUBTRACT 这条轨道大概率会进入"候选池又见底"的状态，提前想清楚下一批减法目标是什么，避免轨道空转。

### 阶段 4（视阶段 1-3 结果决定是否需要，不预先承诺）

- 若阶段 1 里 D5 被确认为"物理多机长期 deferred"，那么 launchd/crontab/Hermes 单机绑定的风险（§5 第1条）会变成一个需要正式面对的长期状态，而不是"迟早要多机所以先不管"。建议阶段 1 决策落地后，再评估要不要单独立项做"单机灾备速赢"（T6-08 报告里已经给了具体方案：三件快照脚本挂到现有 08:30 cron，工作量约一天）。
- 这一项刻意放在阶段 4 而不是阶段 2，是因为它的优先级依赖阶段 1 的决策结果，不应该抢在决策之前先动手。
