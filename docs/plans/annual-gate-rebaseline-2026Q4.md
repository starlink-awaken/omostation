# Y1Q4 年度门重基线提案 (BET-Y1Q3-T1-04)

## 背景

Y1Q4 年度门 `code_loc <= 690000 AND adr_active <= 120 AND gac_rules <= 80` 的
690K 基线按 Y1 初制定, **未纳入两个变量**:

1. **gbrain 重写噪音** — gbrain 独立仓库整体重写(god-module 拆分等),
   名义 churn +179K/-179K, 净值仅 +360(纯对称改写, 净贡献≈0)。
2. **新项目出生** — cockpit-ui/omlxc/runtime 等新项目在 Y1 期间落地,
   其代码量是"出生"而非"膨胀"。

当前实测(2026-08-18, `bet-ledger.py surface`):

| 指标 | 当前 | 基线(2026-08) | 变化 |
|---|---|---|---|
| src_loc(总量口径, 含子模块) | 1,663,966 | 726,412 | +937,554(+129%) |
| test_loc | 803,823 | 350,854 | +452,969(+129%) |

## 净值口径 (T1-03, since 2026-08-01)

| 项目 | churn_add | churn_del | 净值 | 重写噪音 |
|---|---|---|---|---|
| _root | 678,328 | 1,275 | +677,053 | 1,254 |
| gbrain | 179,046 | 178,686 | **+360** | 183 |
| agora | 67,048 | 60,366 | +6,682 | 1,314 |
| omo | 39,007 | 9,817 | +29,190 | 4,372 |
| cockpit | 34,664 | 9,109 | +25,555 | 2,366 |
| cockpit-ui | 36,574 | 6,187 | +30,387 | 1,660 |
| runtime | 28,916 | 7,346 | +21,570 | 1,629 |
| ecos | 23,255 | 9,769 | +13,486 | 2,532 |
| omlxc | 24,697 | 2,934 | +21,763 | 1,996 |
| l4-kernel | 3,727 | 791 | +2,936 | 437 |

**关键结论**:
- 名义 "+937K" 中, `_root` 的 +677K 是主仓自身 churn(含合并/工具变更),
  gbrain +179K add 中约 179K 是重写(净值 +360)。
- **真实业务增长 ≈ +145K**(cockpit-ui +30K / omo +29K / cockpit +26K /
  runtime +22K / omlxc +22K), 与 T1-03 retro 结论一致。
- 总量口径 1,663,966 中, 子模块(gbrain/agora/cockpit 等)占大头,
  690K 基线只锚定了主仓初态。

## 三种情景

### 情景 A: 守原门 (code_loc <= 690000)

- 按**净值口径**衡量: 真实增长 +145K, 若以"Y1 初基线 + 净增长"为门,
  690K 仍可守住(726K 基线 + 145K 净增长 = 871K > 690K, **已超**)。
- 结论: **原门无法守住** — 即便剥离重写噪音, 新项目出生 + 主仓 churn
  已把净值推过 690K。守原门 = 刻舟求剑, 会诱导 T3-01 式谎报。
- **建议: 不采用**。

### 情景 B: 调门 (code_loc 重基线到净值口径)

- 门值建议: **code_loc <= 1,100,000**(净值口径实测 1,663,966 中,
  剥离 gbrain 重写噪音后真实承载 ≈ 1,480K; 预留 20% 余量)。
- 或者按"基线 + 净值增长 + 余量": 726K + 145K × 2 = 1,016K, 取整 1,020K。
- 论证: 该门允许 Y1 期间的项目出生与工具 churn, 同时仍约束"净膨胀"。
  gbrain 重写不再计入(重写是维护成本, 不是表面扩张)。
- **建议: 采用 1,100,000**(含余量, 避免频繁重基线)。

### 情景 C: 拆门为分项目门

- 门改为: `_root code_loc <= 700K AND 各子项目净增长 <= 预算`。
- 优点: 每个子项目独立预算, 新项目出生有明确配额。
- 缺点: 多项目门使门检复杂, 且 `_root` 门仍需重基线(当前 _root 已 677K+)。
- **建议: 作为情景 B 的补充约束**, 不单独替换。

## 推荐

**采用情景 B(调门到 1,100,000)+ 情景 C 的分项目净增长观测**:

```yaml
gates:
  Y1Q4:
    question: 表面积是否达标?
    pass: code_loc <= 1100000 AND adr_active <= 120 AND gac_rules <= 80
    on_fail: Y2 不启动扩展, 继续做 Y1
```

同时:
- 门检从"总量口径"切换为"净值口径"(gbrain 重写噪音剥离)。
- 新增分项目净增长观测(季度报告), 不设硬门, 但超预算需解释。
- adr_active <= 120 / gac_rules <= 80 维持原值(本提案不改)。
