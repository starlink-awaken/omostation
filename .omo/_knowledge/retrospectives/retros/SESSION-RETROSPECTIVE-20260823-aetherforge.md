## 2. 三个失败模式(按发现顺序，不是按严重性)

### 模式 1：数据层验证深度不够 —— "代码路径对了"≠"真的起作用"

**症状**：PR #51 声称"记账接线完成"，代码确实调用了 `record_usage`，`usage_log` 表确实在持续增长(55 条记录)。但 `SUM(cost)` 恒为 `0.0` —— `estimate_cost` 依赖的 `PricingRegistry.get_price()` 因为 model_id 格式不匹配（网关传入全限定 `ENG-XXX-CLOUD/model` 形式，注册表按 `{短provider名}/{裸model}` 建索引）永远查不到价，`deepseek: $50/block` 配置从未真正触发过。

**根因**：验证 PR #51 时只确认了"记账函数被调用"（usage_log 行数在涨），没有确认"记的账是不是非零"。这是验证的最后一公里没走完——数字在动 ≠ 数字对。

**排查中的一个反向教训**：一度怀疑 longcat/nvidia/volcano/opencode-go 四个引擎"缺定价数据"，准备去查/编真实费率，查证 SSOT 后发现 `cost_multiplier: 0.0` 是这几个引擎（免费层/扁平订阅）的**设计意图**，不是数据缺口。差点在没查清楚设计意图前就往定价表里塞了不该塞的数字——这类"看起来像 bug 实际是设计"的情况，动手前必须先查 SSOT 里有没有写明意图，不能只看表面数据。

**防范**：验证记账类功能，不能只看"函数被调用/行数在涨"，必须看"记录的值是否符合预期量级"。

---

### 模式 2：惰性状态同步 + early-return 组合极易出执行顺序 bug

**症状**：PR #52→#53→#54 三连，同一个功能（401 淘汰死 key）修了三轮才真正落地：
- #52：淘汰逻辑本身写对了，但传的是 token 名（`kimi`）不是 db 里真实的别名解析后名（`kimi_for_coding`），`UPDATE` 语句 `WHERE` 条件零匹配，静默无效。
- #53：修了名字解析，但更新代码放在了 `_sync_credentials` 的"key 未变提前返回"逻辑**之后**——所有构造时已经拿过一次 key 的引擎（等于全部引擎）永远走不到那行代码。
- #54：把更新提前到 early-return 之前，真正生效（`sqlite3` 实测 `is_active: 1 → 0`）。

**根因**：`_sync_credentials` 这类"惰性同步 + 提前返回优化"模式，本身对副作用的执行时机很敏感——一旦有代码需要在"值不变时也执行"，就必须显式挪到 return 之前，容易被默认的"没变化就跳过"直觉带偏。

**每一轮都不是靠代码审查发现的，是靠"模拟完整链路实测"**（构造 adapter → 手动调用 sync → 触发淘汰 → 查 db 真实状态）——这个方法论本身值得固化：**对有状态副作用的代码，读代码判断不出时序对不对，必须真的跑一遍再查底层状态**。

**防范**：类似"惰性缓存 + 条件更新"模式，写完后不要只测"最终结果对不对"，要专门测"值不变的分支是否也执行了该执行的副作用"。

---

### 模式 3：部署收尾纯手动重复 14+ 次，操作面靠人肉 tail -1 兜底

**症状**：
- dev 仓库一度 detached HEAD（验证后无害——本地 main 分支指针其实全程正确，只是 HEAD 指向游离，大概率是某次诊断用的 `git checkout <sha>` 后没切回来，且因为本地 `main` ref 本身没问题，没有造成实际数据丢失风险）。
- 一次分支清理命令因为上一条命令的 cwd reset，误推到了 `omlxc` 仓库（分支名在那边不存在，推送失败无害）。
- 15 个已合并 PR 的功能分支残留在 GitHub（`gh pr merge --rebase` 没带 `--delete-branch`），复盘时才顺手清理。

**根因**：`dev 仓库 switch main → pull → 删分支 → cd 部署目录 → fetch → checkout → 重启 → curl 验证` 这套流程手打了 14 遍，每次都是新的一长串命令 + `tail -1` 肉眼核对，没有自动化兜底。

**修复**：`tools/sync-and-deploy.sh`（PR #56）封装了"合并之后"的纯重复段，加了三个当场真实撞过的安全网——工作树不干净直接拒绝、detached HEAD 主动报警、健康检查重试 5 次而非死等固定时长。已自举验证一次真实运行成功。

**防范**：任何被人工重复 ≥3 次的固定操作序列，第 3 次之后就该脚本化，不要指望"这次会记得看清楚 tail -1 的输出"。

## 3. 制度有效性评估

这次会话没有走 BET / workflow 治理链路（不是台账认领任务），但有其他制度在起作用：

| 制度 | 拦截了什么 | 证据 |
|---|---|---|
| **Claude Code 权限分类器** | agent 自我合并未经人工审阅的 PR | 两次拦下 `gh pr merge`（PR #50、#54），每次都停下问用户，没有绕过 |
| **端到端真实验证纪律**（本会话自建，非仓库既有制度） | "代码看起来对但实际没用"类 bug | 模式 1/2 的全部三轮修复都是靠真实请求/真实 db 查询发现的，纯代码审查发现不了 |
| **`make test` 全量门禁** | 语法/逻辑层面的回归 | 17 个 PR 全部 423 passed，过程零测试回归 |

**缺口**：没有制度拦住"部署收尾手动操作导致的 detached HEAD / 误推分支"——这类操作面风险完全靠运气没有变成真事故，PR #56 是本轮唯一一次事后补的防御，不是既有制度接住的。

**这一轮的价值不在"修了多少个 bug"，在于反复验证了同一条方法论：写完代码不算完成，跑一遍真实链路、查一眼底层数据的真实值，才算完成。** 三个失败模式（记账空转、淘汰时序、部署操作面）没有一个是靠读代码发现的，全部是靠"构造真实请求/模拟真实调用链路/查 sqlite 真实状态"揪出来的。下一个 agent 接手时，遇到"看起来应该已经工作了"的功能，先怀疑，再验证，不要因为测试绿了就相信生产行为也对。
