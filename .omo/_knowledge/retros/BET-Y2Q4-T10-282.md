# Retro — BET-Y2Q4-T10-282 spine 缝不可达立案 + 验收尺 PATH 假阳

## 本意

BET-Y2Q4-T10-281 修好了 B4b 的 E7 量具（`scripts/tools/launchd-workspace-reality-check.py` 的
`repo_root` 缝），这条 BET 做修好之后的**第一次真实测量**，并把测量里出现的两类缺口各自归位：

1. 量具自己报出的 2 条 workspace 命中，是否都在 B4b 的改道范围内；
2. `scripts/tools/spine-daily-ingress.py` 里那个与 T10-281 同形的死缝（T10-281 显式列为
   非目标，所以它需要一个自己的台账条目，而不是继续挂在别人名下）。

准入腿范围限定在**立案**：写 spec、把 BET 插进台账，不动生产代码、不动 plist、不迁移任何数据面。
工程腿（本 retro 的新增部分）把 spec §2 的 5 条 done_when 全部变成实测绿。

## 实际发生

### 准入腿

测量读数（origin/main，`python3 scripts/tools/launchd-workspace-reality-check.py --json`）：
`total_plists=85 / pointing_to_workspace_count=2 / pointing_to_install_count=40 / other_count=43`，
两条命中是 `ai.hermes.gateway` 与 `com.omostation.test-archive-purge-7d`。

逐条读到文件内容才定性：`ai.hermes.gateway` 的 Workspace 字面量只出现在继承来的巨型 `PATH`
字符串里（`...:/Users/xiamingxing/Workspace/bin:...`），**不是入口、不是 WorkingDirectory**，
因此不属于「入口在检出」的改道对象；`com.omostation.test-archive-purge-7d` 是真的——
`:45` argv `cd /Users/xiamingxing/Workspace && …`、`:48` `WorkingDirectory`、`:64/:66` 日志路径。
所以 B4b 批次 2 的**真实待改道是 1 条而不是 2 条**。

同一把尺的另一个后果：它对整份 plist 做子串包含判定，于是任何在 `PATH`/日志/注释里出现过
Workspace 的服务都会被计成命中。B4b 的验收判据「workspace 命中数 → 0」在这种口径下**不可满足**
（除非改环境、把 Workspace 从所有服务的 `PATH` 里摘掉，那不是本轮范围）。这条被写进 spec 的
`done_when` 作为量具的第二项修复（路径判别式），而不是留给下一次现场发现。

spine 侧复测（origin/main `scripts/tools/spine-daily-ingress.py`，275 行）：`:29`
`_LIB_DIR = Path(__file__).resolve().parents[1] / "lib"` 解析到 `scripts/lib`，该目录在**检出根
与运行时安装位都不存在**；`:33` 的 `from repo_root import code_root, state_root` 因此
`ImportError`，`:34` 起 `except` 返回 `:36`/`:38` 两个字面量 `/Users/xiamingxing/Workspace`。
即：**缝按构造不可达，且 `state_root()` 的兜底也钉死在检出根**，声明 profile 对它的写落点零影响。

台账准入用 `bin/gac/ledger-safe-insert.py` 先 dry-run 再实插，`bets` 578 → 579，插入点 46321 行；
插入前 `origin/main` 上 `status: in_progress` 的 BET 为 **0** 份（本轮这条是第 1 份）。
两次拒绝都是真实口径问题，不是工具毛病：① 我把条目写成 `- id:` 列表项，工具要的是单个 BET
mapping；② `completion_evidence.axes` 必须是 `['engineering','operational','value']` 且
`overall_state` 必填。查 `origin/main` 上 `in_progress` 的 BET 数量为 **0**——没有任何先例可抄，
于是我拒绝写 `delivery_accepted`（那等于宣称验收了未交付的工作），改用
`NOT_STARTED` / `not_started` 显式空态，让「工程腿还没做」这件事在台账上可读。

### 工程腿

四件（两件脚本 + 两份用例）合并为 PR #5045 → squash `0b67fac45451201a70847de7c2dda0f85885ddbe`。
过程中三件事值得留下：

1. **自己的「已排除顺序依赖」是假声明**。用例 4（摘掉守卫后拿不到 `ModuleNotFoundError` 契约）
   最初写成只把兄弟尺文件排在前面复跑，据此在 PR body 里断言"无顺序依赖"。这条断言是错的：
   真实残留面是 `sys.path` 里的 `bin/lib` 与 `repo_root` 模块缓存，写它的是**任何** exec 过真实
   尺/写者的用例，而 30 个 `tests/unit/*.py` 里匹配 `bin/lib|repo_root` 的远不止我排的那两三个。
   换 30 文件批量跑立刻复现 `FAILED: DID NOT RAISE ModuleNotFoundError` —— 按 done_when 2 的
   口径，那份红必须来自守卫本身，红变成顺序依赖就等于判据失效。修法是载入前显式摘残留、
   载入后恢复快照（commit `41e492fa2`），并把 PR body 里的原句改成显式订正。
2. **同批 PR 被一条日历炸弹钉红**。#5045 的 `gac-gate` 恒红与内容无关：

   PR #5046 squash `c85038635`。推 base 不重跑 pull_request 检查，**必须有新 commit 推上去才触发**，
   所以 #5045 是在 `41e492fa2` 落地后 gac-gate 才自动转绿，没有手工 rerun。
   顺手订正一处我在 PR body 与 registry 注释里写错的受害面：open 的三个 PR 里只有 #5045 因这条炸弹红，
   #5044 的真实阻碍是 `CONFLICTING`，不是日历炸弹。
3. **冷 worktree 的环境类失败要归因而非绕过**。`make gac-local-gate` 67 项 PASS / 1 项 FAIL

   未使用 `--no-verify`。**归因订正**（收口腿复测；工程腿此处原写「`bus-foundation` 与 `agora` 未物化」，

## 教训（可复用判据）

1. **量具报出的命中要逐条读到文件内容再定性**——「计数」和「在范围内」是两件事。本轮 2 条命中里
   1 条是 `PATH` 继承噪声；若不读内容就按 2 条排改道计划，B4b 批次 2 会背一条不存在的活。
2. **一把尺的验收判据必须与它的计数口径一致**。整文件子串包含这种口径写出来的「→ 0」判据是
   结构性不可满足的；发现即要把判别式一起立案，不能留到执行现场再解释为什么绿不了。
3. **`except ImportError` 里的字面量兜底 = 缝从未生效**，且这类缺陷**没有任何测试会红**（与
   T10-281 同形、与 AGENTS.md §7「写路径要在调用时刻解析」同族）。判据是问
   `repo_root.__module__`／`_LIB_DIR` 实际解析到哪，而不是看代码里有没有 import 缝。
4. **台账没有先例时按口径写显式空态，不借邻近状态**：`in_progress` 的 BET 在 main 上是 0 份，
   `ledger-safe-insert` 只约束键名与 `overall_state` 非空，真正的枚举校验发生在 `status: done`
   时（`bin/plan/bet-ledger.py`）。把未交付的工作写成 `delivery_accepted` 能过插入工具、过不了
   事实核对。
5. **准入腿与工程腿分离登记**：本轮 `done_when` 里那条「`spine-daily-ingress.py` 写落点跟随
   profile」的前置是**数据面往哪落的署名裁定**（历史 spine 缓冲在检出根，改道即可能造孤儿），
   裁定权在 principal。写进 spec §3 `non_goals` 与 §4 熔断，而不是顺手把范围改掉或缩小判据。
6. **hermetic 断言的复现面要按「谁共享同一份残留」枚举全集，不能按记忆里的邻近文件**。
   判据：写下「已排除顺序依赖」之前，先用 `rg -l` 算出所有会改同一份全局态（`sys.path` /
   `sys.modules` / CWD / env）的文件并批量跑；子集绿只证明子集。
7. **判据跑在哪个事件上，决定它红给谁看**。只挂 `pull_request` 的规则（X2-C05）会让 main 恒绿、
   所有 PR 恒红，而"main 绿"会被误读成"这条规则没问题"。查某条治理门禁的真实评审对象：
   `rg -n "pull_request.head.sha|if:.*event_name" .github/workflows/`。
8. **台账里的 `expect` 要做算术可行性预检**。`total = workspace + install + other` 是守恒式，
   「一桶降、其余三桶不变」不可能同时成立 —— 写判据时先算一遍，否则执行现场只能改判据或造假读数。
9. **治理 CLI 的根可能被一次 import 覆盖**（`bin/agent-workflow.py:278` 的 `__file__` 根被 `:283`
   `from omo.workflow import WORKSPACE` 换掉）。在 linked worktree 里跑 claim 报 `BET_NOT_FOUND`，
   第一问不是「台账里没有吗」，而是「这个进程读的是哪一棵树的台账」——实测规范检出落后 origin/main
   25 个 commit 时就会这样。同族缺陷登记在收据「订正与残留」§5。
