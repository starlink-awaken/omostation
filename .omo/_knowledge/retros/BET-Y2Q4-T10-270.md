## 2 happened — 实际发生了什么

**编号在动手前就被占了。** 原定 `BET-Y2Q4-T10-269`。claim 完成、spec 落盘、digest 算好之后，插台账前跑
`git fetch`，发现 `origin/main` 已从 `1612bb75d` 前进到 `f0c5ce934`，而前进的那**一个** commit 正是
「`chore(bet): BET-Y2Q4-T10-269 立项 —— 统一 scheduler 检查的检出（A4 ↔ cockpit）` (#4895)」。
于是这条固化必须改铸为 **T10-270**（先例：T10-234 撞号改铸）。改铸面：spec 文件名 slug、frontmatter
`bet_id`、台账条目 id / `decision_ref` / `write_surfaces` 三处路径、以及 digest 重算 —— 共 5 处，
全部由字段名定位，没有一处靠"搜索旧字符串"。

**基线重做的选择记下来。** 固化腿的 worktree 当时**零 commit**，所以用了 `git merge --ff-only origin/main`
把分支指针推进到新的 main（只带进 2 个文档文件，无 gitlink 变化），而不是另起一个新 claim。
这不是"用 merge 吸收上游"（那条禁令针对的是已有交付 commit 的分支）：ff-only 后的树与从新 main 重新
claim 逐字节等价，且省掉一次 16 子模块 PASW 布置。判据：**分支有无自己的 commit** 决定能否 ff-only。

**§6 三处陈旧指针是被自己的 verify 逼出来的。** 为写 item ② 需要引用"本仓禁止 rebase/merge/pull"的站点，
按 §7⑥「引用行号前先取该行内容核对」去读 `gac-worktree.sh:507`，结果是 `then`。继续查发现
AGENTS.md §6 的三处指针（`:507` / `:683-691` / `:780-783`）全部陈旧，真实站点 `:966`/`:994`、
`:967`–`:985`、`:1241`–`:1244`。就地修正，并把旧号在文中的消失钉成断言。

**存在性检查抓不到这类漂移 —— 这是本轮新增的一层。** 先写的 verify 是"扫 AGENTS.md 所有 `file:line`，
断言行号在文件行数内"，跑出来只有 2 条 `MISSING-FILE`（prose 里省略目录的裸文件名与一份不在本仓的
部署仓脚本），**三个真陈旧指针全绿通过** —— 因为它们指向的行确实存在，只是内容不是那件事。
于是把它换成按内容断言（`966` 行须含「禁止 rebase/merge/pull」、`985` 行须是 `exit 2`、
`1244` 行须含「先 submit 开 PR」）。这与 §7⑥ 是同一条纪律的第二面：⑥ 说"行号会漂"，本轮补"检测它漂的
尺必须是内容而不是行号存在性"。

**判据刚写进文档就被自己误读一次。** PR 开好后我跑 `git diff --name-only HEAD origin/main -- <ledger> <AGENTS.md>`
看到两个文件名，读成"上游又动了我的对象"。实际 `HEAD` 已含我自己的 commit，`HEAD origin/main` 是把**我的**
增量反向显示。正确的左端是 `git merge-base HEAD origin/main`（实测 `= origin/main = f0c5ce934`，
上游零漂移，`mergeable=MERGEABLE`）。item ② 的判据文本写的是 `<my-base>`，在 pre-commit 时刻恰好成立，
所以规则本身没错 —— 错在我把"插入前"的用法直接搬到了"提交后"。
**收口腿据此做了实修**：`AGENTS.md` §7 item ② 与 spec 的判据正文都改写为显式
`git diff --name-only "$(git merge-base HEAD origin/main)" origin/main …`，并把"左端必须是 merge-base、
不得写成 `HEAD`"连同这次误读的实测读数一起写进判据；纪律段补一句「判据里凡是依赖『当前分支还没有自己的
commit』的隐含前提，必须把左端 ref 显式写进判据正文」。spec 正文因此变化 ⇒ 台账
`accepted_specifications[0].content_digest` 必须重算 —— 这正是 item ③ 说的两类互不相交的摘要位，
本轮按字段路径分别枚举刷新，未用任何"值不等于新值"的反选。

**收口腿第一次过门禁是硬 FAIL，不是静默失效。** 五个文件一次过 `gac-local-gate --scope files` 当场
`FAIL | 2 SOFT WARN`，决定性一行是 `change-lane-check: FAIL mixed lanes=docs,docs_data,governance_state`。
读 `bin/change-lane-check.py:196 allowed_for()` 才看清 `:207` 是 `if "governance_state" in lanes and len(lanes) > 1`
—— **governance_state 必须独占一次提交**，而 `ALLOWED_COMBOS`（`:14-21`）里有 `{docs, docs_data}`，所以正确的
是三条 lane 里那条独占的必须拆开。处置按规则本身走：拆成 `c18e04ea1`（AGENTS.md + spec + receipt + 台账，
`lanes=docs,docs_data`）与 `154e04151`（retro，`lanes=governance_state`），**不加 `--allow-lane`、不设
`AGENT_WORKFLOW_ALLOWED_LANES` 自我授权** —— 那条扩权口是 workflow 注册表授权用的，不是给当前这条腿发许可证用的。
两次分_lane_跑都 `PASS (68 checks executed, 2 SOFT WARN)`，两条 warn 与固化腿逐字同名（`system.yaml` 缺席 =
T10-235 摘库后的常态；KOS db 缺席 exit 78 = skipped 非 passed）。

**台账块边界的一次越界自纠。** 驱动脚本取 `BET-Y2Q4-T10-270` 块时只把块尾判成"下一条 `^- id: `"，

## 3 changed — 因此永久改变了什么

- `AGENTS.md` §7 多三条 证据→判据→纪律；§6 三处指针重钉；两条 frontmatter 日期。
- 新增一条可复用判据：**引用行号前先按内容核对，且"行号存在"不构成核对**（写进 verify 的是内容断言）。
- 新增一条可复用判据：**基线漂移检查的左端是 merge-base，不是 HEAD**（提交后尤其容易搞错）——
  这条不是停在 retro 里，它已回写进 §7 item ② 与 spec 判据正文。
- 台账交付前必须 fetch 后**同时**查两件事：同块是否被重排、目标编号是否已被占。
- `CHANGE-LANE` 的真实约束在此前只是"被拦过一次"的印象；本轮读源码钉成可复述事实：**governance_state 独占提交**，
  `{docs, docs_data}` 可同批。

## 4 lessons — 下一轮该带走什么

1. **撞号是并发面的常态，不是异常。** 编号唯一性检查要和"台账是否被上游重排"放在同一次 fetch 里做，
   两者都是"插入前的前置条件"。
2. **零 commit 的 worktree 可以 ff-only 重定基；有 commit 的必须造受控后继。** 判据是分支上有没有自己的
   commit，不是"感觉会不会冲突"。
3. **一条新写好的判据，交付前要按"它是否会被我自己误用"再读一遍。** 本轮 item ② 的 `<my-base>` 在提交后
   就被我用成了 `HEAD` —— 措辞里少了一个"pre-commit"限定词。**固化 lane 的正确形状因此是两条腿**：
   第二条腿不只是补 evidence，还要把第一条腿里被实测误用过的措辞收回感知面（否则文档里留着的就是那把
   刚割过自己的尺）。
4. **改了 spec 正文，`content_digest` 就必须在同一批里重算**，且刷新脚本要按字段路径分两类枚举
   （规范绑定摘要 vs receipt/retro 证据摘要）—— 本轮就是靠"这次真的改了 spec"来检验 item ③ 的判据可用性，
   结论：分类枚举 + 双向断言（每个证据位等于磁盘文件、`content_digest` 等于 spec 字节）足够。
5. **门禁 FAIL 的判据要读源码，不要读提示。** `mixed lanes=` 那行只列出撞在一起的 lane，不说哪条不能共行；
   去掉 `governance_state` 与去掉 `docs_data` 都能"看起来过"。**判据**：遇到 change-lane FAIL 先 `sed -n` 取
   `allowed_for()` 的分支，按规则拆提交；**纪律**：绕规则的那个 flag 存在不等于本轮可以用它。
6. **文档类交付"改了就重算摘要"没有例外窗口。** 本轮 receipt 在提交后又补了 §4.5（如实记那次硬 FAIL），
   摘要立刻失效 —— 说明"写完再一次过门禁"的顺序本身不安全。**判据**：凡在 commit 之后还编辑过被台账引用的
   文件，就在下一次提交前重跑一次字段路径刷新脚本；工具上就是 `python3 /tmp/t270_closeout_ledger.py`
   （它自带双向断言，绿了才允许提交）。
