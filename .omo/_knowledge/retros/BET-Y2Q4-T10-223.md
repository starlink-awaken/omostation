## 根因（三层）

1. **协议层**：读端 15min 新鲜度硬上限（安全约束，合理，不动）；
2. **发布层**：全量 publisher 的强身份校验（HEAD==origin/main + 完全洁净 + 双子模块对齐）在生产主树（常年有并发 WIP）几乎不可能满足，且采集 5~14min 压不住 15min 窗口 —— **自动发布通道实际不存在**；
3. **部署层**：launchd 跑的 `~/.local/share/zhixing-dashboard/panorama-collect.py` 是 2026-09-22 旧版，根本没有 `publish_projection_revision` 函数 —— 生产从未运行过能发布 revision 的代码。

## 教训（固化）

1. **「协议上线」≠「通道存在」**。reader 侧 9-24 就启用了 revision 校验，但发布侧到 10-04 才有自动生产者 —— 中间的可用性全靠人工。**任何「读端收紧」的变更必须同步验收「写端持续生产能力」**，否则就是把定时炸弹埋进运维。
2. **人工应急会制造二次事故**。手动续期在 state root 顶层留的 lock 文件触发 CODE_DRIFT，把「数据过期」升级为「服务无法启动」。应急操作必须知晓读端的全部启动校验（指针哈希、manifest 哈希、**仓库洁净**、身份绑定）。
3. **无 GC 的不可变存储必然回涨**。631 个孤儿 revision / 9.9GB。不可变 revision + 定时生成 = 必须内置 GC。
4. **并发 agent 时代，BET 号也会撞车**。T10-222 被并发会话先行占用（#4617），避让重号为 T10-223 —— 与既往 T4-06 撞号事故同构。取号后应尽快落账或 claim。
5. **spec-init 的 YAML round-trip 会造成全文件重排**（本次 1833 行噪声 diff，已手工清理为 +64/-1）。对超大 SSOT 文件，round-trip 工具要用文本级插入替代。

## 遗留与后续

- **全量 publisher 生产通道仍不存在**（另立 BET）：数据内容刷新仍依赖 panorama-collect 全量跑通强身份校验；当前 dashboard 数据龄期会增长，租约续期只保证服务可用性。建议在 dashboard 增加「数据观测龄期」醒目告警（当前 UI 有 observed_at，但无超龄警告）。
- **stopgap cron 未能清除**：`crontab(1)` 写入持续 EINTR（系统级，12h 前尚可用），stopgap 行仍每 8min 从 worktree 路径执行（功能无害 —— 与 launchd 同锁同 skip 逻辑）。待系统恢复后执行：`crontab -l | grep -v STOPGAP-projection-republisher | crontab`，然后退役 worktree `ws-projection-autorepublish`。
- **看门狗盲区**：端口级看门狗对 `projection_stale`（服务活着、数据过期）与启动期 CODE_DRIFT 均无能为力（反复 kickstart 反而拖慢启动）。建议看门狗探测失败时先 kickstart republisher 再探，仍失败才重启服务（另立小 BET）。
