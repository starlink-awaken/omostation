## 4 lessons — 下次直接可用的判据

1. **"不进 git" ≠ "不跨检出"**。解释一个 gitignored 目录的行为时，先 `ls -l` + `stat -f %i`
   两侧路径，再决定它是不是共享面；用 ignore 规则反推物理布局是猜。
2. **契约里只写不会被时间冲掉的量**。条数、耗时、谁在跑这类读数要么绑定一次具体的 run 记录，
   要么换成语义量（阈值、状态字段）。写"实测 N 条"时必须同时写下 N 的取值时刻。
3. **台账条目定稿 → `start` → claim 完 → 才改非投影字段**。`verify`/`done_when`/`scope`/`goal`
   在 WorkPacket 投影里，改它们会挡住后续 claim；`status`/`done_at`/`completion_evidence` 不在，
   所以 `complete` 照常。首轮 BET 用不了 `refresh-packet`（要求源已合）。
   判据来源：`bet-ledger.py:2336` + 一次回退重放。
4. **文档类门禁要在 `git add` 之后跑**。`--scope tracked` 的"tracked"含索引项，不含 untracked；
   commit 前跑出的 PASS 不构成对新文档的证明（§2 第四条）。
5. **判据 1 的指针抽取要覆盖 `.gitignore` 这类点开头文件名**。正则写成 `[A-Za-z…]+\.(?:py|md|…)`
   会静默漏掉 `.gitignore:12` —— 漏检不报错，正是本轮把 verify 命令补上 `gitignore` 分支的原因。
6. **从别人报告里抄的数，必须连它的定义一起抄**。"六个检出侧读者"抄自一行讲"某笔 commit 暂存了
   哪些文件"的文字，语义完全不同。判据：写进契约的每个数都要能说出"用哪条命令、在哪个集合上数的"；
   说不清就删计数、留指针，而不是换一个自己也复现不了的数。
7. **gitlink 类红先做三条测量再决定处置**：① `git rev-parse HEAD:<sub>` vs `git rev-parse <base>:<sub>`
   （我到底碰没碰指针）② `main` 在那个 base 上的 CI 结论（`gh run list`）③ 该 job 的 `ref:`
   （head tree 还是 merge tree）。三条齐了就知道"分支内 bump"通常是错路（本例被
   `submodule-guard` 的非 fast-forward 拒绝 + `write_surfaces` 越界双重否掉），
   对的路是从已对齐的 base 重落同一批字节。
