## 1 intended（原本要什么）

`_is_merged_to_origin_main` 只做 merge-base 祖先判定。本仓 PR 统一 squash 合并，分支原
提交永远不是 origin/main 的祖先 → 已落地的 worktree 只能落在 active/stale_* 桶，
`--auto-clean` 形同虚设（2026-10-04 实证 PR #4627 的 w-simplify）。目标：补 squash
感知，同时死守 fail-safe（判不清一律未合并）。

## 2 happened（实际发生什么）

两级探测落地：
- (a) **累积 tree 等价**：分支触碰路径上 `merge-base..head` 与 `merge-base..origin/main`
  的 diff 逐字节相等 → 判 merged。对多 commit squash 成一个、以及 rebase 后合并都成立
  （比的是累积 diff，不比单 commit patch-id——后者在多 commit squash 场景必败，这是
  TASK 描述里 git cherry 路线的设计缺陷，spec 阶段弃用）。
- (b) **gh PR MERGED 兜底**：`gh pr view --head <branch>` state=MERGED 且本地无超出
  PR head 的提交。gh 缺席/未认证/网络失败 → 静默 False。
- DETACHED 分支不问 gh（无 PR 可查）。

真仓冒烟：rc=0，捞出 3 个 `merged_with_dirty`——此前被误判 active/stale 的 squash 落地
分支归位。fail-safe 面全部有测试钉住（main 后续改动破等价 → unmerged；超出 PR head →
unmerged；gh 缺席 → False 不抛错）。

## 3 learned（学到什么）

- **误判方向的代价不对称**：判 unmerged 只浪费一点磁盘；判 merged 是删除工作。所以
  (a) 用逐字节 diff 等价而不是"路径集合相等"这种宽松口径——squash 后 main 又改过
  同文件的分支必须继续留在场。
- **修判定 vs 修清理**：本 BET 只修判定，不引入批量清理历史遗留的迁移脚本。让
  `--auto-clean` 在日常 cron 里自己逐步收口，避免一次性大删。
- 台账 spec-init 会按字母序重排全文件（2731 行 diff）——语义级对比证伪内容丢失
  （added={251}, removed=∅, changed=0）后才放心提交。以后新建 BET 遇到大 diff 先跑
  这道对比。
