# BET-Y1Q3-T10-76 retrospective

## Q1. What was intended?

Restore `.omo/state/system.yaml` to the counts computed from the task source
tree, using the OMO state-sync broker rather than direct state writes.

## Q2. What happened?

The dry-run identified one stale counter pair on the planned/total axis. The
live `sync-tasks` broker rewrote the projection so `planned` rose from `6` to
`7` and `total` rose from `298` to `299`, while keeping completed (`290`),
active (`1`) and blocked (`1`) counts unchanged.

> The original spec said the broker would go the *opposite* direction
> ("planned 7→6, total 299→298"); that direction was an inversion of
> filesystem truth and was amended in this run to match what the broker
> actually does.

## Q3. What was discovered?

The full `omo state sync --dry-run` path can wait on unrelated runtime services;
the narrower `state sync-tasks` route is the correct owner for a task-counter
projection repair. The derived task index is regenerated as part of the broker
contract, while source task YAML files remain unchanged.

When the spec direction diverges from filesystem truth, fix the spec rather
than the broker — the broker is reading real `*.yaml` files; only the spec
got the delta direction wrong.

## Q4. Surface accounting

One generated `.omo/state/system.yaml` projection and one derived task index
changed; one BET ledger entry, one report, one Spec, and one retro were added.
No task source, Documents content, runtime payload, or new writer was added.

## Q5. What should the next agent know?

Use `omo state sync-tasks` for task-counter drift. Verify both the source-task
aggregate hash and `current-state-coherence.py`; do not hand-edit counters or
infer task completion from a stale `system.yaml` snapshot.
