# BET-Y1Q3-T10-108 retrospective

## Q1. What was intended?

Remove inactive CC Switch recovery databases, SQL workspaces, configuration
backups, and logs from Documents without touching active or iCloud CC Switch
state. Workspace owns the transaction capability; native App Support owns the
retained recovery payload.

## Q2. What happened in the planning phase?

Read-only inspection found 21 regular files and 417772968 bytes across
`.codex-optimize-log` and `.cc-switch-recovery2`, no source handles, an absent
target, and a green consumer audit. The design selected a separate App Support
recovery root and split implementation from host mutation so the live move will
use code already reachable from main.

The governance-profile clone omitted transitive projects needed by required
workflow health. Structured doctor output identified exact missing dependencies;
initializing the existing aetherforge, l4-kernel, bus-foundation, metaos, and
model-driven gitlinks restored health without changing any pointer.

## Q3. What changed in the design?

The original broad next wave was decomposed into three independent contracts:
CC Switch recovery relocation, L4 semantic classification, and retired runner
log quarantine. T10-108 owns only the first. Its implementation plan further
separates the capability PR from the host-closeout PR, preventing unmerged code
from becoming the sole operator for durable user recovery data.

## Q4. What is the surface accounting so far?

Planning added one specification, one implementation plan, one BET ledger
record, one bootstrap waiver, and this append-only retro. No production code,
script registry, CI workflow, migration-family source, active application data,
iCloud data, Documents payload, or Workspace runtime payload changed during the
planning phase.

## Q5. What remains?

All engineering and operational acceptance remains open: write RED tests,
implement the transaction and CLI, register and wire CI, merge the capability
PR, execute dry-run and host apply from main, replay verification, update the
migration family and completion matrix, merge closeout, and rerun the full-tree
Documents audit. Value remains `NOT_PROVEN`.

## Implementation phase update

Four RED-to-GREEN cycles now cover preflight, transaction behavior, existing
owner dispatch, and migration-family uniqueness. The initial new bin entry was
not accepted: `bin-quota-diff` exposed entry-point growth, so specification
1.0.1 moved command dispatch into the existing registered Documents owner.
The superseded CLI was deleted and final bin growth is zero.

The implementation currently has 21 focused tests green, the 25-test prior
Documents baseline green, Python 3.9 execution green, Ruff green, migration
coverage green, and local GaC green. These are branch-level engineering facts,
not mainline or operational proof. Remaining work is implementation PR merge,
mainline replay, the live 21-file move, durable manifest verification,
postflight consumer/L4 evidence, completion matrix, and closeout PR. Value is
still `NOT_PROVEN`.

The migration checker required one coverage sample per family while the legacy
regression fixed both sample count and family set. The packet was amended to
include that existing consumer; the final registry reuses one former
root-oneoff sample slot, preserving candidate count 17 while giving each family
exactly one or more samples.

The first mainline host plan then found a false assumption in 1.0.1: a recovery
corpus can intentionally contain a corrupt pre-repair database. The tool halted
before mutation, proving the circuit breaker. Six other SQLite recovery files
are healthy. Specification 1.0.2 preserves the known damaged `current.db` by
exact SHA and quick-check result digest while still requiring healthy recovery
and exact post-move replay. Host apply remains open until the amendment merges.

The amended dry-run now reproduces the original 21 files and 417772968 bytes,
with six healthy SQLite databases and exactly one digest-bound
`corrupt-preserved` database. This converts a false binary health assumption
into explicit recovery evidence without weakening hash, mode, path, rollback,
consumer, or active-data boundaries.

## Final host closeout

After 1.0.2 reached main, a fresh clone produced two identical plans and moved
all 21 files to durable App Support. Mainline verify proves equal source/target
fingerprints, six healthy SQLite checks, one byte-identical pre-corrupt check,
source absence, consumer 0/0, and executable rollback. The manifest is retained
at mode 0600 and permanent deletion is false.

The strongest lesson is that recovery health is not binary: a corrupt
pre-repair artifact can be valid recovery evidence if its corruption is
explicit, digest-bound, and replayed without byte drift. Gates caught two real
design errors before data loss: a new bin entry and a false all-SQLite-green
assumption.

Surface accounting: the final capability adds one focused library and one test
file, deepens one existing owner, adds five CI lines and one migration family,
and adds no net bin entry. Host state moved 21 files/417772968 bytes; no active
or iCloud CC Switch file was selected. Documents-wide runtime/archive debt
remains for later BETs. Value remains `NOT_PROVEN`.
