# BET-Y2Q4-T10-258 retro — 把一条只在装了机的机器上看得见的缺陷搬进 CI

## 1 intended — 原本要发生什么

B3 的门禁判据里 E2（已安装而未声明的 label）只剩 1 条：`com.omostation.omo-state-sync`。要做的是三件事，且严格限定在"登记现实"：

1. 把这 1 条按 observe-only（`generate: false`）回填进 `services.yaml`，使 `owned_declared == owned_installed == 47`、E2 归零；
2. 把 `.omo/cron/registry.yaml` 里同一条 job 的 `declared_only / proposed` 与正文那句「尚未安装」改成与现实一致（三面对齐）；
3. 不动本机 launchd / crontab，不宣布 B1/B3/B4/B5 或 plan 完成。

## 2 happened — 实际发生了什么

判据都按测量达成（明细在 receipt §3），但本轮真正的产出是计划外的第 4 件：**发现 E2 这条缺陷在 CI 上结构性失明**，并为此补了一条纯仓内守卫。

发现路径不是推理而是读文档：`tests/test_service_registry_reality.py` 的 docstring 逐字写着「门禁的现实侧输入是 `~/Library/LaunchAgents` —— 那既不是 CI 上存在的东西，也不该被单元测试读写」。 ⇒ 「往 `bin/ops/launchd/` commit 一份 plist 而不 commit 注册表声明」这种错，在 CI 上**永远不会红**，只有装过机的机器看得见。本轮补的守卫把判据换成仓内两棵集合（`bin/ops/launchd/*.plist` 的 label 集合 vs `services.yaml` 声明集合），与 host 无关，因此能进 `governance-check.yml` 的显式白名单（`:203`，理由注释 `:164`）。

过程中四处读数值得留下：

- **豁免面是 2 条而不是 0 条**，且都是"未装"：`arch-health-weekly`、`panorama-refresh-guard`。后者还带一个真实文件缺陷（XML 注释体内出现 `--` ⇒ `ExpatError: line 26, column 48`），本轮不修，只豁免并另铸 BET。守卫用**集合相等**钉它，不用子集，所以将来有人装机而不登记、或削减豁免而不补声明，都会当场红。
- **`services.yaml` 是双文档 YAML**，`load_services()` 取 `docs[-1]`；守卫若误取 `docs[0]` 会在"零 services"上绿。为此单独留了一条 `test_services_body_doc_carries_the_namespace_partition_too`。
- **交付后 09:27Z 该排程自己打响了**（`job state = running`、`runs` 2→3、日志 mtime `09:27:05Z`）：`reality=installed` 从"文件在场 + launchctl 读得到"升级成"确实在执行"。这条不在计划里，是撞上的。
- **`gac-worktree.sh release` 之后 claim 文件仍在**：清理调用是 `swarm-discipline-cli.py branch-release … >/dev/null 2>&1 || true`（`bin/gac/gac-worktree.sh:1158-1159`），失败被静默吞掉。手工同参数再跑一次即 `{"released": true}`。⇒ AGENTS.md 的"三查判据应全空"里，claim 那一项在 release 后**可能假绿失败**，判据要跑 verb 而不是只 `ls`。

## 3 changed — 哪些认知被改变

**「两次快照结果不同」的第一因是我自己的快照脚本，不是被测对象。** ISC-6 第一次比对报 `state_lines: A==B False`，而 host_sha / mtime / crontab 全等。真实原因是 A 用键名 `launchd_state_lines`、B 用 `state_lines`，我的比较式取 `a.get("state_lines")` 得 `None` —— 于是**装置内部不一致被读成现实变化**。T253 已在同一判据上栽过一次（那次是 float 秒 ×1e9 存 ns 造成 5 份 plist 全部 `mtime_same=False`），纪律写的是「取快照一律 `st_mtime_ns`」。本轮是**同一条纪律的另一种失效面**：T253 修的是刻度，本轮漏的是**键名与采样集合**，而"两次快照由两支不同的临时内联脚本产出"这个形状本身就足以造假不等。

⇒ 因此本轮把快照落成一支**可重复调用的脚本**（一次性装置，不入库），后续读数都由它产出，键集合固定。**判据**：凡"前后对比"类验收，两个读数必须由**同一支脚本、同一组键**产出；比较前先看两侧键集合是否相同，再看值。这比"用整数刻度"更一般，也更早能拦住。

顺带一条同族小坑：`change-lane-check.py` 的参数是 `--file`（append）而不是 `--files`，我第一次回放三个 commit 时全部 rc=2 —— 那是 argparse 用法错，差点被读成"三个 commit 都被拒"。改用 `--file` 后读数是**三个都 `ok=false`**，其中包括两个已经在 main 上的先例（T253 `a8f04bd05`、T257 `73c848b80`）。所以「混合 lane 的硬失败」不是本轮引入的形状，是既有形状；这条只能靠**回放先例**证明，不能靠回忆。

## 4 lessons — 固化的话

1. **登记面与运行面的分界要能自证**：本轮对 launchd 的"零改动"不是靠承诺，而是靠三个字节级读数（plist sha256、mtime、`crontab -l` sha256）+ `runs` 未归零（归零是 bootout/bootstrap 的特征）。写"不动运行面"的 BET，验收里就要有这一组，而不是"我没执行那条命令"。
2. **门禁的可见性也要当成判据审**：一条缺陷"修好了"和"这条缺陷下次能在 CI 上被看见"是两件事。E2 的根因不是那 1 条 label，而是现实侧输入落在 host；补集合守卫才是把缺陷类别关掉。**判据**：每做一次"现实回填"，顺手问"这类错下次会在哪儿红"。
3. **`generate: false` 的理由必须是实测的键面差**：本条 plist 有 `WorkingDirectory`，`gen_launchd_plist` 从不输出该键 ⇒ 翻成 `generate: true` 会立刻造 E1 漂移。这个理由可测、可复现，比"这轮先不接管"稳。
4. **同一条纪律要记它的失效面而不只记当时的机制**：T253 的「用 `st_mtime_ns`」没有防住本轮的「键名不一致」。凡是"上次因为 X 错了"这类教训，落成纪律时该往上问一层——真正的一般形式是"两个读数同源"，而不是"换成那个具体修法"。
5. **脚本里 `|| true` + `>/dev/null 2>&1` 的清理步，其"成功"不可信**：判据用 verb 的重跑结果，不用"脚本没报错"。
6. 本轮**不宣布** B1/B3/B4/B5 或 plan 完成：B3 的 `--reality-check ok` 仍为 `false`（E4 18 条未分区 + E5 2 条），已装集合==registry 集合这半条本轮才成立。
