# Retro — BET-Y2Q4-T10-248 双 profile verify 腿进 CI

## 1 intended

在各自 root 之下**。它要防的不是「写错根」这一次，而是「verify 自己变成假门禁」——

## 4 lessons（可迁移的判断）

1. **否定式验收会被自己的 receipt 否证**：「检出里没有 X」这种判据，只要 X 恰好从来没被写过就恒绿。
   改成正向落点断言（landing 必须是本腿实际写出文件的绝对路径、且在本腿 root 之下）之后，
   「一个 root 假装两个 profile」和「一个字节没写」都能当场红。**判据**：任何「移走某个写目标」的契约，
   先问「它的正向落点断言在哪」，没有就是假门禁。
2. **准入面先于代码面**：同一 BET 连开四个 Run、四个 blocked close，零个是代码缺陷——
   全是 scope/授权/锁窗口。**判据**：动手前把「这次要碰的路径」逐条对照 packet 的 `write_surfaces`，
   需要新增就**如实追加再交付**（本轮 governance-checks.yaml 那一条即此），
   而不是「先接了线再说」；范围外的接线会被按非必需撤回。
3. **blocked close 是一种如实收口，不是失败**：源已冻结 + 真实 push + CI pending 时，
   `close --status blocked --evidence` 把 root-gate/project/path 锁还给并发会话，
   而 PR/CI 的只读跟进不需要持代码锁。本轮实测：释放锁之后，T10-250 才得以用 merge
   解台账插入点冲突（并发会话在同一位置追加）。**纪律**：不持锁等远端 CI，不翻 done、不伪造 ok。
4. **CI 的两棵树在这条腿上第二次咬人**：`governance-verify` 用 `pull_request.head.sha`（评分支自己的
   head tree），`meta-doctor`/`interface-check`/`doc-freshness` 用合成 merge commit——
   所以**接线必须与代码同一个 PR 落**，拆成两个 PR 会让「CI 绿」对新用例不成立。
5. **探针语义要区分 warn / deferred / pass**：`install_root()` 在本机 `warn`、在 CI 干净检出 `deferred`，
   两者都不是通过。把「探不到」记成 pass 是这个 BET 的 ISC-5 明确禁止的形状，
   也是本仓最常见的假绿来源之一。
