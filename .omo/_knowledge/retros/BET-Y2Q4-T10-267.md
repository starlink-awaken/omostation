## 1 intended — 原本要发生什么

ADR-0456 决策 5 把一件事写成承诺：`~/.local/share/zhixing-dashboard` 是外部依赖，所以它要有

## 2 happened — 实际发生了什么

一参定位器；`ops/cli.py check-signals` 的 observe-only `/health` 轴；`tests/unit/test_zhixing_external_root_contract.py`

计划里没写的三件事，都发生在**判据层**而不是代码层：

1. **我把契约名单写成了代码里的第二份来源。** 第一版 `external_root()` 读一个手抄的
   `EXTERNAL_ROOT_ENVS = {"zhixing-dashboard": "ZHIXING_DASHBOARD_ROOT", …}`。它当场能跑、28 例能绿 ——
   而它正是 T10-239 那条「契约名单不得手抄第二份」的形状：登记表改 env 名，代码静默指错。
   改成登记表 `root_env:` 字段后，env 名只有一份。**这次是自伤，不是被 review 抓住的。**
2. **我自己写下的两条验收装置按实测不可达。** ① done_when-5 写「`git grep -w pinned_sha -- bin/` 零判定
   读取点」—— 实测 `bin/` 有 13 处 / 4 个文件读这个词，读的是**无关的**子模块 gitlink 概念；
   ② verify-1 假设 `ZHIXING_OBSERVATORY_PORT` 已被导出 —— 全机没有任何 rc 文件、hook 或 cron 导出它，
   裸跑只会得 `undetermined`。两条都在 spec §5 与台账同步改写，并写成**不共享失效模式的两台装置**
   （消费者 AST 零命中 + 全 `bin/` 文件集合 == 被评审名单），**没有**摘掉判据。
3. **解释器是装置的一部分。** verify-1 在 `bash -lc` 下第一次跑出 `ImportError: cannot import name 'UTC'`
   —— 那条 shell 里裸 `python3` 是 `/usr/bin/python3` 3.9.6，而 zsh 交互下是 homebrew 3.15。
   命令改成 `uv run --no-project --python 3.12` 后三条 verify 在最坏 shell 里全部 rc=0。

一处**我的直觉错了**：我以为 `require_health: yes` 会被校验拒掉。实际 PyYAML 1.1 先把 `yes/on/True`
折成布尔 `True`，所以它是**合法声明**。改成「非布尔字面量一律拒 + 按 required 处理」，并补一条
专门钉折叠行为的用例 `test_yaml_truthy_words_fold_to_required_before_validation`
（`tests/unit/test_zhixing_external_root_contract.py:361`）。

## 3 changed — 之后做法不一样

- **顺序纪律补一半**：台账里「定稿 → `start` → claim 完 → 才改非投影字段」这条之外，本轮实测到
  `start` 之后改 **spec 正文**（哪怕只是订正措辞）会让 `refresh-packet` 直接拒 ——
  `WORK_PACKET_REFRESH_SPEC_DRIFT: accepted Spec binding changed`（`bin/agent-workflow.py:846`）。
  这不是一句 projection 刷新，而是 binding 变更，工具按设计不许它自动过。后果写清楚：**一旦 spec
  动过，后续 claim 新路径这条路就没了**；本轮靠「retro / receipt 无需 claim 即可提交」交付收口腿，
  这是既有事实（packet 校验的调用点只有 `claim` 与子 run 继承），不是绕行。
- **变异的记账单位是「每例改法 → 点名用例」，不是红条数。** 6 组变异读数分别 2/2/3/3/1/3；把它们
  压成「摘掉守卫就红」会丢掉承重信息（M-d 只红 1 例，说明那条校验只有 1 个用例承重 —— 这是**下一步该
  补什么**的线索，不是一个成绩）。
- **凡「目录读不到」与「内容为空」都可能同形的地方，读数前先确认扫描面非空**。本轮 28 例里有三条
  自证：`test_indent_parser_is_not_a_no_op`、`test_pinned_sha_detector_is_not_a_no_op`、以及消费者用例
  里那句「先断言集合确实含 `repo_root.py` + `ops/cli.py`」。

## 4 lessons — 可复用的判据

1. **定位器不得复述它所读的登记表。** 新符号若读某个 registry，它的输入（env 名、键名、字段集合）
   必须来自 registry 本身；在代码里出现第二份同名映射 = T10-239 那个缺陷的镜像面。
   **判据**：`grep -n "EXTERNAL_ROOT_ENVS\|= *{.*: *\"[A-Z_]*_ROOT\"" <被检文件>` 为空，且登记表里
   `root_env` 的读者只有一处。
2. **验收装置不可达时，换成等价或更强的装置并写明原因；不许删。** 三处证据要同时留在文档里：
   原措辞、实测读数（13 处 / 4 个文件、无 env 导出）、新装置的失效模式为什么与原装置不同。
3. **判据要指名解释器**（AGENTS.md §7「换装置读数不同」）：verify 命令里出现裸 `python3` 且被测代码用了
   3.11+ 语法/标准库（`datetime.UTC`），则它在 `bash -lc` 与 zsh 下会是两个答案。要么指名
   `uv run --python <ver>`，要么把语法下限降到目标解释器。
4. **`pinned_sha` 类「溯源字段」的守门方式只能是消费面扫描，不能是词频为零**。同一个词在仓里可能属于
   另一个概念；判据是「出现该词的**文件集合** == 已评审名单」，且名单成员**不引用**本 registry。
5. **观测器把自己的失败折成另一种状态，是让「坏了」与「正常」分不开的那类设计**（本轮实证：
   `north_star_meter_v2` 在依赖面缺 `pydantic` 时报 `status=unprovable reason=observer_unavailable`，
   与「账本不可用」的 `not_ready` 两种原因共用一个状态位）。读到这类状态时先换依赖面复跑一次再定性。
