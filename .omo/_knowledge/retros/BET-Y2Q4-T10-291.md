# BET-Y2Q4-T10-291 · A4 Scheduler 判据按整行比对

## 1. 本意（intended）

`bin/scheduler-compile.py::check_drift()` 是 A4 Scheduler 门禁的判定核。它在登记侧
（`:235`）与安装侧（`:248`）都把比对键截到 120 字符，本轮要把键宽改成**归一化整行**，
使「声明与实装只在 120 字符之后不同」不再等于「一致」。四条 done_when：

1. 反例用例成立（前提由用例自证，旧实现读 `ok=True`、新实现读 `ok=False`，
   `drift_count>=1` 且 `orphan_count>=1`）＋同对整行相同时 `ok=True` 计数 0；
2. 欠计反例成立（5 条差异全在 120 之后 ⇒ `known_orphan_count == 5`，而不是 1）；
3. 本机读数迁移可解释（`drift_count`/`orphan_count` 前后同为 0，`known_orphan_count` 4 → 10，
   新增 6 条逐条命中既有 `known_orphans`）；
4. `test_shadow_segment_never_blocks_the_gate` 仍绿且 hermetic。

非目标写死在 spec 里：不改任何 crontab / launchd 实装，不新增 `known_orphans` 条目，
不动归一化三段逻辑，不加严格度开关或 observe-only 中间态。

## 3. 改变了什么（changed）

- A4 门禁的判定宽度：crontab 平面从此按整行比对，`*_count` 是真实条数。
  本仓最后一处判据截断位消除（launchd 平面早就是 label 全串比对）。
- 债账读数：`known_orphan_count` 4 → 10。**数字变大不是新增债务**，
  而是原先被折叠的 6 条一直在机器上、只是没被数到。后续 shrink_only 判断要用新基线 10。
- 观测面（未在本轮动手，只登记事实）：新计到的这些行是 legacy cron 常驻控制面，与已注册的
  launchd 常驻任务**同时在跑**。实测两侧集合：cron 侧 9 条 resident 行
  （`--role` decision/execute/heartbeat/monitor/sediment + `resident` inbox/ingest/promote/signals），
  launchd 侧 6 个 label（`com.l4.resident.{decision,execute,signals,inbox,promote,event-ingest}`），
  `launchctl print gui/<uid>/…` 读数 `runs=846 / 846 / 339`、`last exit code=0` ——
  即两边都是活的，不是「launchd 已接管、cron 只是残渣」。
  其中 `heartbeat / monitor / sediment` 三个角色只存在于 cron，`event-ingest` 只存在于 launchd。
  撤任何一侧都属于机器实装变更，principal 决定。

## 4. 教训（lessons）

- **判据的键宽度小于被检对象的实际宽度时，「相等」是截断的产物。** 这与 AGENTS.md §7
  「六类静默失效形状」⑥/⑧ 同族，但方向不同：⑥ 是匹配词命中不了实际文本，⑧ 是分类规则
  漏认形状，这里是**比较键被物理截短**。三种形状的共同失败形态都是「读数正常」，
  所以反例必须让**前提自己说话**（用例内断言 `a[:120]==b[:120] and a!=b`），
  否则用例绿可能只是因为构造没成立。
- **反基线读数要在复刻树上量，且复刻树要按被测文件的实际读取面补齐。** 本轮第一次复刻少
  两个文件就多出一条假「预存红」。判据：对照实验里每个 red 都要能指到「它读了什么」，
  指不到就先怀疑装置缺件，而不是把它写进「预存」名单。
- **死锁的正确出口是问「谁占着、它交付了吗」，不是删锁。** 取证链（锁的 `expires_at`
  + run 的 `objective` 里的 BET id + 该 BET 在 `origin/main` 的 `status`）三样都是只读测量，
  10 分钟内可判定；判定成死锁之后仍然不该由我拆别人的锁 —— 缺一条认领只是 warning，
  代价远小于误拆一条活锁。
- **测试里的 host 字面量会被一把专门的尺点名，而它的正解方向只有一个：派生。**
  `test_tests_unit_host_anchors.py` 把 `tests/unit/**/*.py` 里 `<用户目录>` 的命中
  收成一个冻结集合，且断言**双向相等**（`_hits(...) == LEGITIMATE_HITS`）。本轮为了
  构造「差异落在 120 之后」的注入行顺手写了绝对路径，CI 当场点名 —— 这条红不是
  门禁太严，是它按设计工作。两种可走的路上：**给集合加一项**＝把那把尺收窄到
  恰好容纳自己的笔误（AGENTS.md §7「不许靠改窄断言过关」）；**从 registry 派生**＝
  字面量本来就不需要 —— 覆盖注入行的是 `known_orphans` 里的模式，模式本身来自 registry，
  所以 stem 只需要含那个模式。附带收获：派生之后 filler 宽度必须按
  `_normalize_interpreter(stem)` 的**归一化后**长度算，而不是原始字符串长度，
  否则归一化改写会让前 120 字符不再相等，前提悄悄失效（用例里那条
  `len({norm(l)[:120] for l in injected}) == 1` 正是拦这个的）。
- **`claim_policy` 的 tier 名单要按 mode 读，不能按「是不是治理文件」读。** 台账看起来
  很「治理」，但它不在 required tier 里，这一点决定了死锁是可绕行的（降级）而不是硬阻断。
  下一次遇到同类阻塞先读 `.omo/_truth/registry/agent-workflows/_root.yaml` 的
  `claim_policy.tiers[].mode`，并要求 `claim_coverage_report()` 的 `missing_required` 为空即可。
- **台账 `verify[].cmd` 是一种尺，落笔前要在本机真跑一次；而且 cmd 与 expect 必须同一装置。**
  本条开台时把 hermetic 命令写成
  `uv run --no-project --with pytest --with pyyaml …`，实测当场 `unrecognized arguments:
  --timeout=300` —— 根目录 `pyproject.toml` 的 `addopts` 带 `--timeout`，缺 `pytest-timeout`
  包时 pytest 直接拒收参数，而 `_work_packet_from_bet()`（`bin/plan/bet-ledger.py:2173`）
  把这些 cmd 原样投影进 WorkPacket，于是「验收怎么做」交给下一位执行者时是一条跑不动的命令。
  第二处更隐蔽：同一条 cmd 声明了 `HOME=$(mktemp -d)`，`expect` 却写「全部通过」——
  两个面在同一份文本里互相否证。实测（base `ed737e423`）本机原样环境 `9 passed`，
  按 cmd 自己声明的装置跑 `2 failed, 7 passed`，而基线复刻树（`a59a966e7`）逐名同为
  `2 failed, 4 passed`：红的是 `test_every_active_launchd_entry_resolves_to_an_installed_label`
  与 `test_launchd_bidirectional_drift_structure`（前者直读 `~/Library/LaunchAgents`，
  后者调 `check_drift()` 不注入 ⇒ 读真实 crontab/launchd）。
  **判据**：写 expect 时把「用哪把装置跑」写进 expect 本体，并在**该装置下**量一次；
  本机绿不等于 hermetic 绿，反过来也一样。
  本轮实测用的是补上 `--with pytest-timeout` 的同一条命令；cmd 与 expect 的修正在收口腿做，
  不在 claim 之后动投影字段（`verify`/`done_when`/`scope` 都在 packet 投影里，改了会让后续
  claim 报 `WORK_PACKET_SOURCE_DRIFT`，AGENTS.md「顺序纪律」）。
- **收口腿的产物路径本来就在 WorkPacket scope 之外** —— `write_surfaces` 只列了代码/spec/台账/测试，
  于是 claim `.omo/_knowledge/retros/<BET>.md` 与 `docs/reports/<…>.md` 当场
  `WORK_PACKET_SCOPE_MISMATCH`。这不是拦截：`claim_policy.mode: advisory`，且这两类路径不在任何
  `mode: required` tier 里，`claim_coverage_report()` 只把 `missing_required` 计入 `ok`。
  正解是**如实报告未认领**而不是为了过 scope 去改台账的 `write_surfaces`（那同样是投影字段）。
- **`--check` 这类生产门禁命令天然是 host 读数，不要拿它当 hermetic 证据。** 本条
  `verify[1]` 读真实 `crontab -l`，所以它的 `known_orphan_count` 会随机器漂移；
  可复现的判据是注入缝用例，机器读数只是「本轮这台机器此刻的迁移证据」，收据里必须写明
  取读数的时间与对照脚本的 base。
- 遗留判据缺陷（本轮未纳入范围，证据在案）：`lifecycle.py:1422` 的 A2A 冲突谓词不看锁 TTL，
  而 `_root.yaml` 的 `compliance_slo.stale_locks: 0` 说明本仓**期望**零陈旧锁 ——
  两者矛盾，值得单独开条 BET（谓词改成「run active **且** 锁未过期」）。
