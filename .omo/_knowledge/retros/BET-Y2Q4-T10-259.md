## 1 intended — 原本要发生什么

T10-258 的 circuit_breaker 明写「改用评审清单而不是替它们决定『该不该活』」。本轮的意图是：
把 `--reality-check` 仅剩的 20 条 finding（基线读数：E4 未分区 18 + E5 双向不一致 2；
   合并前复测为 21 条 / E4 19）逐条取证，
陈述**三条**可用准入机制及各自的代价，让署名裁定从「20 次开放式问答」变成

不把任何 label 塞进 `services.yaml`。

## 3 changed — 哪些认知被改变

1. **判据文本里的每条命令，落笔前必须真跑一次**（AGENTS.md §7⑥「匹配词要能命中」的下一层：
   不只是匹配词，**整条命令行**要与被检对象同源）。写错的 verify 不会当场红，
   它会在**下一轮执行者**手里变成"判据失效→改窄判据"的诱因。
2. **陈旧检出让「回归」与「落后」同形**：一份落后的治理态检出会精确地报出
   "上一轮刚归零的那几条又回来了"。判别量不是读数大小，而是
   `git rev-parse HEAD` 是否等于 `origin/main`，以及缺项集合是否等于
   「已知由最近几轮回填的那几条」。
3. **取证文档有一条隐私边界要显式写进 spec**：`EnvironmentVariables` 只记条数、
   值一律不抄。不写这条，下一轮的清单就会顺手把 12 个键名和值贴进公开 PR。
4. `ledger-safe-insert.py` 顺带把 `total_bets` 552→553，`git diff --stat` 因此显示
   `1 deletion`。**看到 deletion 先看那一行的内容再定性**（本轮实测唯一删除行是
   `  total_bets: 552`），不能据 stat 判"插入器动了别人的条目"。

## 4 lessons — 固化的话

- 清单类交付的价值判据是「**它能不能被一次答完**」：每行一个 finding + 一个拟用
  classification + 代价说明，而不是"列了 21 条待办"。
- 「不改判据本体」必须有可测量后果才能被相信 —— 交付前后 `--reality-check`
  的 **逐字段相同**就是那个测量 —— 本轮证明这句话本身是错的：基线读数
  `installed_total=76 / E4 18 条`，合并前复测 `77 / 19 条`，多出的
  `com.local.magpie-refresh` mtime 落在两次测量之间（2026-10-19T19:26:33Z），
  我什么都没做判据就自己变红。**对活平面写「逐字段相同」的验收，会在交付者无过错时
  自红，并把真回归埋进「机器自己动了」的噪声里。** 正确分档：回归敏感字段
  （E1/E2/E3、unclassified、owned 等式、registry 总数、E5）逐字段相同；
  运行面自变量（installed_total 与 E4 集合）只允许因**可指认的外部落盘**变动且须记名放行。
  台账 `done_when` / `verify` 与 spec §7 已按此改写。
- 观察与处置分离：`com.localbrain.preseed-http` 的 `--bind 0.0.0.0` + `KeepAlive`
  只陈述事实，改绑与撤 job 都属运行面、需单独授权。清单不夹带处置。
- **清单是快照，命令才是判据**：条目数随本机落盘变动，交付物必须写明「作答前先按
  `--reality-check` 当次 findings 与表双向对拍」，否则第 19 条这种东西会安静地漏答。
- packet 哈希由 ledger+spec **共同**重导（`bin/plan/bet-ledger.py:2202` 的 acceptance
  取 done_when/verify，spec_binding 取 content_digest），所以 `start` 之后任何一次
  修 spec 或改 verify 都造 `WORK_PACKET_SOURCE_DRIFT`（`:2336`，只在 **claim** 与子 run
  继承两处调用，函数名就叫 `_validate_work_packet_claim`）。本轮因修一条指向不存在脚本的
  verify 命令而已漂移。
  **订正（本轮实测，推翻我自己先前写下的补救方案）**：本仓**没有** `refresh-packet`
  这条命令 —— `agent-workflow.py --help` 的 26 个子命令里没有它，`bin/` 与
  `projects/omo/src/omo/workflow/` 全文搜不到这个名字。真实可行的补救是两步：
  ① 对已漂移的旧 run 跑 `close <run-id> --status ok --evidence "…合并与实测读数…"`，
  它同时 `release_locks()`（只 unlink run_id 等于自己的锁）；② 用**合并后**的
  ledger+spec `start` 一个新 run 承接收口腿 —— 新 packet 由已定稿的源重导，天然不漂移。
  不这么做的话，旧 run 的 `docs/plans/3y-bet-ledger.yaml` 路径锁会一直挂着，
  新 run 的 claim 先撞 `A2A Path Lock Collision`，改旧 run 又撞 `WORK_PACKET_SOURCE_DRIFT`，
  两面都是死路。判据：**凡在 `start` 之后还要修 spec/verify 的轮次，收口腿按设计就该是新 run**。
