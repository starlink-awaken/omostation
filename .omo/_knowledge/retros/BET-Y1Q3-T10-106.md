# BET-Y1Q3-T10-106 retrospective

## Q1. What was intended?

Deploy omlxc.dma_daemon as a persistent macOS launchd agent and execute Thunderbolt 5
chaos drills (cable unplug, memory spillover) to verify sub-50ms fallback and sub-1.5s recovery.

## Q2. What happened?

The chaos drill suite (4 drills) all PASS at the simulation level:
- launchd_persistence: generate_launchd_plist produces valid plist with KeepAlive + ThrottleInterval=5
- probe_cycle: 1.063ms probe time, mesh-telemetry.json written with TB5 DMA 120Gbps
- vram_spillover: 0.119ms spillover trigger, no OOM, telemetry reflects active state
- disconnect_recovery: reconnect attempts increment, exponential backoff works

The 24-hour real launchd heartbeat test was NOT executed because it exceeds the session
time budget. The plist emission + persistence path is verified; the actual launchd bootstrap
and 24h freshness requires human operator execution on the physical MBP M5 Max host.

## Q3. What went well?

- The dma_daemon controller already had a clean public API (`_probe_cycle`,
  `_trigger_kv_spillover`, `generate_launchd_plist`) — no source code modifications needed.
- The chaos_drill.py harness exercises 4 distinct state-machine paths via the existing
  controller methods, validating the architecture without writing new daemon code.
- All 4 drills complete in <30 seconds total, making them suitable for CI integration.

## Q4. Surface accounting

- projects/omlxc/packaging/launchd/com.omostation.omlxc-dma-daemon.plist (canonical plist)
