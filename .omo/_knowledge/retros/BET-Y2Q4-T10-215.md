## Q1 意图 vs 实际发生了什么

意图：B1 把根侧 `repo_root` 做成 code/state 双根之后，omo 内核还剩一条由入参根派生的写面
（四件投影 + `runtime/omo/**` 镜像根）。把它改挂 `state_root` 是"半天到一天"的活，
appetite 1 day、risk L2、`human_gate: true`。

实际分布：**改代码的部分很小**（`omo_ingress_state.py` +82/−53 含测试），时间花在
两处"契约写窄了/写宽了"的返工，和一次自己给自己造的 CI 红。

| 我原本以为 | 实测 | 花在哪 |
|---|---|---|
| 翻完投影写侧，"dev 跑一次就脏检出"就关掉了 | 只翻写侧时 `git status` 仍出 `M .omo/state/system.yaml`，作者是 `compass_radar.py:482` subprocess 起来的 `evidence-smoke.py` | 根侧配套改 `_system_yaml()`，并把 C6 从"一条改动"升成"调用图闭包" |
| 真实 sync 也该零 diff | 真实 sync 脏两枚 **tasks 面**时间戳（`omo_state.py:449 → :218/:232/:283`），计数逐字未变 | 判定为契约边界而不是隐藏写者，改写 spec 判据 7 + 台账 breaker 例外，而不是顺手搬 `.omo/tasks/`（709 个跟踪文件，non_goals 明写不搬） |
| "跑完没 diff"就是证据 | 否定式证据不成立：无 diff 无法区分"写到了 state 根"与"根本没写" | 先补正向落点判据，措辞写成"检出副本**不含**这三行 evidence"—— 这句**又被我自己的 receipt 否证**（`git show HEAD:.omo/state/system.yaml` 第 3–5 行就有它们，是上一次生产运行的读数）。终版判据换成更强的判别量"同一字段的值只在 state 根滚动"：检出三行逐字未变、新时刻只落 `<tmp>`（报告 §3.2） |
| 分支 CI 会替我验 `tests/unit` | `tests/unit/**` 未接 CI（只 `integration.yml` / `worktree-hygiene.yml` 引用），那条预存红是静默的 | 读数靠本地跑 + 在 closeout 里显式披露 |

## Q2 一次自己造的红灯

`gac-gate` 第一次跑就 FAIL，报错不是我碰的逻辑：

```
docs/superpowers/specs/…bet-215-omo-write-side-single-root.md: missing_frontmatter [warning]
  missing required frontmatter fields: owner
.omo/_truth/registry/document-governance.yaml: unbaselined_warning [error]
  warning bucket is not covered by an exception budget (missing_frontmatter:accepted-specifications count=1)
```

机制：**doc-governance 的 warning 桶是"未基线即阻断"**。全库 145 条 warning 都在基线里，
我新写的一份 accepted spec 多出一条不在基线里的 → 该 surface 计数 1 → 直接 error。
也就是说**新增文件只要 frontmatter 少一个字段，就会把整条 gate 拉红**，
跟它是不是"警告级别"无关。

根因是 skill 清单漏项：`bet-closeout-chain` 步 1 写的 frontmatter 七件套没有 `owner`。
修法是抄同批已绿的邻居（`2026-09-29-bet-214-closeout-evidence-integrity.md` 的
`owner: governance-team`），而不是猜一个值 —— 猜出来的 owner 会再造一条未基线告警。

代价：一个 commit（`13e3ab5e26`）+ 一轮 CI（约 6 分钟）+ 台账绑定 digest 重算
（`238c5acd…` → `f1fac56c…`）。spec 正文一字未动，所以重算是安全的。

## Q3 中途改变做法的地方

1. **C6 从"复述判据 6"变成独立判据。** 起初台账里 C6 与判据 6 是同一句话的两种写法；
   实测之后两者分化：判据 6 只看 dry-run 报告里 `writes[].path` 指向哪，
   判据 7 看检出 `git status` 是否逐行相同，判据 8/9 看 `evidence-smoke` 的正反用例。
   分化之后才发现"三条都成立"才是"关掉 dev 跑一次就脏检出"的充分条件。
2. **台账 `circuit_breaker` 与 `non_goals` 对齐。** breaker 原文"禁止任何落检出的写"
   与 non_goals 1"不搬 tasks 面"矛盾 —— 真实 sync 必然触发自己的 breaker。
   加例外而不是删 non_goals：例外写清作者行号，读者能核。
3. **不做"看起来更彻底"的方案。** 把 `.omo/tasks/` 一起翻根能让判据 7 在真实运行下也零 diff，
   但那等于把 709 个跟踪文件从 git 历史里摘走，属 B5 残留（#98）的判据范围。
   选择登记边界、留正向/反向两条读数，而不是偷做邻 BET 的改动来让自己的判据好看。
4. **PR-2 不另起 run。** 三条目标路径已被本 BET 的 code-change run 活动 claim 占有，
   新 run 起手就撞 `A2A Path Lock Collision`。改为在原 run 下落 evidence/retro，
   新 run 以 `blocked` 关闭并在 closeout 里说明（没落任何改动）。

## Q4 固化下来的教训（可复用判据）

1. **写侧改动要用"写到了哪"验收，不是"哪里没变"。** 否定式（无 diff、无新增文件）
   只能当辅助；每条"移走某个写目标"的契约都要配一条正向落点断言。
   **但正向断言也必须先跑一次再写进契约** —— 我第一版正向判据（"检出副本不含这三行"）
   就是没核对跟踪态现状写出来的，被自己的 receipt 否证；改成"同一字段的值只在 state 根
   滚动"后判据反而更强。
2. **调用图闭包的前提常常是"没传的参数"。** `compass_radar.py:482` 不传 `env=`
   才让 `OMOSTATION_STATE_ROOT` 靠继承进入子进程。这类"沉默契约"必须在 spec 里点名，
   否则未来任何人加一个 env 白名单就会静默断开写面收敛。
3. **新增被治理目录下的文件时，frontmatter 抄同批已绿的邻居，不抄 checklist。**
   `accepted-specifications` 桶未基线告警 = error；`owner` 是必填但清单没写。
4. **测量类判据不能与并发写者同跑。** 并行 pytest 让 `git status` 多出一行 ` m projects/omo`，
   第一次 verify 因此作废重跑（串行）。判据本身依赖工作树状态时，"谁能写工作树"要先进清单。
5. **治理 CLI 的三个入口形状**（本轮各撞一次）：`start` 需要 `--actor` 与
   `claim-bet` 的身份一致；`claim --path` 需要 `--affected-hash <receipt 路径>`
   （flag 名是 legacy，值必须是 `affected-graph.py --output` 产出的文件）；
   source drift 只在 **claim 时**强制，已 claim 的路径不会因 `origin/main` 前进而失效。
