# BET-Y2Q4-T10-253 retro — 把「已装 == 已登记」变成一条能被两棵树证明的判据

台账：`docs/plans/3y-bet-ledger.yaml` `BET-Y2Q4-T10-253`
规格：`docs/superpowers/specs/2026-10-19-services-e2-observe-only-backfill-4.md`（spec_version 1.0.0，digest `sha256:b19b1fec…`）

## 1 intended — 本来打算做什么

plan 里 B3 那一行的完成判据是「`--check` exit 0，且『已装 label 集合 == registry 集合』」，
而 B4b 每批的止损条件是「切完 `--reality-check` E2 仍为 0」。T10-246 把 E2 从 3 降到 1 之后，
剩下的 4 条全是 B4b 期间**新装而未登记**的 Workspace 命名空间服务 —— 判据没被满足，只是没再恶化。

理想态三条同时成立：① 4 条从 E2 消失且 `owned_declared == owned_installed == 46`；
② 登记对 E1/E3/E4/E5 与 `--validate`/`--check` 零扰动；③ 本机 launchd 逐字节不动。
外加一条范围边界：署名裁定面（`com.cockpit.dashboard` 的 `enabled`、缺装的 `com.l4.omo.sync`、
14→16 条 E4 未分区）不进本轮，否则「让判据变绿」会变成「让判据迁就现实的最新一份」。

## 2 happened — 实际发生了什么

**第一个拦我的不是判据，是锁面。** `start` 成功、run yaml 落盘、5 条锁都建了，紧接着 5 次
`claim` 全部报 `missing lock file: …bet_BET-Y2Q4-T10-253.lock.yaml`。没有重试，去查文件本身：
两条锁躺在 `locks/.archive/`，`ctime == mtime == 09:46:31` —— 和 `start` 建它们的是同一秒。
全机唯一的搬运者是 `bin/gac/fix-orphan-locks.py --apply`（orphan 判据是「锁的 `run_id` 不在 runs 目录」，
而 `start` 恰好是**先写锁、后让 run 可见**；`.omo/_delivery/` 又是全机共享的 symlink 桥，
所以它扫的不是我这个检出）。它的驱动方是 `tests/test_fix_orphan_locks.py`，即并发会话的一次测试/门禁跑。
`claim` 的前置 `heartbeat_run` 会逐个预校验声明过的锁（`lifecycle.py:1078` 缺一个就整条拒），
所以锁被带外归档 = claim 结构性不可能。
处置：`close --status failed` 把那条 run 如实收掉（不 `prune-locks`、不 `--force-lock`、不改锁面判据），
然后在**同一条命令里** `start` + 立刻 `claim`，让归档器没有插入窗口。第二次 5/5 成功。

**基线在交付窗口里被机器自己动了。** 预交付快照记 `installed_total 71 / E4 未分区 14`，
交付实测 `73 / 16`。第一反应不能是「我的登记把现实改多了 2 条」。装置是**同一台机器跑两棵树**：
把 `origin/main` 的 `services.yaml` 抽到临时路径再跑一次 `--reality-check` —— 读数是
`installed_total 73 / e2 4 / owned_declared 42`。于是 `71 → 73` 明确归因到机器侧
（两条 `com.localbrain.*`，mtime 本地 09:39 / 09:52，基线拍下 13 分钟内装上），
而我的改动只动了 4 个声明面字段。`workspace_scoped` 37 与 `owned_installed` 46 逐字未变，
说明这两条新装 label 不在本仓命名空间，对「owned 集合相等」零影响。

**「plist mtime 变了」是我的快照自己造的假红。** ISC-4 比对里 5 份 plist 全部 `mtime_same=False`，
而 sha256 和 size 全对。逐 ns 打出差额是 `+12 / +116 / +212 / −3 / +133` ns，再用
`int(st.st_mtime * 1e9)` 重算 —— 与基线值**逐位相同**。根因是快照当时用 float 秒 × 1e9 存 ns，
float64 在 1.79e15 这个量级的 ULP 约 0.4 ns，末几位被舍掉了。文件系统没动，是我的尺子刻度不够。

**`generate: true` 这条路对 resident-agent 不是「会漂移」而是「跑不起来」。**
把 4 条按 generate: true 在内存里喂给 `gen_launchd_plist()`（不落盘、不 load）实测：
resident-agent 当场 `ValueError: interpreter 含 uv 临时路径`（`resolve_interpreter` 见到 `/.venv/bin` 就拒），
另外三条能生成但输出缺 `WorkingDirectory` —— 这个键生成器从不发射。这坐实了 observe-only 是唯一
不造 E1 漂移的选择，也给了 `notes` 里可复核的理由，而不是「写着玩」。

## 3 changed — 改变了什么

- 取快照一律 `st_mtime_ns` 整数，不用 `st_mtime * 1e9`；比对留容差不如留正确刻度。
- 共享 delivery 面上的 `start` 与 `claim` 合成一次调用；`missing lock file` 的第一诊断动作是
  查 `locks/.archive/` 的 ctime，不是重试。
- 凡判据里出现「机器读数」（装了几个、哪些 label 在跑），验收必须并测**改动前那棵树**，
  否则无法区分「我改的」与「现实变的」。本轮把它固化成 receipt §2 的两列对照表。
- `installed_total` 从「ISC-2 的等值判据」降级为「归因证据」：owned_* 那一对才是本轮能动的量。

## 4 lessons — 固化什么

1. **登记面要能指出「不登记」的代价**：`notes` 里写清生成器不发射哪个键、`resolve_interpreter`
   会不会直接拒，下一轮想改 `generate: true` 的人不用重新做一遍实验。
2. **归属只写 grep 得到的**：4 条里只有 1 条有仓内写者；其余 3 条如实记「未归属」，
   比编一个可信来源便宜，也比留空更容易被后来人补上。
3. **判据失效的常见形状是尺子，不是被量对象**：本轮三个假信号（claim 不可能、installed_total 漂移、
   mtime 不一致）全部由「测量装置与被测对象不同源」造成。
4. **集合相等是会被构造重新打破的**：4 个 installer 往 `~/Library/LaunchAgents` 写而不登记，
   所以这轮收口之后，任何一次 `service_ctl install` 都可能再造出 E2。真正的收口是收口 installer，
   已登记为下一轮候选，不在本轮顺手做。
