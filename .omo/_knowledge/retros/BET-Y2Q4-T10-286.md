# Retro — BET-Y2Q4-T10-286 B4b 批次 3（`com.omostation.test-archive-purge-7d` 改道）

## 本意

ADR-0456 B4b 的验收判据是「指向 `Workspace` 的 plist 由 43 → 0」。批次 1–2 之后真实残差只剩一条：
常驻作业 `com.omostation.test-archive-purge-7d`。这条 BET 把它改道到安装位，三处声明（仓内 plist 源、
`services.yaml`、`.omo/cron/registry.yaml`）与机器侧安装副本重新同源，并把「为什么它必须留在检出根」
这句写在三处同源副本里的理由按证据处理掉。价值轴 NOT_PROVEN：这是治理收敛，不是业务收益。

## 经过

交付面比预期直：plist 的 `cd` 目标 / `WorkingDirectory` / 日志面改到安装位与 `~/.local/log/`，
新增 `OMOSTATION_STATE_ROOT`，`services.yaml` 补 `runtime_root: install` 并重算 `content_digest`，
cron registry 的同一句理由一并订正。行为等价性在碰机器之前先测：无参数分支走 `status()` 只读，
两侧实跑 cards=0 / dispatches=0 / due=0，改根行为等价。

三件事值得单独记：

1. **改完尺读数不降反升**。`workspace_scoped` 仍 2、`e7_undeclared` 由 0 变 1。根因不是改动错，而是
   `gen-service-configs.py:729` 与 `state_root_pins()` 读的是 **`~/Library/LaunchAgents` 的已安装副本**：
   声明已改、写面未改。用「把 87 份已装 plist 复制到临时目录、只覆盖本 label 那一份，再直接调
   `reality_check(registry, <tmp>)`」得到重装后的预测值（`workspace_scoped=1`、`e7_undeclared=0`、
   `e7_profile=29`），无需先动机器。`launchd_dir` 是第二形参（`:710`），而 CLI 路径 `:896` 硬走 `_launchd_dir()`，
   所以这一列**不可能用命令行复现** —— 这是量具的可用面，不是我的取巧。
2. **CI 首跑红，且红得对**。`governance-verify` 唯一失败：`test_undeclaring_registry_entries_still_resolve_to_checkout_root`
   报「声明运行根的条目应为 28，实为 29」。`INSTALL_ROOT_SERVICES` 是运行根声明的漂移钉，
   注释自述「增删一条都必须经过这里，而不是静默发生」。处置是登记（28 → 29），不是放宽判据。
   这条红同时是那条判据的判别力证明：它抓到了未登记的声明。
3. **E6 面上多一条 undetermined**。本 label 在 E6 里 `state=undetermined, script=null`，`e6_non_ok` 5 → 6，
   `e6_blocking` 保持 0。归因已立案缺陷 #173：E6 从 `ProgramArguments` 找脚本路径，认不出 `/bin/bash -c` 内联载荷。
   这是第 4 例。写进 spec AC-03b 而不是从读数里隐去 —— 一条明明已离开检出根的服务，在 E6 轴上与「完全没查清」同形，
   正是 #173 的代价。

## 教训

1. **「读数没动」要先问量具读的是哪棵树**。声明面（registry）与执行面（已装 plist）分家时，改完立刻复跑同一把尺
   得到「倒退形状」极易被误读为回归。修法是把尺的输入参数当缝用（这里 `launchd_dir` 正好是形参），
   先仿真预测，再决定是否值得动机器。
2. **同一条缝也能做反证**。收口腿把同一装置倒着用：临时目录里只把本 label 换回改道前的旧副本，
   `workspace_scoped` 立刻回到 2 且点名本 label，`e7_undeclared` 回到 1、`e7_profile` 回到 28。
   这既是 AC-04 的尺级判别力证明，也把「AC-03 的 2 → 1 归因于本条改道」从推断升级为测量。
3. **bound spec 中途增补在现有工具链里没有出路**（新立案 #196）。spec 内容一改，`claim` 先撞
   `SPEC_DIGEST_MISMATCH`，把 run 记录的 digest 手改对齐后再撞 `WORK_PACKET_HASH_MISMATCH`
   ——work_packet 由 spec 正文派生，此后该 run 的任何 claim 都被硬拦。`agent-workflow.py` 的子命令全集里
   没有 rebind/bind/update，`start` 无 spec 选项，`resume` 只接 run_id；台账侧「spec 再改必须重算」有约定，
   run 侧没有工具。本轮选择**还原 admission 快照**（不维护一份手改指纹的 run 记录），把已改 spec 的绑定让给
   收口腿的新 run。含义很直白：要么别改已绑定的 spec，要么先造重绑路径。
4. **不改别人的活锁**。`docs/plans/3y-bet-ledger.yaml` 被并发 run（`claude-lead` 的 T10-285）持有；
   收口腿起手实测 `A2A Path Lock Collision … in run 20261104T115230Z-project-code-change-d825f60f`，
   对方 `expires_at` 未到 ⇒ 不是可清的僵尸锁。只 claim 无主的 retro 与收据两径，台账腿另起 run，
   比 `--force-lock` 便宜且不越权。
5. **代价与收益同条目登记**。台账 done_when 里除了「`workspace_scoped` 2 → 1」，还写了
   「`e6_non_ok` 5 → 6（#173 代价，须在读数里可见）」与「漂移钉 28 → 29 由 CI 实跑拦住后登记」。
   验收尺如果不记代价，下一次读数的变动就没人能分辨是回归还是本条的余波。
