## 2. happened（实际发生了什么）

- 根因定位到「同一名字绑两次」：`bin/agent-workflow.py:278` 是执行检出根，`:282-287` 的
  `from omo.workflow import (WORKSPACE, …)` 覆盖它，kernel 侧值来自
  `projects/omo/src/omo/workflow/core.py:43` 的 `parents[5]` ⇒ 含义由**谁供给 `omo` 包**决定。
  此前我在 T10-272 的 evidence 里把它描述成「读 `canonical_root()`」——措辞不准确，本轮更正为「读供给 kernel 的那棵树」，
  canonical 只是当时恰好供给它的那棵树。
- 探针实测（base `14ee5723e`）：本检出供给 kernel ⇒ 两侧同值（diverge=False）；把 kernel 供给根换成
  `~/Workspace/projects/omo/src` ⇒ `diverge=True`，kernel-level 变成 `/Users/xiamingxing/Workspace`。
- 复算取证（含交付物的树）：`ensure_delivery_anchor()` 建桥后 run 记录可见 359 条；
  T10-272 的 `validate_completion_evidence` 读 `derived_state=delivery_accepted errors=[]`，
  `chain_bind.evaluate_complete` 读 `ok=True reasons=[]`。同两文件在 canonical 主检出（`dc67a0f5f`，落后）里 ABSENT。
- 装置自身的坑一条：探针第一版把根写成 `parents[1]`（脚本落在 `runtime/affected/` 是深度 2），
  当场 `ModuleNotFoundError: No module named 'omo'`。这类「`__file__` 深度」错误与被检对象无关，是测量装置没搭对。
- 写这条期间上游前进一条 `a1ecb980b`（CI checkout token 兜底，#4921），逐面核对：不碰本腿五个写面，
  也不碰被引用的三个尺本体（`bin/agent-workflow.py` / `bin/plan/bet-ledger.py` / `projects/omo`）⇒ 行号指针在新 base 上同样成立。

## 4. lessons（可迁移的三条）

1. **「两次读数不同，先疑基线」有一条更强的同族**：动的可以不是数据、也不是检查脚本的 base，而是
   **检查脚本所加载的 kernel 来自哪棵树**。问 `omo.workflow.core.__file__` 比问 `git rev-parse HEAD` 更根本。
2. **同名常量的第二次绑定是把语义交给导入路径**：`parents[N]` 类反推根在「脚本自己」上尚可读，
   一旦值来自别的包，它就不再表示执行检出。判据要写成「读哪棵树」而不是「读哪个根」。
3. **否证的候选项不得登记**：「AGENTS.md 幽灵路径 `bin/gac/doc-governance-check.py`」是我自己的笔误
   （本文件引裸文件名，真实脚本在 `bin/ssot/`）——把自身笔误写成仓库缺陷即伪造溯源，本轮显式拒绝并留否证读数。
