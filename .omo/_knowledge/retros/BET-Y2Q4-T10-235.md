## 4 lessons — 固化什么

1. **摘一条被文档与门禁引用的路径，失效面是「读者类」而不是「文件」**：本轮实测 5 类读者（存在性判定 /
   链接目标 / 输入契约 rc2 / 脚本登记 / 配额计数），每一类都要一条正向落点断言。已入 AGENTS.md §7。
2. **判据只允许「补创建者」一侧时，红线要能测**：削弱 `core_documents` 或让 coherence 缺输入返回 0
   同样能让 5 处红消失，而那删掉的正是「这份文件不能被直接摘库」的全部理由 —— 红消失而判据同时失明不是修复。
3. **「解析失败退回空」让「文件坏了」与「内容为空」同形**：`check-ci-surfaces.py::_load_yaml` 吞
   ScannerError 返回 `{}` ⇒ 登记面整块消失并造出 129 条与真实漏登记逐字相同的 error。先看**计数非零**
   再看 error 数。已入 AGENTS.md §7⑨。
4. **配额类检查读的是两棵已提交树**：`_get_baseline_delta` 用 `git show HEAD:` ⇒ 工作树里的 baseline bump
   在 commit 之前不可见，「改了就 FAIL」不是回归而是装置时区。
5. **判据的装置必须包含被判对象**：「0 broken links」在 `git archive` 复刻里不可证（17 条 gitlink 被排除），
   必须再在子模块齐备的树上取一次；两种树各一次，缺一格就是空绿。
6. **预存红只能用基线复刻复跑填**：全量 `tests/unit` 11 条红，用 `git archive d25b0dcee`（分支基线）跑同
   5 个文件得到**逐条相同**的 FAILED 列表才算证据；且 `tests/unit/**` 不在 CI 白名单 ⇒ CI 绿不构成它们的证据。
7. **摘库类交付的终验要在一棵「合并后新建的检出」上做，而不是在交付分支上做**：交付分支曾经跟踪过那个文件，
   它的 `git status` 干净是**同一棵树的自证**；只有新 claim 出来的检出才与 fresh clone 同形。本轮把这一步
   做成第四轮，结果它同时是判据-2 唯一能被直接观察的形态（缺文件 → rc=2 真报错，而不是"我以为它会报"）。
8. **`gac-worktree.sh merge` 的清理段会被自己的 checkout 弄脏**：脚本 squash 合并成功后把 worktree 切到
   `main` 并 ff 到刚产生的合并 commit，而 `git checkout` 不递归子模块 ⇒ `M projects/ecos` /
   `M projects/knowledge/kairon` 两条 gitlink 漂移，释放段以「worktree 不干净」退出。合并本身已经成功
   （`gh pr view --json state,mergedAt` 是判据），自清只需 `git submodule update --init <那两条>`，
   **不要**把它读成合并失败再跑一轮。
9. **D0 铁律与「摘库类交付」结构性冲突，结算方式只能是从 `write_surfaces` 摘除该路径**：
   `bet-ledger.py::cmd_complete` 对每条 exact 写入面跑 `_d0_surface_tracked()`（root index → pinned gitlink
   两级），而本 BET 的交付本体就是让 `.omo/state/system.yaml` 两级都查不到 —— 实测 28 条里唯一一条
   `not tracked`。`--force` 不是出路（它连同 `vision→retro` 链校验一起跳过）。先例 BET-Y2Q4-T10-212 把
   `.omo/state/health.yaml` / `.omo/_control/governance-data.json` / `BRIEF.md` 三件已摘库路径留在清单里
   至今 `done`，今天同样报 `not tracked` —— 那笔账没结算，只是没人复跑过守卫。**纪律**：写入面清单描述的是
   「会被本次交付写入且必须入库的路径」，摘库的正当性由 `done_when` 判据与正向忽略规则承载，不靠清单里
   留一条注定入库失败的指针。
10. **两套门禁读数不可互换，且「登记在门禁」不等于「CI 执行」**：`make gac-local-gate`（68 checks，rc=0）
    与 `--strict`（86 checks，rc=1）差 18 条，`gac-gate.yml:150` 用的是后者 —— 用前者当「与 CI 对等」的证据
    是装置错配。反过来 `--strict` 本机那 5 条红也不能读成「CI 该红」：`gate_checks(strict=True)` 在
    `_is_ci_env()` 两侧给 86/79，差集里的 `state-freshness-check` / `service-config-drift` /
    `agent-workflow-doctor` 在 CI **根本不执行**，另两条（compliance / observe）读本机全局
    `.omo/_delivery/agent-workflows/`（symlink 桥，`git ls-files` 该目录 **0 行** ⇒ CI 干净检出按构造绿）。
    **纪律**：引一条门禁读数当证据前，先问「CI 那一步跑的是哪个 flag、这条检查在 CI 是否被执行」，
    指认命令是调 `gate_checks(strict=True)` 在 `_is_ci_env()` 两侧对拍，**不是**去 `CHECKS` 里 grep 这个名字：
    `state-freshness-check` 在源码里登记两次（`:150` 带 `ci_only: True`、`:180` 带 `--json`），
    构建后的 `CHECKS`（87 条）只留**后者**，但 `CI_ONLY_CHECKS` 与 `CI_SKIP_CHECKS` 两个集合都由**全部**登记
    构建 ⇒ 该名字同时属于这两个集合，净效果是「非 strict 本机跳（ci_only）、strict 的 CI 跳（ci_skip）」，
    真实执行面只剩「本机 strict」这一格。按名字 grep 只会得出「它接在门禁上」，而这句话在 CI 侧是假的。
11. **分侧计数要由装置分侧产出，不能从混排清单里「数」**：receipt §5 把站点拆分写成「11 处子模块 /
    root 侧 13 处」，与真实读数（root 11 / 子模块 13）恰好**两侧对调** —— 总数 24 是对的，所以任何
    「合计与别处对得上」的复核都抓不到它。成因是首次扫描只打印一份混排命中列表，两侧数字是**按输出
    顺序数出来的**（`bin/` 排在后面），抄反了归属；本轮改成按侧分组、每侧先印计数再印明细，一次跑出
    `11 / 13 / 24` 三个数才落笔。**纪律**：凡「总数 = A + B」这类拆分断言，装置必须**分别**产出 A 与 B
    （并各自可指认到文件），而不是产出一串再靠人分堆 —— 与 §7⑥「先 print 原始行再定性」同根，
    只是这次错的不是判据而是**抄写**；证据文档里两个数字都「有出处」，却都出错了，这只能是重测。
12. **否定式断言（「未登记 / 不存在 / 找不到出处」）要把对象自己的元数据字段读一遍，不止读判定字段**：
    receipt §7.1 首稿把 `~/.local/opt/omostation-publisher` 写成「第三个**未登记**的安装位」，而它就在
    **同一条服务的 `notes` 里**（BET-Y2Q4-T10-227 原话「维护专用洁净检出 `~/.local/opt/omostation-publisher`…
    机器属主，不进 ws-* 卫生面」），也是 driver 的 `CHECKOUT` 默认值（`bin/panorama/projection-full-refresh.py:32-34`，
    env seam `OMOSTATION_PUBLISHER_CHECKOUT`）。首稿只读了 `program` / `interval_sec` / `generate` 三个**判定用**
    字段就下结论 ⇒ 「我没查到」被写成「不存在」。复算后真正的缺口在**词汇面**而不是登记面：该路径在 ADR-0456
    的根词汇里没有位置（`repo_root.install_root()` 只认 `~/.local/opt/omostation`，B4a）⇒ 结论形状从
    「多出一个根」改成「双根契约在机器级进程里被部分采用、部分绕过」—— 后者才是对计划有用的那条。
    **纪律**：写否定式断言前，把该对象的**全部**字段（含自由文本的 `notes` / `description`）打印一遍再定性。
    同批一条正向收获：`gen_launchd_plist()` 内存产物 vs 盘上的 `unified_diff` 由首稿的 60 行重测为 **63 行**，
    且两侧**缩进指纹相反**（盘上 tab 缩进 40 行 / 4 空格 0 行，生成侧 tab 0 / 4 空格 15）——
    这条指纹比「有差异」强一档：它证明盘上那份**不是这台装置写的**，把「谁写的」从猜测变成可指认。
13. **批量重算装置自己也是被判对象，近邻启发式的「绿」不是一次测量**：本 retro 第 12 条落盘后，我用
    「路径命中行 **±3 行**内任意 `sha256:[0-9a-f]{64}`」批量刷新台账摘要，并**拿它自己的输出当证据**。
    按 YAML 子映射配对（`ref` 与它的 `sha256` 是**同列兄弟键**）重导时才发现跨键串写 **2 处**：
    `engineering.rollback` 与 `operational.fresh_receipt` 的 `ref` 指向 receipt，摘要位上却是 retro 的哈希。
    装置在这份数据上「大部分时候对」，所以它**交付的那一刻是绿的** —— 与 §7⑥「匹配词与实际文本不同源」
    同族，这里不同源的是**配对规则与被配对的键**。
    **纪律**：凡是「一次跑完、结果直接进账」的批量改写，必须用**另一台不共享失效模式的装置**复算 ——
    本轮是列配对行扫 + `yaml.safe_load` 结构走查两台，读数一致 **refs=11 stale=0**（三笔 `accepted_specifications`
    + T10-235 全部 8 条 `receipt://` 轴键）才算闭合；且装置自己的**配对假设**要在明细里逐条印出
    「哪条 ref 配了哪条 digest」，只印 `ok/stale` 计数看不见串写。
