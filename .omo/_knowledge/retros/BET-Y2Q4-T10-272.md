## 4 教训

1. **判据里不许写隔壁桶的读数。** 「E1 仍 0」是我自己桶之外的东西，它由另一条 lane 的注册表动作决定。要么把它写成条件式（「E1 的本轮净贡献为 0」，可由 `test_e7_promotion_does_not_disturb_e1_to_e6` 这种同函数内的证据支撑），要么显式标注它随 base 变、必须带 base 读数。**判据**：一条 done_when 若含另一个桶的绝对数值，它在交付那一刻就不受交付方控制。
2. **两次读数不同，动的可能是尺，也可能只是隔壁的数据。** 先前固化的是前者（`check-work-landed.py` 由 `__file__` 定根 ⇒ 尺随 base 变）。本轮是后者：`bin/plan/bet-ledger.py` 在 `4858eb530 → 2ba4b614d` 之间 diff 为空，5 条 ERROR 却清零了 —— 是台账文本被并发 PR 改了。所以比较前不只 diff 检测器路径，还要 diff **被检对象**的路径。
3. **跨 base 的「等值」不是证据。** 「ok/rc 与改道前一致」这一条最终由两条测试承重，而不是由「两次读数一样」承重，因为 E1 已经变了、两端不可比。凡是「不改既有行为」类判据，优先落成正反用例，读数只做旁证。
4. **管道尾的 `$?` 不是被检命令的 rc。** 本轮据此把 `affected-graph.py` 命中已存在输出的情况误记为「rc=0 只报文字」，无管道复测真值 `rc=2`。落笔前按无管道形式复算一次（AGENTS.md §7 zsh 条的又一次自伤）。
