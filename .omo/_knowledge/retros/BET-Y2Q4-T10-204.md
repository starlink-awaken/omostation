## Q3 过程中发现的与 plan 不符的事实（打假）

1. **"门禁漏报" 这个直觉读数站不住。** 事件形状（改动从 main 消失、全程零门禁报错）天然
   指向 harness。实测：回退 commit `28158b9bc` 自带 `[gitlink-regress: …]` 豁免并指名理由
   （"freshness gate requires the pin to be the child main tip"），即回退是**按规则正确执行**
   的行为。真正的缺口是**用 gitlink 当交付载体**。若顺直觉去改 freshness gate，
   会造出一个反向的错误。
2. **`--require-main` 是被有意移除的，不是漏配。** PR `4209`（`86b61b84e`，2026-09-22）
   为了支持跨仓 PR 模式，从 `.github/workflows/gac-gate.yml:202` 的 reachability 步骤删掉了
   它。pre-push hook（`bin/gac/hook-runner.sh:212` + `hook-manifest.yaml:94-95`）同样不带。
   本 bet 因此**不**把它加回去 —— 反转属 principal 决定。
3. **一条 main 上红了 4 天的测试是同一事实的另一面。**
   `tests/test_gac_gate_workflow_purity.py::test_reachability_and_generators_are_check_only`
   仍断言 CI 步骤含 `--require-main`（实测 `1 failed, 6 passed`）。测试与 PR 4209 的决策
   必须有一侧被更正，但两侧都由 principal 决定 —— 按 non_goals 只登记不处置。
4. **`git rev-parse projects/omo` 是静默陷阱。** 对 gitlink 路径它返回字面路径而非 SHA，
   于是我把 ledger `verify` 第一版写成了不可运行命令，而**没有任何检查会告诉你**：
   `.github/workflows/bet-done-gate.yml:28-38` 的 `bet-done-transition` 只跑
   `bet-ledger.py lint`（模式校验），不执行 `verify` 里的命令。
   正确写法 `git rev-parse HEAD:projects/omo`。另有 zsh 把 `"$VAR:mod"` 当修饰符吞掉的坑。
5. **`ledger-safe-insert.py` 对新 bet 也强制要求完整 3 轴 `completion_evidence`。**
   诚实的交付前形状只能是 `NOT_STARTED`/`NOT_PROVEN`/`evaluating`；为了过校验写
   `delivery_accepted` 就是伪造。同理它只接受 **mapping**（`- ` 列表项由工具自己渲染），
   且普通 YAML 标量里的 ` #4209` 会被当注释吃掉 —— 第一次 `--dry-run` ParserError 的真实原因。
6. **`claim` 的 `--affected-hash` 不是摘要，是工作树相对 JSON receipt 路径。** 必须先跑
   `bin/gac/affected-graph.py --changed-projects <p> --output <rel> --json`。
   非 `projects/…` 的 claimed path 绑定到哨兵项目 `workspace-root`。
7. **一次 CI 红在同 SHA 上重跑即绿，且我用四条独立证据排除了自身因果：**
   `cascading_test` 报 `assert 1277162 == 0`。用例是
   `projects/omo/tests/unit/test_resident_status.py` 里的
   `test_one_hundred_concurrent_full_snapshots_are_bounded_and_side_effect_free`，
   它 monkeypatch **全局** `status.time.sleep` 并断言 `sleep_count == 0`，负载相关。
   排除链：omo 自身 CI 在 `e925214` 绿 / 根 main 绿 / pin 只差一个 commit 且未设 profile 时
   解析路径逐字节相同 / `gh run rerun --failed` 同 SHA 转绿。未 `--no-verify`、未登记豁免。
8. **陈旧 `refs/remotes/upstream/main`（`6330e8202`）会污染 transaction 的增量 base**，
   尽管根本没有 `upstream` remote —— 表现为假的 ".gitmodules changed，请改用 --all"。
   而 `--all` 会把 16 个未初始化 gitlink 一起 stage 进 commit。解法是显式
   `--changed-from origin/main`，不是听提示词。
9. **"脏态先快照"这条纪律对 worktree 根本不生效，且已发生一次不可回溯的对齐。**
   实测 `workspace-wip-guard.py status` 在本 worktree 返回 `main_workspace: false`、
   `snapshot_count: 0` —— 该守护只覆盖主工作区，worktree 内的子模块工作树没有任何快照机制。
   早前 b1 的 worktree 释放时就发生过一次"未快照直接把子模块工作树对齐回 pin"。
   可证明的：**没有对象丢失** —— `0790f8977` 仍由子仓远端分支
   `agent/governance-agent/ws-devruntime-b1s2` 可达，且与 `e925214` 的内容差仅
   `src/omo/omo_paths.py | 4 +---`；**不可证明**的：当时是否存在被丢弃的未提交文件改动。
   因此本轮在本 worktree 重复该动作前先做了检查（两个子模块 `git status --short` 均为空）
   才对齐 —— 这是现有机制下唯一可执行的替代防线。

## Q4 改变了什么 / 教训固化

**改变的东西**

- gitlink 落位规则从"口口相传"升为 contract spec（4 条：pin 必须是子仓 main 的祖先；
  子仓先合再动指针；只走 `submodule-pointer-transaction.sh`；`[gitlink-regress:]` 只用于
  真正坏掉的 pin）。
- B1 的内核侧 seam 重新出现在 `origin/main` 上，且 verify 四条形成的"正向存在性检查"
  可被下一个 agent 直接复用。

**固化下来的判据（比规则本身更实用）**

1. **主仓 CI 绿 ≠ 子仓改动已落地。** 最便宜的肯定式检查是读 pin 上的文件：
   `git show "$(git rev-parse HEAD:<sub>):<path>" | grep -c <新符号>`。不要依赖门禁告诉你。
2. 交付跨仓改动的顺序被钉死为 **子仓 merge → 根 pointer bump → 根 PR**。反向顺序一定会被
   freshness 波次回退，且回退是正确行为。
3. 动指针前跑**严格式** `submodule-reachability-gate.py --source head --fetch --require-main`
   （比 CI 实际跑的更严），它能在合并前发现"可达但未合"的 pin。
4. 遇"某改动从 main 消失了"：先 `git log --all -p -- <path>` 找 commit body 里的豁免标记
   （本例的 `[gitlink-regress:`），再谈是不是事故。多数自我记录的自动化不是事故。
5. verify 命令必须**当场跑一遍**再写进 ledger。写进台账的不可运行命令比没有命令更坏。

**报告给 principal、本 bet 不处置**：Q3 第 3 条（测试 vs PR 4209 二选一）、第 7 条（全局
sleep monkeypatch 的负载脆弱性）、第 8 条（陈旧 ref 应清理）、pre-push reachability 34.8s
（建议下沉 CI）、`BET-Y2Q4-T10-203` 的 `completion_evidence` 未随回退更新（**不代其补写**）、
ADR-0456 仍为 PROPOSED。
