# BET-Y2Q4-T10-260 retro — 仓内唯一不可解析的 launchd plist 镜像

台账：`docs/plans/3y-bet-ledger.yaml` `BET-Y2Q4-T10-260`
规格：`docs/superpowers/specs/2026-10-20-launchd-plist-mirror-xml-legal-argv.md`（spec_version 1.0.0，digest `sha256:922daf45f32cd9aca6d43096e5c1ce35042a580fef4ce97eefdad1e00edbb418`）
Receipt：`docs/reports/2026-10-20-launchd-plist-mirror-xml-legal-argv-closeout.md`
交付：PR #4832 squash 合并为 `011f7b953d9a64c97d3f3c20d3432e81c9cd6144`

## 1 intended — 原本要发生什么

T10-258/T10-259 把 B3 的注册面收敛到「声明 == 已装」之后，剩下两条从未安装的 plist
（`com.omostation.arch-health-weekly`、`com.omostation.panorama-refresh-guard`）被 T10-258 的
circuit_breaker 明确留给评审清单，不在那一轮判定「该不该活」。本 BET 只处理其中一条**技术非法性**：
`com.omostation.panorama-refresh-guard.plist:26` 的注释体里写了确切命令行
`python3 bin/gac/panorama-refresh-guard.py --json --dry-run`，而 XML 规范禁止注释内出现连续两个
半角连字符 —— 于是这份镜像按 expat 的判据**整份不可解析**，`plistlib` 报
`ExpatError: line 26, column 48`。

意图是「消除非法性且不丢信息」：argv 移到 `--` 合法的一侧（脚本模块文档），plist 注释留指针。
基线读数（`origin/main@0329ceeb3`）：`tests/unit/test_launchd_plists_xml_safe.py` → `2 failed, 2 passed`。

## 2 happened — 实际发生了什么

- 修复确实是两侧的，且先在 `/tmp/t260` 副本上由检测器自己验算过才开始改真实检出：
  `plistlib parses OK / offenders = [] / docstring carries the exact argv: True / ast.parse OK`。
- 交付后读数：`plistlib` rc=0 且 `Label = com.omostation.panorama-refresh-guard`；
  检测器 `4 passed`；`ast` 解析确认 `guard.py:15` 的 `Manual check` 行逐字承载 argv；
  注释块 `--" inside any: False`。
- 运行面零效应是被**正向读数**证明的，不是靠「没执行写操作」的意图：`~/Library/LaunchAgents`
  内该 label 命中 0 份、plist 总数仍 77、`crontab -l` sha256 前 16 位仍是 `cbf14ddc2fdd972a`。
- `bet-ledger.py lint` = `OK -- 554 bets, 16 tracks, no errors`；
  `doc-governance-check.py --scope workspace` = `ok=true`、30 findings、无一条指向本 spec。
- 一处**判据措辞与真实读数的偏差**没有粉饰：done_when-2 写的是「命中仅在 `guard.py`」，
  实测 `git grep` 另有 3 处**散文引用**（本 BET 自己的 goal 文本、自己的 verify 命令文本、
  以及 T10-258 spec §163 对这条缺陷的记录）。关键面 —— plist 文件本身 —— 是 0 命中。
  第二腿把这条 `expect` 文本改成实测读数（「任何 plist 内零命中；代码面唯一命中是 `guard.py`
  的模块文档，其余命中是记述这一缺陷的文档」），而不是删引用去凑「仅 1 处」—— 完整命中列表
  仍逐条留在 receipt。
- **第二腿是被 CI 逼出来的**：`interface-check` 唯一那条红是
  `test_ops_launchd_plist_declared_guard.py::test_malformed_plist_still_reports_its_label`
  —— 它把断言钉在「这份 plist 不可解析」这个**一次性缺陷**上，文件修好后前提按构造消失。
  这不是回归，是 T10-258 故意留的耦合。它的报错文案要求「同时从 ALLOWLIST 摘除**并登记进
  services.yaml**」，后半句不采纳（登记属署名面），只做了前提维护：回退分支改由合成样本覆盖，
  另加一条同时钉「文件已合法」与「缺口仍敞开」的不变式。基线 `1 failed, 408 passed, 9 skipped`。
- **台账在本腿被自己写坏过一次**：上一次编辑在 `yaml.safe_load` 之前就把文本落盘，多行明文标量
  的续行与 `expect:` 键同缩进 ⇒ `ScannerError: while scanning a simple key, line 43647`，
  整份台账在磁盘上不可解析。判据顺序改了（先构造字符串 → 试解析 → 再 `write_text`），
  并把续行缩进/引号补齐。另发现 `non_goals[1]` 早在第一腿就被明文标量里的 ` #124` 静默截断
  （`#` 在未加引量的标量里开注释），已改成带引号标量后逐字回读确认。

## 3 changed — 现在与之前不同之处

- 该镜像成为可安装的一份 plist（**可安装 ≠ 该安装**；装不装仍属 #124 的 21 条准入清单）。
- `tests/unit/test_launchd_plists_xml_safe.py` 从 main 恒红变绿。但 CI 仍看不见它 ——
  `.github/workflows/governance-check.yml:118-127` 的 pytest 白名单不含 `tests/unit/**`。
  本 BET 明确不扩白名单，只把盲区登记在交付说明里。
- 台账侧新增一条用 `ledger-safe-insert.py` 插入的 BET（`+83/-1`，一次成功，无手工定位行号）。

## 4 lessons — 教训

1. **「消除非法性」与「骗过检测器」的分界是信息去哪一侧**：同一份 argv，删掉 = 丢信息、
   挪出注释 = 合法且保信息。判据写进 spec C2 才不会被下一轮「简化」成删除。
2. **`write_surfaces` 要宣告「被这个缺陷钉住的测试」，不只是「我要改的文件」**：本轮第一腿
   自认为把面声明完了（主面 + retro + receipt），实际漏了 `test_ops_launchd_plist_declared_guard.py`
   —— 而它正是唯一会因这次修复而红的 CI 用例。判据：领 BET 后先
   `git grep -l "<缺陷的识别串>" tests/`（本轮识别串 = 该 label / `XML 非法`），
   命中的用例文件全部进首版 `write_surfaces` 再 `start`。
   漏了之后的代价是可复现的：改投影字段 ⇒ 后续 `claim` 一律 `WORK_PACKET_SOURCE_DRIFT`；
   而 `refresh-packet` 在本仓**不可用**（`bin/agent-workflow.py:678/814/1031` 有实现体，
   但 argparse 的子命令表里没有它），真实补救是**新 run 承接**：本轮对新面起
   `20261020T035750Z-project-doc-change-60d72e4e` 单独 claim 那条测试路径，台账面仍由第一腿的
   run 持有（同一 run 重复 claim 会 `A2A Path Lock Collision` —— 撞的是我自己的旧锁，不是并发 agent）。
3. **零匹配的运行面判据不能走 shell 管道**：`ls | grep -c <label>` 在零命中时 grep exit 1 断链，
   本机 `ls` 又是 eza 别名（`-t` 直接报 `--time` 非法值）。改用 python 计数并**同时打出绝对量**
   （0 命中 + 总数 77），这样「判据本身没跑起来」与「真的零命中」在读数上可分。
4. **判据的 `expect` 文本也是要实测的物件**：写「命中仅出现在 X」之前先跑一次 `git grep`。
   本轮偏差无害（plist 侧确实 0 命中），但同一形状若反过来就是假红。
5. **改台账这类大 YAML 的手势顺序：先在内存里构造 + 试解析，通过了才 `write_text`**。
   本轮反过来做，磁盘上的权威台账一度不可解析（`ScannerError` at line 43647），
   而这颗雷只在下一位读者碰到时才响。两个同源形状各有其坑：① 多行明文标量的续行必须比**键**
   更深缩进（与键同缩进 = 被当新键，`could not find expected ':'`）；② 未加引量的标量里
   ` #` 开注释 —— `task #124` 把整条 non_goal 从 `（属 task` 处截断且**不报错**，
   `lint` 照样 `no errors`。凡正文含 `#`/`：`/括号的登记面一律用引号标量。
   判据：改完必做「`safe_load` 成功 + 目标键逐字回读 + 括号配平」三件事，只看 lint 绿不够。
