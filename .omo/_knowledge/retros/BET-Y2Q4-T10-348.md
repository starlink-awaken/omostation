# Retro — BET-Y2Q4-T10-348

## 1. 意图（intended）

`bin/omo-status`（swarm 可观测性大盘）在全部 agent 心跳陈旧约 25 天的情况下仍显示
"● HEALTHY · 6/6 Agents Active"。本 BET 消除该健康度假阳性：healthy_count 不再取
心跳 tick JSON 自报的 ok_count，改为对 per-agent 秒龄真算（≥600s 判 stale 不计入），
header/TUI 徽标收紧为全绿才 HEALTHY，并补回归测试锁定语义。

## 2. 实况（happened）

**根因双点**：`swarm_collector.py` 的 `ok_count = data.get("ok_count", agent_count - failed)`
直接采信心跳文件写死的自报数字（文件是 2026-10-28 写的，ok_count 恒为 6），与同循环内
`sec_ago < 600` 的真判定脱钩；`swarm_cli.py` 的 `healthy_count > 0 → HEALTHY` 让单个
healthy 也能亮绿灯。现场证据：2026-11-22T12:10:26Z 快照，6 agent SEEN 全部 2178608s。

**验证数字**：cockpit 全量 1626 passed / 0 failed / 1 xfail，其中新增
`test_swarm_heartbeat_staleness.py` 3 用例（陈旧→0、新鲜→全绿、自报忽略）全过；
实机对照——同一颗 25 天陈旧心跳，修复前 `6/6 Active + HEALTHY`，修复后
`healthy=0/6` 全员 stale，header 如实渲染 `○ DEGRADED · 0/6 Agents Active`。

**circuit_breaker 触发与处置**：healthy_count 消费方扫描发现 `swarm_app.py:262`
（TUI 状态栏）同构消费（`> 0` 判绿），性质清晰（同一 bug 的第二显示面），一并收紧
为全绿才绿，台账 write_surfaces 与 spec 同步扩项后重绑 digest——未静默越界。

**门禁面**：`gac-local-gate` 唯一 FAIL（service-config-drift）为主仓/worktree 双环境
同报的存量 launchd 漂移（com.omostation.omo-debt-refresh plist vs services.yaml，
双处 exit=1），与本 BET 写面零交集，如实入证不私改。

- `projects/cockpit/src/cockpit/tui/swarm_collector.py`：删除自报 ok_count 消费，

  HEALTHY（+8/-1 行）。

- `projects/cockpit/src/cockpit/tests/test_swarm_heartbeat_staleness.py`：新增 3 用例。
- `docs/plans/3y-bet-ledger.yaml`：登记 BET-Y2Q4-T10-348（596th）+ spec 绑定。

## 4. 教训（lessons）

- 自报字段（ok_count）与派生判定（秒龄 status）并存时，显示层必须消费派生值——
  "当时为真"的数字不是"现在为真"的健康度。这是 §6.6 declare≠execute 在观测层的镜像。
- 修复前先扫全部消费方（circuit_breaker 条款）性价比极高：一次 rg 把第二张同构
  显示面（swarm_app）揪了出来，避免了"修一半"的假阳性残留。
- 治理链路（worktree claim → BET+spec 绑定 → start → affected-graph → claim →
  verify → closeout）全程有门禁拦截语义缺口（缺 spec、缺 profile、锁、缺 retro），
  每次拦截信息都准确——拦得对，不是官僚主义。
