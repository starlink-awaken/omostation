# BET-Y2Q4-T10-210 复盘（固化两条证据装置认知到 AGENTS.md）

1. 断言「CI 评的是 merge tree，不含 base 漂移」；
2. 从未写下本机是浅历史、claim 出的子模块深浅不定。

本 BET 只把这两条写成**可复算**的认知，不动工具、不动 CI。Appetite 2 小时。

## Q3 与 plan 不符的事实（打假）

1. **写台账之前没先拿到台账 claim**。顺序是本 BET 的 spec §2 定的（ledger-safe-insert → start → claim），
   但 claim `docs/plans/3y-bet-ledger.yaml` 时被并发 run 拦住：
   `A2A Path Lock Collision … in run 20260927T142335Z-project-doc-change-17158953`。
   条目已在 worktree 落盘、路径尚未持有 —— 属于协议顺序滑了一下（主仓未被影响，canonical 未写入）。
   正确顺序应是 `start + claim` 在 insert 之前。
2. **拦路的是我自己上一波的 stale run，不是别人的活**。17158953 是 T10-208 wave-2 的记录，其交付早已
   merge（`05eaa064b`，main 上 `status: done` / `delivery_accepted` 均已实测复确认），但记录仍 `active`
   且 `evidence: []`。用 `close`（非 `closeout`）收掉：它声明的
   `path_docs_plans_3y-bet-ledger.yaml.lock.yaml` 磁盘上已不存在，closeout 的 SR-01 heartbeat 会因
   "missing lock file" 必然失败 —— 这是同一类结构性缺陷的第二次现身（rescue 合并锁面非按 run 命名空间隔离）。
3. **`--affected-hash` 不能写进 `.omo/_delivery/agent-workflows/`**：该目录在 worktree 里是
   **symlink**，`affected-graph.py` 明确拒绝父链含 symlink（`receipt output parent must not contain symlinks`）。
   改落 `.omo/_control/`。上一波能落在 `_delivery` 是因为当时该路径不同 —— 别把一次性路径当契约。
4. **"浅历史"不是常量，是随 claim 路径漂移的量**。原计划写"claim worktree 的 `projects/omo` 只有 1 个 commit"，
   但**本次** claim 的 worktree 是深检出（766）。三个历史 worktree 各 1 commit、本次 766 —— 所以写进文档的
   结论必须是"深浅取决于 claim 路径，动手前先测"，而不是给一个固定值。这正是本 BET 要修的认知类型错误：
   把一次测量当长期事实。
5. **数字会因主仓前进而漂移**：root 本地可达 commit 从 8,324 → 8,326，canonical `projects/omo` 从 766 → 767
   （两次测量间隔一次 fetch）。文档里保留数字但同时给出复算命令与测量日期。
6. **spec 的 frontmatter 少一个字段，会让三个 job 同时红**。首次 push 后
   `governance-verify` / `gac-gate` / `interface-check` 三条红是**同一个根因**：
   `document-governance.yaml` 的 `accepted-specifications` surface 要求
   `required_frontmatter: [status, lifecycle, owner, last-reviewed]`，我按 `bet-closeout-chain` skill 里
   写的"七件套"只写了 6 项（**skill 漏了 `owner`**）。补 `owner` 后 spec 的 sha256 变了，台账
   `accepted_specifications[].content_digest` 必须同步重算，否则 `COMPLETION_FILE_DIGEST_MISMATCH`。
   复算装置也不是 `verify-omo.sh`（它本地 exit 0 而 CI 红），而是
   `bin/ssot/doc-governance-check.py` / `bin/gac/ci-check-runner.py --workflow governance-check.yml`。
7. **台账的全局计数器 `meta.total_bets` 是并发 mint 的单点**，有两种失效模式，第二种更坏：
   - 并发写**相同**值 → 文本自动合并成功，但 merge tree 里语义错：
     `META_TOTAL_BETS_DRIFT declared=499 actual=500`（`bet-done-gate.yml` 在 merge tree 上把两个 mint 的
     条目都数进去，计数器只 +1）。
   - 并发写**不同**值 → 文本冲突 → GitHub 造不出 synthetic merge commit → 该 PR **一条检查都不上报**
     （`mergeable: CONFLICTING` / `mergeStateStatus: DIRTY`）。门禁信号完全消失，而不是变红。
   - **我第一次的修法制造了第二种模式**：把整份台账替换成 main 的内容 + 我的条目，反而让计数器区域与
     main 的编辑重叠 → CONFLICTING。正解是 `git merge origin/main`，把冲突解成逐字节相同的**超集**
     （用 `git hash-object` 与 stage-2 blob 比对确认），commit `7f17f7950`。
8. **旧 base worktree 里的本地门禁不可信**，本次两类假红都是这样来的：
   - 台账类：`COMPLETION_FILE_REF_MISSING` / `retro-due` 指向的 main 已有文件不在旧 HEAD 树里
     （`git cat-file -e origin/main:<path>` 成功、`:<path>` 于 HEAD 失败）。merge 后自清，
     `bet-ledger.py lint` → `OK -- 500 bets, 16 tracks, no errors`。
   - BOS/SSOT 类：`check-cross-repo-consistency.py` 报 16 个未注册 / 14 个新增，实为子模块工作目录落后；
     `git submodule update --init --no-fetch projects/agora projects/omo`（本地、不联网）后降到
     2 个 = 2 条已知 backlog，`✅ 12 checks PASS`。
   - 这两类**恰好是本次 AGENTS.md 第二条认知的实例**：治理装置在浅/旧检出里给出的判定不是回归，是装置没历史。

## 教训（固化去向）

- 协议层：`AGENTS.md` §6 两条新条目（本次交付本体）。
- 纪律层：**先 claim 再写台账**；claim 被自己上一波的 active run 拦住时，先核对该 run 的交付是否已在 main，
  是则 `close` 收账（并写明为何不能用 `closeout`），而不是 `--force-lock`。
- 纪律层：**台账竞争用真 merge 化解成相同 blob 的超集**，不要用"整份覆盖"来解 `META_TOTAL_BETS_DRIFT`。
