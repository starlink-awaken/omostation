# BET-Y1Q4-T10-135 retrospective

## Q1. What was intended?

门禁优化二期（红线机制分析建议 3+4）：docs-only PR 风险分级（跳过重检查）+ spec-init 一键工具（消灭 spec binding 五连报错试错）。

## Q2. What happened?

PR #3359 合并（94030491），CI 23/23 CLEAN：
- **docs-only 风险分级**：ci-check-runner 检测变更面（全为 *.md/docs/.omo → docs-only），ci-surfaces 标记 `skip_if_docs_only: true` 的 check 自动 SKIP（首批仅 doc-governance 全量扫描——保守起步，按数据扩）
- **spec-init**：`bet-ledger.py spec-init <BET-ID> --spec <path>` 七件套补缺 + digest + binding 幂等插入/刷新

## Q3. What changed during implementation?

- **spec-init 狗粮实战二次验证**：rebase 冲突解决时 `--ours` 误丢 T10-135 条目，重插后用 spec-init 一键补 binding → start **零报错一次通过**（对比手工时代五连报错）——工具价值实证闭环。
- **remote 污染真凶定罪**：`remote.origin.pushurl`（独立于 url 的 push 专用字段）被 claim 镜像写成 agora——此前所有"轮转污染"观测实为 fetch 行正常、push 行被污染的双轨假象。修复 = `git config remote.origin.pushurl`（set-url 不覆盖 pushurl）。
- **处方化当场立功**：push 失败时 hook-runner 打印 `💡 fix → init 子模块命令`，按方执行即过——T10-134 的交付在本 BET 的 push 环节直接省了一轮考古。

## Q4. Lessons (P73 truth-driven)

- **git remote 的 url/pushurl 是两条独立轨道**：诊断 push 异常必查 `git config --get-all remote.origin.pushurl`，只看 `remote -v` 的 fetch 行会被误导。
- rebase 冲突 `--ours/--theirs` 语义 = 侧别而非"谁的对"——解决后必须重验自己 commit 的核心内容是否还在（本案例 T10-135 条目被静默丢弃）。
