## Q3 过程中发现的与 plan 不符的事实（打假）?

### 1. kairon graph 实现已在 tip (PR #3231, commit 9a381754a)
spec 写时未实现, 写完时已 ship. kairon 指针已被 PR #3231 bump 到 agent/bet-y1q3-t10-117-kairon. 本轮只补 CLI/bootstrap/tests.

### 2. gbrain hybrid.ts 路径漂移
spec 写的 `projects/knowledge/gbrain/src/retrieval/hybrid.ts` 实际不存在, 真实路径是 `projects/knowledge/gbrain/src/core/search/hybrid.ts` (1306 LOC, 已 ship). 修法: ledger write_surfaces 改为真实路径, 加注释说明.

### 3. spec verify cmd 路径无效
spec 写 `python -m projects.knowledge.kairon.cli hybrid-query` 不可执行, 因为 kairon 通过 pyproject 安装为顶层模块, 应是 `python -m kairon.cli`. 修法: ledger verify 改 `cd projects/knowledge/kairon && uv run --with pyyaml python -m kairon.cli ...`.

### 4. spec verify cmd 期望字符串含未引号冒号
原 spec 写 `expect: exit 0, 输出含 policy: 2000 / ...` 直接导致 ledger YAML 解析失败 (`mapping values are not allowed here`). 修法: 整段 expect 用双引号包住.

### 5. spec "Top-3 Recall ≥95%" 无可执行基线
BM25 检索在单查询上完美命中 (P-00000 score 9.000), 但 95% Recall 需要:
- 标注集 (queries + relevant entity IDs)
- 评估脚本 (Recall@3 = hits_in_top_3 / total_relevant)

本 bet 不生成标注集 (production policy corpus 不可获取), 改用 **BM25 在 deterministic synthetic corpus 上的精确命中** 作为弱替代证据. 后续评估 bet 必须补:
- 真实/合成 policy corpus with relevance labels
- `bin/eval/kems_v2_recall.py` 跑 Recall@1/@3/@10

### 6. source 字段是占位 URL
`source: https://kems.example.gov.cn/<type>/<id>` 是 seed 时的占位, 真实 policy 应有官方 URL (国家卫健委 / 国务院 / 各省厅). 后续 ingestion bet 必须:
- 接入真实 source registry
- bootstrap 用真实 corpus + URL 重建

### 7. 4 类 5000 entities 的 corpus 是 deterministic 但 synthetic
content 是模板化字符串 ("卫生健康数字化转型 — 实施指引第 1 号"), 不是真实政策. 优点: 评估可重现; 缺点: 检索质量不等于真实. 后续 ingestion bet 必须用真实数据替换.

### 8. kairon 包结构 vs module 路径
`projects/knowledge/kairon/src/kairon/cli.py` 是 `python -m kairon.cli` (顶层 `kairon` 包), 不是 `python -m projects.knowledge.kairon.cli` (绝对路径). 验证已改为前者.

### 9. kairon jsonl 格式: 实体和边都在一个文件
`g.save(path)` 写入 entity 行 (带 `"entity_type"`) 和 edge 行 (带 `"relation"`) 混合. 测试用 `"entity_type" in line` vs `"relation" in line` 区分. 这是混合存储, 后续可考虑分文件.
