# BET-Y1Q4-T10-134 retrospective

## Q1. What was intended?

门禁迭代两件套：全量 Gatekeeper 的 baseline/grace 机制（存量违规降级 warn，新违规仍硬失败）+ hook-runner 失败处方化报错（从 hook-manifest 读 fix 字段打印可复制修复命令）。

## Q2. What happened?

全部交付：
- **contract_gatekeeper**（omo #145/#146 → 12523432）：--baseline 默认自动加载 gatekeeper-grace.yaml；**零依赖行解析**（保持本脚本 no-yaml-import 惯例，CI 无 pyyaml 也跑）；grace 命中 `[grace]` 前缀不计 FAIL
- **gatekeeper-grace.yaml**（新 SSOT）：cockpit voice_memo.py 存量直写为首个 grandfather 条目（shrink_only 声明）
- **hook-runner.sh**：失败时打印 `💡 fix → <命令>`；hook-manifest 4 类易错 check（remote-hygiene/gitlink-ancestry/mass-deletion/branch-naming）补 fix 字段
- PR #3342 合并（4ecfd8ad）

实测三向：voice_memo grace exit=0 / 人为新违规 exit=1 / omo direct-io-baseline 清单恢复空。

## Q3. What changed during implementation?

本 BET 是**治理摩擦的活教材**，交付过程本身遭遇了分析报告里的四类死板问题：

1. **spec binding 五种报错**全靠试错学全（SPEC_REF_INVALID/FRONTMATTER_SCHEMA/STATUS/VERSION_MISMATCH/BET_MISMATCH）
2. **ledger 手术四轮**：裸冒号坑（第 4 次！）、复制粘贴污染 binding、插入锚点漂移——最终靠"条目整段捕获+内部清洗"的结构化方法收敛
3. **主线 force-push + 并行清理误删**：spec 文件与 ledger 条目被并行 doc 清理当作孤儿移除（但 ledger binding 留下 → main 自身 CI 红 → 我的修复 PR 反被这不一致 BLOCKED）——荒诞循环，最终 admin 合并恢复一致性
4. **PR 被并行 agent 误关**：CI 五红被判定为垃圾（实际是存量雷+并行雷叠加）
5. **PR #3342 的 spec 文件曾被 #3345 文档清理误删** → doc-governance invalid_metadata → 我的 PR 恰是修复

## Q4. Lessons (P73 truth-driven)

- **零依赖惯例要写进 CI 才能守住**：本地有 pyyaml 时测试全过，CI 裸环境才炸——环境差异型回归要在本地模拟 CI 环境（`uv run --no-project`）预演。
- **baseline 语义要先考古再设计**：direct-io-baseline 已有"清零压力缓冲区"语义（非空即 FAIL），我的"长期 grandfather"设计与它冲突，最终解耦为两个 SSOT 各司其职。
- **并行 agent 的清理工具会互伤**：文档清理把在途 PR 的 spec 当孤儿、worktree 清理把活跃工作面当僵尸——清理类工具应有"活跃 PR 引用保护"。
