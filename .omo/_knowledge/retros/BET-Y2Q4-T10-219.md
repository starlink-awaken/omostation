# BET-Y2Q4-T10-219 retro

四问结构。receipt：`docs/reports/2026-10-01-bet-219-system-yaml-field-writer-ownership-closeout.md`。

## 1 intended — 本来打算做什么

T10-220（把 `system.yaml` 的波动键抽进投影）的前置：让"每个顶层键的写者是谁"这件事
**可机器校验**，并把 `fields` 段与事实对齐。Appetite 0.5 day，
交付形态 = guard 新校验 + registry 重写 + 测试 + 一处注释改判据 + accepted spec + 台账。

## 2 happened — 实际发生了什么

交付形状按 spec 走完（7 条 verify 全 exit 0，11 例测试，`make gac-local-gate` PASS 68 checks）。
改变判断的是四件量出来的事：

**(a) "有声明"与"可校验"之间没有必然关系。** `fields` 段声明 14 个键，实有 23 个；
其中 8 个是幽灵，存在已久而**从来不会报错**——因为全仓对 `fields` 的消费者数是 **0**
（`write-owner-audit.py:54` 只取 `write_owners` 路径段）。一个没有读者的声明段，
和没有这一段等价，但它会让人以为已经有归属治理了。本轮的实质工作因此不是"补声明"，
而是**先给它造一个消费者**，再让声明追平事实。

**(b) 幽灵有两种，去留理由不能写成一句话。** 3 个 `debt_*` 键在全仓零引用；
4 个 `phase4x_status` 是被 `ALLOWED_FIELDS` 白名单**结构性挡死**（只放 `phase28_status`），
永远不会出现。前者是"历史遗留"，后者是"死条文"。另外 `next_milestone` 这类
"有条件才落盘"的键我**故意不声明**：提前声明就等于亲手废掉 `undeclared-key` 这条线，
将来它第一次真正出现时会静默通过。判据选择让它第一次落地即触雷。

**(c) guard 自己是 ADR-0456 的违规者。** 它用 `__file__` 反推根，而它检查的
`system.yaml` 正是写面。先修自己（写面 `state_root()` / 读面 `code_root()`），
否则在声明 profile 的机器上它校验的是一份**永远不会更新**的提交快照，
而真正的运行时文件在另一棵树里无人看管。这条由判据 4 用两条不同路径读数钉死，不靠措辞。

**(d) 我自己写的两条判据跑不通。** 第一次 `bet-ledger.py verify --execute` 就 exit 1：
判据 4 读 `json['system_yaml']`，而 guard 把它放在 `targets` 下 → 永远 `KeyError`；
判据 6/done_when-6 写"恰 6 项"，那是 receipt+retro 进 scope **之前**的草稿数（实为 8）。
被测对象没问题，**判据本身是坏的**，而我在立项时一次都没跑过它。

**(e) 文档自身的缺陷只在 `git add` 之后才现形。** 我把 spec 的 `owner` frontmatter 漏了，
而 `doc-governance-check.py --scope tracked` 在未跟踪时**报 PASS**（4530 files / 145 warnings），
`git add` 后同一命令报 `missing_frontmatter: owner` 并升级成
`unbaselined_warning [error]`。补一行就改内容，于是必须重算 spec 的 sha256 并回写台账绑定。

## 3 changed — 交付形态因此变了什么

1. 交付从"改 registry"变成"改 registry + 造消费者"：新校验塞进 `omo-state-write-guard.py`
   既有实现，靠 `gac-local-gate.py:218-223` 早已存在的 step 带响 ——
   于是同时满足 done_when-1（不新增 gate step、不动 `bin/` 净新增脚本配额）。
2. owner 词表从自由文本收敛为 `script:<repo-relative>` 等四前缀 + `anyone`，
   且 `script:` 者必须校验文件存在。这条把"写了个 owner"变成"这个 owner 指向真实代码"。
3. `generate-brief.py` 的注释经历两次改判：原文是"三个写者"（叙述），
   我先改成"实测 10 个入口"，**复算后是 8 个写者模块 / 34 条键-写者边**。
   最终形态不是换个数字，而是把注释改成"数字 + 复算命令"——
   枚举会烂，可复算的读数不会。
4. 台账 `verify` 两条判据在提交前修正（JSON 嵌套路径、8 项），`lint` 复跑 `OK — 514 bets, no errors`。
5. 顺带量出的 G-CONV.5 缺陷**没**顺手修：`m1-closeout-report.py:218` 找
   `bin/ssot/write-owner-repair-draft.py`，而脚本被 #1839 迁进 `bin/_archive/` 引用没跟。
   它不在本轮 write_surfaces 内，写成 receipt §5.1 的读数另立。

## 4 lessons — 下次直接可用的判据

- **接手任何"声明式 registry"之前，先量它的消费者数**：`rg <段名>` 找到读它的那一行，
  看它读的是哪一段。0 消费者的声明段 = 声明可与事实任意背离而不报错；
  给它补条目不产生任何治理效应，先造消费者才有。
- **判据落到台账之前必须跑一遍**（本轮两条：JSON 取错层级、项数过期）。
  坏判据的代价不是"少一条检查"，而是下一个人把它读成"交付有问题"从而回查一整轮。
  `bin/plan/bet-ledger.py verify <ID> --execute` 就是这条判据自己的测试。
- **要说某脚本"注册在案却从未被调用"，先按 basename 全库找它**（AGENTS.md §11 幽灵判定双检）。
  我原准备把 G-CONV.5 记成"第 5 次同类复发"，实测是 `bin/_archive/write-owner-repair-draft.py`
  **存在且 tracked**，只是被 #1839 迁走而引用没跟着改——类别从"从未接线"变成"迁走未改引用"，
  修法也不同（改一行路径 vs 决定这条链要不要活）。
- **有条件才出现的键，不要提前声明**，让 `undeclared-key` 当绊线；
  但要在 registry 注释里写明"为什么这里少一个"，否则下一个人会当成漏声明而补上，把绊线拆掉。
- **多写者同键就写列表**。`health_score`（3 个写者依次覆写）与 `updated_at`（3 个）
  若声明成单 owner，是把事实写错而不是简化；`anyone` 不是"多写者"的替代写法，
  它表示"不限制"，两者含义不同。
- **门禁类工具自己也在被检查的两个根上**：改双根时先跑 `--json` 打印它自己解析出的路径，
  确认写面随 profile、读面随检出，再去校验别人。
- **新建文档的治理检查要在 `git add` 之后跑**：`--scope tracked` 扫不到未跟踪文件，
  未跟踪时 `PASS` 不代表合规。而 `lifecycle: contract` 文档改一个字就是 **digest 事件** ——
  必须重算 sha256 并回写台账 `content_digest`，否则 `COMPLETION_FILE_DIGEST_MISMATCH`。
  照抄同目录已合并 accepted spec 的 frontmatter（本轮 T10-216/217 都有 `owner`，我漏了）。
- **一次瞬时探针比一段推断便宜**：注入键走 tmp、断言 exit 1 且违规类型正确，
  仓内跟踪文件不动——"新校验真的会响"这件事没有别的证法。
