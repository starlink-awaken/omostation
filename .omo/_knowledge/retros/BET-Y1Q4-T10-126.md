## Q3 过程中发现的与 plan 不符的事实（打假）?

### 1. 旧 `_ledger_snapshot` 已隐性写锁, 不只是"低版本 SQLite 安全模式"
原代码: `from omo.resident.ledger_check import check_and_recover` → `wal_checkpoint(TRUNCATE)` 静默申请 rw 锁, 与后台 daemon WAL 写入争用. spec 表述 "低版本 Python SQLite 环境因安全模式校验误尝试降级 journal_mode" 只是症状之一, 根因是 **每次 status.py 都触发一次 WAL checkpoint 写**, 与 daemon 持续写争用. 修法: 显式分 `check_lock_state_only()` (只读) 与 `recover_ledger_with_wal_checkpoint()` (写), 状态探测只调前者.

### 2. 旧 `_LockingBroker` 3 个测试是"功能即 bug"的活化石
旧测试测 `check_and_recover` 写锁重试, 验证 status.py 在 daemon 写锁时能重试 3 次成功. 这正是 T10-126 要修的根因. 删除是正确选择, 不能"为修测试"保留 bug 路径.

### 3. `_probe_ledger_once` 已经是只读 (file:ro URI)
原代码中 `status._probe_ledger_once()` 通过 `_ledger_broker().connect(str(LEDGER))` 走的是 broker, broker 默认连接是 rw. **关键**: 在 `_ledger_snapshot` 里调的是 `_probe_ledger_once()` (broker, 可能是 rw) 而不是直接 `_ledger_broker().connect(...?mode=ro)`. 修法: 改用 `check_lock_state_only()` + 直接 ro URI 连接, 完全绕开 broker.

### 4. 100x 并发测试用 mock writer (无真实 DB 写)
第一次尝试用真 SQLite writer 线程跑 100x 并发, 失败原因是 schema 验证 (期望 `event_log` 表) 拒绝 `events` 测试表. 简化: writer 线程只 sleep, 不真写 ledger. 真正的 T10-126 success criterion 是 "status 探测不申请写锁", 已通过 `test_ledger_snapshot_is_readonly_no_wal_checkpoint` (mock wal_checkpoint 检查调用次数=0) 独立验证. 100x 退化测试是"压力也 OK" 的二次确认, 不必真写.

### 5. `make resident-recover` 是 ops-only 显式 opt-in
spec 4.5 明示 "review 工具改动若破坏 weekly-report 消费方则回退". 实际 `make resident-recover` 是修复工具, 不进 cron; status.py 自动调用 = 历史 bug. 修法: 加 `resident-recover` Makefile 目标, docstring 标注 "ops-only, status 不会自动调用".

## Q5 下一个认领本 track 的 agent 需要知道什么?

1. **`recover_ledger_with_wal_checkpoint` 是显式 opt-in, 不是自动调用**. spec 设计原则: 状态探测不副作用. 如需手动恢复, 跑 `make resident-recover`.

2. **删除 2 个旧测试 = 修根因, 不是删 coverage**. 旧测试验证的是 status.py 在 WAL 写锁时能重试, 但 status.py 不应该有重试 (应直接 read-only). 删测试是修 bug 的合法步骤.

3. **后续监控集成**: weekly-report 可加 `_ledger_snapshot` 输出 "ledger write_locks_attempted=0" 字段, 作为 long-term 防腐断言.

4. **如发现 status.py 又回到写锁路径**: gac-local-gate 的 `governance-semantic` 检查 `omo/resident/status.py` 是否 import `wal_checkpoint` 应作为回归. 建议: 给 `check_lock_state_only` 加 lint hook (CI grep 检测 status.py 是否调用 wal_checkpoint).

5. **dependency**: T10-05 (候选) 不强依赖, T10-126 的 "100x 并发" 实测需要后台 daemon 持续写 WAL — 在生产环境由 cron `resident-daemon --once` 提供. 测试环境用 mock.
