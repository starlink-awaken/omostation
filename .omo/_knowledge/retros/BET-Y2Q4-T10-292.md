# BET-Y2Q4-T10-292 · A2A Path Lock Collision 谓词补锁过期判据

## 1. 本意（intended）

PITFALL-COO-008 记的是现象：一个 `status=active` 的他主 run，其 claim 路径上的锁早已过
TTL，仍能把我的 claim 挡成 `A2A Path Lock Collision`。本轮要把它变成仓库契约，四条硬要求：

1. 谓词从「对方 run `status == "active"`」改成「活跃 **且** 覆盖该重叠 claim 路径的锁
   未被证明过期」——即 `expires_at` 必须被正面证明还在未来，否则才构成冲突。
2. **fail-closed**：锁文件缺失、YAML 不可解析、payload 非 mapping、无 `expires_at`、
   时间戳不可解析或是 naive、无 `scope` —— 任一形状都算「不可证明」，一律仍判冲突。
3. **不复用** `_classify_existing_lock()` 的心跳陈旧规则：`expires_at`（锁 TTL，缺省 24 h）
   与 `last_heartbeat`（`_HEARTBEAT_STALE_SECONDS = 3600`）是两只独立的钟，
   `heartbeat_run()` 只续心跳不续锁，所以「锁过期 + run 仍 active」是常态而不是异常。
   把心跳面引进这个谓词，等于把「闲置一小时的活锁」判成可侵占。
4. 零回归，且判据承重（变异对照分别记读数），并在真实共享协调面上做一次实机 canary。

## 2. 实况（happened）

- 码面在 omo PR #238，squash 为 `af4ebdd1fe6323966c14dd78d59eb7f17731ba98`：新增
  `lock_scopes_past_expiry()`（`src/omo/workflow/lifecycle_locks.py`），
  `claim_run()` Phase 3 消费它（`src/omo/workflow/lifecycle.py:1411` 取集合，
  `:1442` 判 `f"path:{op}" in expired_lock_scopes`）。
- join key 用锁 payload 的 `scope` 原文，不用文件名：`_bounded_lock_name()` 对超过 255 字节的
  名字做截断 + sha256-12，按文件名对齐会把长路径的锁整个漏掉。
- `tests/test_workflow_locks.py` 38 → 54 passed（+16）。
- 变异对照三组读数互不相同，说明断言真的挂在被测形状上：
  - M1 只查 status（摘掉放行分支）→ 2 failed（两条正例）。
  - M2 改成 fail-open（不可证明即放行）→ 11 failed，其中多条是被
    `acquire_locks()` 的 `lock HELD (live)` 拦下的——第二道网也在起作用。
  - M3 复用 `_classify_existing_lock()` → 3 failed，并且该尺自己在
    `lifecycle_locks.py:88` 抛 `TypeError: can't compare offset-naive and offset-aware datetimes`。
    这条异常是「别复用它」的直接证据，不是本次测试的 bug。
- 实机 canary（真实共享协调面）：同一装置下先用 M1 复现缺陷原文
  （`A2A Path Lock Collision: path 'docs/plans/3y-bet-ledger.yaml' overlaps with active claim
  'docs/plans/3y-bet-ledger.yaml' in run 20261104T115230Z-project-code-change-d825f60f`，RC=2），
  再用交付代码放行（RC=0），他主 run 记录逐字节未动（sha256 `b98677b1b163…` 前后一致）。
- 独立尺 `observe --json`：基线 `4c662cdbb` 交付前 `expired_lock=7 / lock_count=7`；交付后该
  台账锁由本 run 以新 TTL 接管，读数变 `expired_lock=6 / lock_count=9`。据此把
  `verify[1].expect` 的口径改掉——原文要求的「交付后仍 7/7」按构造不可达。

## 3. 变更（changed）

- 协调面的准入语义现在有两层证据：锁层（`_classify_existing_lock` → `zombie_expired` →
  unlink 重建）与 run 记录层（本轮补的 `expires_at` 判据）。以前只有前者会放行，后者一票否决，
  两层互相矛盾时以「更保守的那层」为准，于是过期锁永远只是纸面上的放行。
- 验收尺的写法改了：`observe` 这类「读数会因自己的交付动作而改变」的判据，不能把交付后的
  具体数字写进 `expect`，只能写「两把尺对同一对象同向」，并把两次读数分别入收据。
- 登记面新增一个已测量、未处理的残余形状（见 §4.1）。

## 4. 教训（lessons）

### 4.1 放行是「一次性的」：自己的锁转正后，重放 claim 会被同一条陈旧记录再次挡住

canary 之后我用同一装置复跑了一次 claim，读数从 RC=0 变回 RC=2。原因不是回归，而是谓词的
证据结构：他主记录 `20261104T115230Z-project-code-change-d825f60f` 仍是 `status=active` 且
`claims[].paths` 含同一台账路径；而该 scope 上的锁此刻由**我自己的 run** 以 24 h TTL 持有
（`created_at 2026-11-07T00:04:39Z`，`expires_at 2026-11-08T00:04:39Z`），不在「已证明过期」集合里，
于是判冲突。

这个形状在改动前同样存在（改前是首次 claim 就被挡），所以本轮**没有引入新的失效**，但它说明
本轮只消除了 PITFALL-COO-008 的一半：谓词承认「锁过期」，还不承认「锁在我手里」。
按 A2A（agent-to-agent）的语义，锁的持有者就是发起方时，冲突对象并不存在。

不在本轮范围内处理，理由三条：本轮验收契约（spec 摘要已绑定在
`accepted_specifications[0].content_digest`）不含该形状；root CI 正对着 `af4ebdd` 这条 SHA 评审，
中途换码面会让在途评审失效；把放行条件从「过期」扩到「过期或被自己持有」需要正面回答
「他主 run 的 claim 与我持有的锁同时存在时谁让路」，这是另一次契约，不是一次补丁。
⇒ 后续 BET 承接：判据补 `lock_scopes_held_by(run_id)`，fail-closed 口径同本轮。

### 4.2 两只独立的钟不能互相替代

`heartbeat_run()` 只写 `last_heartbeat`（该不可变性由
`test_heartbeat_run_preserves_immutable_fields` 钉住），锁的 `expires_at` 只有
`acquire_locks()` 会写。所以任何「用心跳推锁状态」的写法都是在替别人做决定；
M3 的读数（3 failed + 该尺自身 naive/aware 比较异常）就是这条的实测代价。

### 4.3 一次性 Bash 命令里的 alias 面仍会咬人

本轮再次踩到 `cp → cp -iv`（对已存在文件打印 `not overwritten` 且 rc=1，`&&` 短路后
「M2 读数」实际是 M1 的重复测量）与 `grep → rg`（`-rln` 零命中、`-E` 被读成编码）。
处置一律改成 Python `read → replace → write` 并由脚本自己断言「目标形状存在/不存在」，
变异前后各打一次特征串读数——这是 §7「判据报警先 print 原始行」在变异流程里的具体形态。

### 4.4 验收尺的自我指涉

`verify[1]` 用 `observe` 作为独立尺，但我的交付动作本身会改变它的读数（台账锁易主）。
一把尺的读数被被测动作改写时，`expect` 必须写成不变式（两把尺同向），而不是写成
某个具体数字；否则「交付成功」与「判据失败」会同时成立，只能靠事后改文书解决。
