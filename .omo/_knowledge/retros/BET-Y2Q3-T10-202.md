# BET-Y2Q3-T10-202 retrospective

## Q1. What was intended?

修掉 ADR-0443 事故→规则管道的两个断头，让它们声称的闭环真的闭合：

1. **队列耐久性（G1–G4）**：`.omo/_delivery/rule-drafts/` 入仓、晋升有独立扫描入口
   （`promote-drafts`）、`stats`/`check` 报出逾期缺口（不改 `check` 退出码）、
   `feed_from_escapes` 不再跨类别给 `times_encountered` 加分。
2. **start 门对称豁免（G5，principal 明确纳入范围）**：`chain_bind.start_requires_bet`
   对治理演进 workflow 采用与 `evaluate_closeout` 完全相同的豁免谓词，
   从根因上消灭 70 条 `AGCP_REQUIREMENT_ITERATION_GATE=0` 豁免的需求。

约束：零 gate 豁免、零 waiver 文件、草案只能由 promoter 本身生成、不碰
`governance-checks.yaml`、不改共享门禁退出码。

## Q2. What happened?

两条目标都达成，且全部由实测驱动：

- 队列从"目录不存在"变成 3 份入库草案（`CR-PITFALL-COO-003` / `-GAT-004` / `-GAT-005`），
  `promote-drafts` 幂等（第二次 `created: []`），`stats` 报 `overdue_rule_drafts: []`。
- `check` 退出码与 `origin/main` 版本在同一份库上逐字段对拍：两者 `exit=0`、`problems` 相同，
  新实现只多一个只读 `rule_drafts` 段落。
- G5 后 `bin/plan/chain-bind-check.py self-check` 13 个 fixture 全绿，
  `tests/test_chain_bind.py` + `tests/unit/gac/test_chain_bind_start_gate.py` +
  `tests/unit/gac/test_error_knowledge_rule_drafts.py` + `test_error_knowledge_recall.py` 合计 37 passed
  （I8 收敛两道锁时新增 3 条：AST 对拍两份白名单 + 两条参数化的"草案可提交 / `_delivery` 其余路径仍被拦"）。
- 本交付 `start` 绑定真实 bet、未设任何 `AGCP_*` env、未新增 waiver 文件。

## Q3. What changed during implementation?

三处初始假设被实测推翻，都回写了 spec（不藏）：

1. **spec 说"两个调用点各自传 workspace"** —— 实测两个调用点都从 `<root>/bin/plan/chain_bind.py`
   动态加载，`DEFAULT_WORKSPACE = Path(__file__).resolve().parents[2]` 已经天然拿到正确工作树，
   调用点无需改动；`projects/omo` 侧还是子模块，不该由主仓交付顺手改。
2. **契约反转的落点比预想多两处** —— `chain-bind-check.py self-check` 与 `tests/test_chain_bind.py`
   原本**故意**钉住"start 更严"的旧契约。只改 `chain_bind.py` 会让 13 个 fixture 直接红。
   代价：`write_surfaces` 从 11 扩到 15，而 `refresh-packet` 对"自己改台账的 bet"结构不可用
   （它拿工作区字节比 `origin/main`）→ 只能把 run `20260924T233640Z-…-61f70aad` 以 `failed`
   关闭并注明替代关系，重开 `20260924T234703Z-…-19edbaca` 才能合法 claim（发现 I7）。
3. **`check --json` 被我的"只读报告"打断** —— 追加的人读提示行混进 JSON 之后，
   `gac-local-gate` 的解析会炸。测试先失败、随后把提示限定在非 `--json` 分支。
   "只读报告"和"不污染 stdout 契约"是两件事，后者才是真约束。

另有一项原计划"只登记不修改"的改为随 G5 一并做掉：`bin/agent-workflow.py` 的 start 拦截提示
只列 `observer-audit` 与 ENV 豁免 —— G5 之后留着，等于把下一个 agent 又推回去签豁免。

## Q4. Lessons

- **"门的不对称"要用 waiver 计数来定价**，而不是用感觉。136 份 waiver 里 70 份是同一行 env，
  这个数字比任何形容词都更清楚地说明了 `start` 与 `closeout` 为什么必须同一条谓词。
- **豁免只能沿用已经存在的那一条**，不能新写一条更宽的。G5 的价值不在于"放行变多"，
  而在于两个门现在可以被同一份测试同时钉住（`test_start_and_closeout_agree_on_the_exempt_set`）。
- **管道的缺陷常在末端**：阈值、匹配、记录都工作了一年，而产物落在一个被 gitignore 的目录里、
  且没有任何地方报"该有而没有"。加一个 `overdue` 报告比加新机制便宜得多。
- **死掉的 CLI 面比缺功能更坏**：`confirm`/`reject` 有解析器、没 handler、exit 0，
  任何脚本都会以为草案被人审处置过了。显式 `NOT_IMPLEMENTED` 退 2 才是诚实的。
- **自指型 bet（改台账的 bet）必须一次算全改动面**，因为 refresh 路径对它结构不可用。
  这条已经写进 spec 验收第 6 条，也是 I7 交给 principal 的决策点。
- **同一个故障可能有两道互不相识的锁**。`rule-drafts/` 看不见的最初诊断是"被 gitignore"，
  改完 `.gitignore` 后 commit 仍被拦：`check-runtime-artifacts.py` 另有一份 `.omo/_delivery/`
  黑名单。而它的 `WHITELIST_PREFIXES` 早就为三个同构目录存在——那三个目录能入仓从来不只靠
  `.gitignore`。报"入仓"时要报全部锁，修一处等于没修（I8）。
- **packet 把 spec digest 当冻结输入**，所以活文档型交付的合法顺序是
  「spec 定稿 → 台账 digest → start → 之后只改代码」。start 之后再动 spec 一个标点，
  全部 claim 都会被 `WORK_PACKET_SOURCE_DRIFT` 拒绝，重开 run 没有第二条路（I7 第二型）。
- **台账的 `meta.total_bets` 是派生值，冲突"没报"就是它说谎的方式**。rebase 时 `bets` 尾部两侧
  各插一条（main 的 `BET-Y2Q3-T9-01` 与本 bet）冲突，而 `total_bets` 双方写的都是 `459`
  （各自从 458 加一）→ git 判定同一处同一改，合并后实际 460 条、声明 459 条，且没有任何残留标记。
  判据只能是"按合并后的事实重算并断言 `len(bets) == total_bets`"，不是"有没有 CONFLICT 行"（I9）。
- **留给 principal 的没有动**：`>=3` 词阈值、`PITFALL-GAT-004` 的证据质量（symptom 是一段
  `[PASS]` 日志、标题写 `(8x)` 而计数 46、`last_confirmed` 停在 2026-08-30）、run record 是否入仓、
  H2 的 pre-rebase 冲突、I1 的 closeout `ok` 语义、30 条价值记录、weekly-review。
