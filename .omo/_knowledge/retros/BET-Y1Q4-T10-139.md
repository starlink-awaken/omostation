# Retro — BET-Y1Q4-T10-139: BET 认领广播 (同号竞速防护)

- status: done (PR #3405 + #3408)
- window: Y1Q4 · track: T10-MATURITY · completed: 2026-09-08

## 问题 (根因复盘)

三起同号竞速事故 (T10-135/136/137/138 cycle) 的共同根源：**BET 状态 (ledger) 与
执行意图 (start) 之间没有认领层**。多个并行 agent 同时看到 candidate →
都 start → 都交付 → 合并互相覆盖/重新编号 (4 轮 PR 浪费)。

关键洞察 (用户 2026-09-07 提问触发): `.omo/` 是 gitignored — 每个 worktree 的
`.omo/` 是独立物理目录，**互相不可见**。三起事故的现场是各 agent 的独立
worktree，所以认领广播必须落**共享物理位置**才防得住真实场景。

## 方案 (方案 A — git-common-dir 锚定主 checkout)

- `git rev-parse --git-common-dir` 从任何 worktree 恒解析到主仓 `.git`，其父
  目录即主 checkout —— claim 统一落主 checkout 的 `.omo/_delivery/bet-claims/`
- 解析失败回退当前 checkout (宽容, 防御层不成为新单点)
- 双侧 (bet-ledger.py 与 agent-workflow.py) 同源逻辑 (`_delivery_claims_root`)

## 四件套交付

1. **claim-bet 子命令**: 广播文件 (actor/claimed_at/ttl) + `save_ledger_locked`
   锁内 candidate→in_progress; 异 actor fail closed; 同 actor 幂等; --force 接管
2. **claim-gc**: 7d TTL; 只删文件不动 ledger status
3. **start 拦截** (`_claim_interlock_guard`): 他人持有 → BET_CLAIM_HELD fail
   closed; 无广播/本人/损坏 → 放行
4. **complete 自动释放** (`_release_claim`): done 置位后删 claim 文件

## 实战验证 (dogfood)

- 本 BET 自身用 claim-bet 认领 → 并行 agent 主 checkout 被切到别的分支后
  claim 文件依然可见 (共享锚点实测跨分支存活)
- 异 actor start 被 BET_CLAIM_HELD 实测拦截 (exit=1)
- 战损: T10-139 实现被并行 reset 吃过 3 次 (16:42-17:02 四连 reset +
  17:07:43 刀落在 commit 之后) — 最终靠「reflog 保活 + 重开 v2 分支 + 立即
  commit + 远端 push 物理锁」落地
- 期间修复流程自锁: claim 置 in_progress 后 STARTABLE 拒之 → 流程死锁;
  修法: STARTABLE_BET_STATUSES 加 in_progress (认领者 start 是流程正门)

## 避坑沉淀

1. **claim 广播的落点必须是共享物理根** — gitignored 目录在 worktree 间互盲
   (根因级修复, 用户提问触发洞察)
2. **防御层的失败语义要选对**: 写入侧 fail closed (防误接管), 读取侧宽容
   (防防御层成单点) — guard 异常只警告不阻断
3. **未提交改动活不过 reset 窗口**: 观测 5 次 reset 吞掉实施中的代码; 「做完
   一块立即 commit + push」是唯一可靠节奏
4. **认领语义与 start 状态机对齐**: 认领导致的 status 变化 (in_progress)
   不能把 start 反锁 — 这类自锁需在 spec 阶段推演
5. **shell 管道 exit code 陷阱**: `cmd | head` 吃掉退出码 (艹, 这坑老王也踩),
   验证 fail-closed 必须显式 `echo $?`
6. **untracked 文件活不过清理器**: retro 文件写完没 commit 就被 hygiene 清理
   吃掉一次 — 写完立即 add+commit
