# BET-Y2Q4-T10-257 retro — 让 runs 面的读法不再取决于「这个检出跑没跑过 workflow」

台账：`docs/plans/3y-bet-ledger.yaml` `BET-Y2Q4-T10-257`
规格：`docs/superpowers/specs/2026-10-19-chain-bind-runs-anchor-seam.md`（spec_version 1.1.0，
digest `sha256:18ef9a0e…`；v1.0.0 的 digest 是 `sha256:56f47576…`，被第二面推翻后修订）
PR：#4817（分支 `agent/governance-agent/t10-257-chainbind-seam`，commit `caa00807d` + `1822f2c89`）
性质：ADR-0456 读面缝的一条**缺陷修复**。不动缝本体、不动 launchd、**不宣布 B1/B3/B4/B5 或 plan 完成**。

## 1 intended — 本来打算做什么

`bin/plan/chain_bind.py:37` 定义 `RUNS_REL = ".omo/_delivery/agent-workflows/runs"`、`:189`
直接 `workspace / RUNS_REL` 读 runs 面。runs 面是全机共享面，每个检出的
`.omo/_delivery/agent-workflows/` 由 `ensure_delivery_anchor()`
（`projects/omo/src/omo/workflow/delivery_anchor.py:117`）做成指向 canonical 的 symlink，
而**桥是惰性建的** —— 唯一生产调用点是 `omo/workflow/core.py:457` 的 `_runner_path()`，
只有在**该检出内**跑过 workflow 状态类操作才建。

立项现场：run `20261019T015151Z-bet-execution-8fb82293` 真实存在、`bet_id` 已绑、status active、
5 条 scope lock 均在；在无桥收口 worktree 里跑 `bet-ledger.py complete BET-Y2Q4-T10-253`
却报 `missing_bet_binding`。理想态四条：① 无桥检出读到 canonical 的 run；
② 缝摘掉 ⇒ 与改前逐字节相同（CI 干净检出、fresh clone 的行为是硬约束）；
③ 读侧不写检出（不调 `ensure_delivery_anchor()`）；④ 判据既有正向也有反向对照，且检测器自证。

## 2 happened — 实际发生了什么

**第一版绿了，但生产路径上什么都没发生。** commit `caa00807d` 的缝写成
`from omo.workflow.delivery_anchor import locate_anchor, is_worktree_of`，六条用例全绿。
合并前我做了一次**真装置**复测：bare `python3` 里 `import omo.workflow.delivery_anchor`
→ `ModuleNotFoundError`。原因不在我的探针，而在**生产调用本身** ——
`bet-ledger.py` 只把 `projects/ecos/src`（`:2110`、`:2132`）和 `bin/plan`（`:3310`）
放进 `sys.path`，`chain_bind.py` 自己没有 bootstrap。于是那条出问题的调用里，
import 抛异常、被我自己的降级分支吃掉、读数仍是 0 个 run：**改动接了，但没接上**，
而且**没有任何测试会红**（我的 fixture 用 `_install_seam()` 把库注册进 `sys.modules`，
正好把生产缺的那一半补上了）。

修法不是复制定位语义，而是**按文件路径加载同一份缝本体**：候选依次是「跑这段代码的检出」
（`DEFAULT_WORKSPACE`）和「被查询的检出」（`workspace` 参数），两者都没有那份文件时才退回本地面。
C2 因此收窄 —— 退回条件从「库不可 import」变成「那份 `delivery_anchor.py` 也不可达」，
前者现在是**要修的形状**，不再是退回的形状。

**覆盖面读数当天就变了，所以判据不写名字。** 立项时记「10 个检出：5 有桥 / 4 无 agent-workflows / 1 canonical」；
收口当天复测「带 `MARKER` 的 9 个检出：6 有桥 / 3 无桥」。差额是并发会话在这几小时里 claim/release 造成的，
不是我的改动。三个无桥检出（`ws-lifeos-magpie-foundation` / `ws-resident-phase11-multimodal` / `ws-task-c64652`）
在 bare `python3` 下改前各读 **0** 个 run、改后各读 **331** 个，全部解析到
`/Users/xiamingxing/Workspace/.omo/_delivery/agent-workflows/runs`。

**绿不绿由变异对照说，不由装置说。** 把 `chain_bind.py` 换成 `git show HEAD:` 的改前版本 ⇒
`1 failed / 7 passed`，红的恰是新增的 ISC-7 正向用例；换回后 sha256 前缀 `d1c56ee2e7c6`、
按路径加载分支在场。ISC-4 的文本判据仍由同一次 AST 扫描同时产出「改前 1 处 / 改后 0 处」，
并在合成违规行上命中 `[1]`，防检测器空转。

**`make gac-local-gate` 的「绿」在本基线不可满足。** v1.0.0 §4 写了这句，实测本机 gate 有一组
与本轮无关的既有硬失败（launchd / 投影面）。判据改成「**硬失败集合等于基线（零新增）**」，
与台账 `done_when` ISC-6 同文 —— 改的是判据措辞，不是被断言的对象。

## 4 lessons — 固化什么

1. **import-only 缝在 `omo` 不在 `sys.path` 的调用里是惰性的：判据要钉生产解释器形状，不是 fixture 形状。**
   测试装置里为了让 import 可用而做的任何注册，都会恰好掩盖「生产里没有」这一半。
   反面同构：本轮之前 `chain_bind` 无 `sys.path` bootstrap，而 `bet-ledger.py` 只加自己需要的两条 ——
   一个被间接 import 的模块不能假设调用方给了依赖面。
2. **每条"能读到共享面"的修复都要跑一次真装置（bare `python3`，无 venv）计数**，
   并在同一台机器上给出改前/改后两个读数；只有 venv 读数的「绿」不构成交付证据。
3. **覆盖面类数字必须写成形状而不是名单**（检出集合随并发会话变动，当天就会差 1–2 个）。
4. **判据若在本基线不可满足（`gac-local-gate` 恒有既有硬失败），改措辞为「集合等于基线、零新增」**，
   别把 gate 的既有红当作自己引入的回归，也别偷偷删断言。
5. `git push … 2>&1 | tail -8` 会因管道broken把真实失败吞成 exit 0（本轮撞了一次）：
   推送一律重定向到文件 + 显式 `echo PUSH_RC=$?` + `git ls-remote` 回读 ref。
