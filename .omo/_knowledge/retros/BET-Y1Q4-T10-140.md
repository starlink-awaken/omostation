## 问题

T10-139 交付期间观测 7 次并行 reset/prune 吃掉未推 commit（含刀落 commit
后的案例）。三个清理器的删除判定只有 dirty-skip / open-PR（部分工具），
未推 commit 与活跃工作面无任何保护——`git branch -D` 后 commit 只靠
reflog 90 天保活，跨会话不可靠。

## 交付

**共享 guard**（`lib/cleanup-guard.py`，DRY 三清理器同一实现）：

1. `unpushed` — 未推远端 commit（含远端无同名分支 = 全本地场景）
2. `open-pr` — gh open PR（查询失败宽容放行）
3. `bet-claimed` — T10-139 认领广播联动：活跃 bet_id 出现在分支名

接入：branch-ttl-gate（enforce 全查）、prune-zombie（worktree 删但受保护
分支保留）、gac-branch-prune.sh（work+agent 段 CLI 契约 exit 0/1）。

## 关键决策与发现

1. **数据源现实修正**: 立项 done_when 写"活跃 run 分支"，勘察发现 run
   文件无 branch 字段（无数据源）→ 修正为"活跃认领 BET 分支"（T10-139
   广播现成数据源）。**立项时的保护维度若数据源不存在，落地前必须修正
   而非硬造数据源**。
2. **匹配双形态**: 全 id（BET-Y1Q4-T10-139）与尾段短 id（t10-139，真实
   命名惯例 work/t10-139-xxx）都匹配；短 id 带边界（`-t10-139-`）防
   相邻编号误伤（T10-13 ≠ T10-139）——测试先行暴露了这个真实缺口
   （初版全 id 子串匹配对惯例分支名全部漏防）。
3. **失败语义沿 T10-139 哲学**: guard 故障宽容放行 + 警告——防御层不
   成为清理流程新单点。
4. **保护优先级**: unpushed 先于 open-pr 先于 bet-claimed（最便宜的
   本地 git 查询最先，网络 gh 查询其次，缓存 claims 最后）。
