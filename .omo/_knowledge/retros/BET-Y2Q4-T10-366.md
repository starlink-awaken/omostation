# Retro — BET-Y2Q4-T10-366

## 1. 意图（intended）

`BET-Y2Q4-T10-365` 把「采集器字节 == 生产者代码根 HEAD 字节」补进了发布器,
但它的复盘 §4 留了一条尾巴: **「同一半边契约可能在别处重演」**。

本轮把那半边契约落到**运行期的另一半** —— live server 自己的身份自校验:

- live server 的 `CODE_ROOT` 在 **import 时**解析 (`runtime_paths.py.asset:17`
  的 `Path(__file__).resolve().parent`) ⇒ 进程一旦启动就钉死在当时的 release;
- 投影 revision 的绑定来自**采集器当时看到的 `current` 软链** ⇒ 每次发布换一个
  `commit_oid`, 两侧必然不等 ⇒ `CODE_DRIFT` ⇒ 静态资源 503;
- 而 `publish()` 只做「切指针 + SHA 校验」, **从不读运行态** ⇒ 返回 `ok: true`
  而驾驶舱整站只读, 恢复只靠人工重启 (`T10-364` 回执 §5 实测)。

本轮三件事: ① 切换 `current` 之前先取两侧身份并做三态判定;
② 绑定将被破坏时由**发布器自己**完成重绑定 (kick 采集器刷新 + 重启 live server)
并**验收收敛**, 不收敛即回滚; ③ 判据有正反用例, 且接线钉在真实 `publish()` /
`restore()` 入口上。

## 3. 差距与坑（learned）

1. **指针切换不是发布事务的终点**。`current` 软链只是一个指针; 真正被用户感知的
   「发布」是「指针 + 投影 revision + 运行中进程」三者一致。发布器此前把前者当成了
   全部 —— 契约缺口不在检查层, 在**事务边界**: 检查做完了, 事务没做完。
   **纪律**: 发布器要问的不是「字节拷对了没有」, 而是「切完之后系统还可用吗」。
2. **身份自校验是 import 时求值的冻结值**。`SERVER_CODE_SHA256` /
   `CODE_BUNDLE_SHA256` 全部在 import 时算出来 ⇒ 进程**不可能**自己感知到
   指针已经变了。指望运行中的服务自愈是错的; 唯一的收敛手段是**重启**。
   **纪律**: 任何「进程启动时解析出身份」的组件, 其发布面都必须带一次重绑定动作。
3. **恢复链对只读态是瞎的**。宿主看门狗探针是 `curl -s -o /dev/null` (缺 `--fail`),
   HTTP 503 的退出码仍是 0 ⇒ 只读被判定为「活着」⇒ 分级恢复链从不触发。
   ⇒ **503 形态的故障不会自愈**, 只能由发布事务自己闭环 (跨仓残留已登记)。
4. **不可观测 ≠ 不通过, 但「不可观测」也不能被当成「安全」**。本轮把判定做成三态:
   绑定保持 / 绑定将被破坏 / 不可观测。前两态要有动作, 第三态**跳过而不阻断**
   (沿用 T10-365 同源纪律); 但当「绑定将被破坏」且**协调通道也不可用**时,
   判据必须**拒绝发布** —— 宁可不发, 不可发到只读态。
5. **接线钉子必须走真实入口**。核心用例走的是**真实 `publish()` / `restore()`**,
   沿用 T10-364 / T10-365 的教训 (「测试绕过接线就钉不住接线」)。
6. **台账轴状态有取值域**: 起草态 `IN_PROGRESS` + `overall_state: evaluating`,
   收口时改 `VERIFIED` / `PROVEN` + `delivery_accepted`; `done_when` 里带 `: `
   的条目要加引号或改写, 否则被解析成 dict (本轮台账条目起草时踩到)。
