# BET-Y2Q4-T10-247 retro — 三个"绿"都不是证据的时刻

台账：`docs/plans/3y-bet-ledger.yaml` `BET-Y2Q4-T10-247`
规格：`docs/superpowers/specs/2026-10-12-projection-fullrefresh-ledger-root-seam.md`（spec_version 1.0.0）
Receipt：`docs/reports/2026-10-12-projection-fullrefresh-ledger-root-seam-closeout.md`
交付：PR #4736 → squash `df9457d1d`（2026-10-13，无 admin、无 `--no-verify`、无 `--force`；push 前 L3 深度安全审查未发现安全问题）
性质：ADR-0456 **B4b 批次 2+ 的前置** —— 把 projection-full-refresh 这个写者从"import 时定根"改成"调用时定根"，否则批次切换后它会继续往检出写。

## 1 intended — 本来打算做什么

`bin/panorama/projection-full-refresh.py` 的 ledger 目标在 import 时由模块级常量求值。
profile 晚声明 ⇒ 常量冻结在声明前的根 ⇒ 投影写进检出而不是 state 根，且没有任何测试会红。
这与 `bin/compass_radar.py:482` 不传 `env=` 那条沉默契约同族。

理想态四条同时可证：① 写路径在调用时刻经 canonical 缝解析；② 缺副本时不凭空建半份镜像；
③ 正向落点断言（投影真的出现在 state 根）而非"检出没脏"这种单面否定；④ 台账 verify 的每条期望
由**被测真树**产出。

## 2 happened — 实际发生了什么

三个"绿"当场被否证：

**其一：ISC-7 的活线读数来自合成树。** 评审过的备份条目里 `done_when` 的 ISC-7 用一棵 `/tmp` 合成树
测 resolver 面。合成树没有真检出的跟踪面，读数与真树不同。修正后必须在被测真树复测，
`content_digest` 随 spec 改动重算 —— 这是一次**故意的**内容变更，不是工具偷偷改的。

**其二：verify 期望"全绿 exit 0"按构造不可满足。** 原期望把两个文件合成一条命令，
且"全绿"的读数取自合成树。在真树上 `tests/unit/test_resident_write_plane_split.py` 必有 4 条红
（`origin/main` 上 `CALLER_EVIDENCE` / `SPLIT_EXACT` / `STATE_FAMILIES` 这几份在册名单
相对真跟踪面结构性陈旧：`bin/_archive/**` 175 个 py、`bin/ssot/**` 228、`bin/kb/**` 3、
`bin/gac/m1-closeout-report.py`、5 份 `.omo/_knowledge/*.jsonl` 里的 omo 字面量）。
拆成逐文件实测读数后，那条的期望改成**非回退对拍**：HEAD `5 failed / 16 passed` →
本版 `4 failed / 20 passed`，NEW_RED = `[]`，本版红集合 ⊆ HEAD 红集合。

**其三：门禁第三条 FAIL 是宿主读数，不是仓库读数。** `make gac-local-gate` 首跑 3 FAIL，
其中 `check-evidence-freshness` TIMEOUT。计时定性：`evidence-smoke.py` 直跑 **196.95s**，
而 `check-evidence-freshness.py:61-76` 里写死 `timeout=60`；warm 后该检查 6.15s PASS
（score=100.0, age=0d），二跑 gate 内该条转 PASS。P75 的 D8 说的就是这个面。
硬失败集因此是 **2** 条，且这 2 条在**规范检出** `~/Workspace` 上跑同两条命令的读数**逐字节相同**
（08:46Z / 08:52Z 双树对拍）；再加一层按构造归因：`gen-service-configs.py` 的 `--check`
解析 `canonical_root()`，它读不到我的 worktree。

## 4 lessons — 固化什么

1. **一条合同期望必须由被测树产出。** 拿 `/tmp` 合成树的读数写进 verify，等于在交付那一刻
   造一条按构造不可满足的判据 —— 它不会报错，只会在下次执行时红，并且红得像代码回归。
2. **"全绿"是两个文件粘一条命令时的假象。** 期望要逐文件写，否则一个文件的预存红
   会遮蔽另一个文件的新增绿，非回退性无从判定。
3. **门禁的 timeout / 阈值是宿主读数。** 出现 TIMEOUT 先计时直跑被测脚本再定性；
   `-1`/timeout ≠ fail，不得据此放宽门禁或登记债。
4. **"硬失败集不得新增"要靠双树逐字节对拍证明**，不是靠"我记得 main 也红"。
   再加一层按构造归因（读的是哪棵树）比读数对比更硬。
5. **新建 BET 的台账定稿顺序是结构问题不是操作问题**：`start` 之后再改台账里投影字段
   （`verify` / `done_when` / `scope`）会永久挡住该 run 剩余 `write_surfaces` 的 claim
   （`WORK_PACKET_SOURCE_DRIFT`），而 `refresh-packet` 要求 ledger+spec 已在 `origin/main`，
   新建 BET 首轮用不上 —— 两边互锁。本轮靠"retro/receipt 本就可在未 claim 状态下提交"绕过，
   没有动 `prune-locks`，也没有用 `SWARM_ESCAPE_ID`。
6. **`tests/unit/**` 不在 `governance-check.yml:118-127` 显式白名单里**，所以这批用例的
   唯一证据是本地 receipt；"CI 绿"不构成它们的证据，反之亦然。
7. **自证类探针的基线不能是可变的 HEAD。** 台账完整性探针比对"工作树 vs HEAD"，
   commit 之后 HEAD 就含本 BET 条目，`added` 从 `[BET-Y2Q4-T10-247]` 静默变成 `[]` ——
   判据在同一棵树上失去了对象。本轮把它改成比对**记录的交付前 base**（`BASE_REF=6d01f51ce`），
   commit 后重跑才又有了牙。反面教训：如果当初把断言写成"新增恰为这一条**或为空**"，
   这条探针会在交付那一刻起结构性空绿。
8. **远端写操作返回错误时，先读状态再重试。** `gh pr merge --squash` 第一次以
   `TLS handshake timeout` 失败（rc=1），**服务端是否已合并是未知的**。判据不是直接重试，
   而是先读 `gh pr view --json state,mergedAt,mergeCommit`：确认 `OPEN/mergedAt=null` 才重试，
   否则重复一次 squash 会造出第二个合并。同一形状适用于 push、release、部署。
