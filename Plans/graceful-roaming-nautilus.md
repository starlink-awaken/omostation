# SwiftBar 菜单栏整体治理与迭代规划

## Context
菜单栏是 Hub v2（`~/.config/menubar/hub.30s.sh`）聚合 5 个域：代理 / 网络 / 算力 / 路由 / 工程。
脚本合计约 1500 行，展开后单域 25~150 行，算力域一级菜单就有 16 项。
用户反馈：内容杂，关键信息不突出。勘察后确认这不只是排版问题，还有**健康判定缺陷**和**一个域直接坏了**，所以先修真相，再改版式。

## 目标设计：三层信息架构

1. **菜单栏标题（L0）**：只显示"最差域"。全绿时 `●` 一个点；有异常时 `🔴路由 🟠网络`，只列异常域，带名字缩写，不再 5 个点加数字。
2. **Hub 顶层（L1）**：
   - 顶部新增 **「需要关注」块**：汇总所有域的 🔴/🟠 告警，最多 5 行，每行带域名和一键动作。全绿时显示"一切正常"一行。
   - 其后每域一行摘要（图标 名称 状态点 关键数 + 一句高亮），按重要度排序：算力、代理、路由、网络、工程。
   - 末尾只保留一个「全部刷新」。
3. **域子菜单（L2）**：统一为「状态 / 操作 / 详情」三组，详情默认折叠，**菜单深度≤3 级**。

**统一告警约定（KISS，沿用现有文本约定）**：域脚本把需要关注的行以 `⚠ ` 或 `🔴 ` 开头输出，Hub 扫描 body 收集。ai-stack 与 omlxc 面板已在用这个写法，不引入新数据层。

## 分阶段落地

### P0 修真相（先做，纯修复，不改版式）
- B1：`ai-route.sh` 改用解析后的真实路径（`readlink -f`，验证 macOS 版本支持，否则用 `python3 -c realpath`）。
- B2：路由标题色/指标改为由采集器状态推导（错误数、额度、数据新鲜度），去掉硬编码。
- B3：代理域补红色条件：关键链路红、云机掉线、证书红、配额>90%、云机负载>85%；`errors=?` 记为未知（灰）而非绿；橙色阈值从"一半节点可用"收紧。
- B4：网络域过滤无害 Health 提示，peer 离线计入橙。
- B5：工程域简报陈旧>N 分钟变橙；`gates_total=0` 记为未知。
- B6：Hub 用线程池并行采集 5 个域，单域超时降到 10s。
- B7：基准段在无真实数据（多行完全相同）时隐藏，不展示假数据。
- B9：删除 Hub 中 ai-quota 的死引用。
- 涉及文件：`hub.30s.sh`、`parts/ai-route.sh`（及 `local-ops` 里的真身）、`parts/engineering.sh`、`clash/repo/swiftbar/proxy-fleet.30s.sh`、`tailscale.5s.sh`、`parts/ai-compute-deep.sh`。

### P1 Hub 重构（解决"关键信息不突出"）
- 新增「需要关注」汇总块和新的 L0 标题规则（见目标设计）。
- 渲染子菜单时去掉各域自带的"刷新/更新时间"行，只保留 Hub 一个刷新入口。
- 各域按"最差优先"自动展开：有告警的域在顶层多显示一行最紧急告警。

### P2 各域瘦身
- **算力域（16 个一级项 → 约 6 个）**：合并「模型+KV+电源」为「内存与模型」；「门面+自愈」合为一组；「别名+能力」合为一组；「工具」并入「快捷入口」；omlxc 折叠段与本域已有的节点/服务重复部分去重；深挖段并入对应分组而不是再套一层折叠，并去掉静态说明文字和硬编码的 embeddinggemma 提示（改为按真实注册状态动态显示）。
- **代理域**：去掉硬编码 DERP 行；带宽守护 14 行仅在降级时展开；Tailscale 相关展示只留网络域。
- **网络域**：peer 列表折叠成子菜单，顶层只保留中继延迟和异常。
- **路由域**：66 行手动切换按钮收进一个「手动切换」折叠子菜单；删除免责声明和"未知"占位行。
- **工程域**：结构已较精简，仅补陈旧与缺失数据提示。

### P3 防回退
- 新增 `bar-lint`（放在 `~/.config/menubar/`）：逐域限时渲染并断言：输出非空、首行格式合法、菜单深度≤3、一级项数量上限、告警行格式、单域渲染耗时；Hub 总耗时需<10s。
- 在 `ai-compute-deep.sh` 等自写脚本头部保持 PATH 自给的约定。

## 风险与注意
- **文件归属**：`parts/ai-route.sh` 是指向 `~/local-ops/config/menubar/parts/` 的符号链接，`ai-route-collect.py`（1478 行）也在那里。改动前要确认 `local-ops` 是否是带版本控制/由 magpie 同步的仓库，避免被覆盖；我新增的 `ai-compute-deep.sh` 目前只在 `~/.config/menubar/parts/`，如该目录不被同步需一并纳入。
- 菜单栏是用户每天都看的界面，每个阶段改完先用脚本渲染验证，再让 SwiftBar 刷新，坏了可回滚（改前备份到 `~/.config/menubar/.bak-20261009/`）。
- 不 commit、不 push，除非用户另行要求。

## 验证
1. P0：逐域 `bash <域脚本> | head` 看输出非空；路由域首行有真实状态而非 `?`/橙色硬编码；人为制造一次异常（如临时改阈值或读取假数据）确认标题变色。
2. P0-B6：`time bash hub.30s.sh` 总耗时较改前下降，目标<10s。
3. P1：渲染 Hub 输出，检查「需要关注」块、标题只列异常域、全绿时的"一切正常"形态；在 SwiftBar 里肉眼确认。
4. P2：统计各域一级项数量和最大菜单深度（≤3），对照改前（算力域 16 项、深度 4~5）。
5. P3：运行 `bar-lint`，全部断言通过。
